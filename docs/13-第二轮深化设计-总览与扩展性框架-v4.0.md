# 第二轮深化设计：总览与扩展性框架 v4.0

> 定位：在第一轮（v1.0–v3.0：范围 / 表结构 / 分模块业务细化）基础上，进入 **第二轮深化**。
> 本轮主线：**端到端流程（时序）+ 严谨状态机（转换表）+ 领域事件 + 接口契约 + 可扩展性框架 + 权限矩阵**。
> 原则：**业务级先于技术级**，可配置化、可扩展、可集成，紧扣"详细 + 可扩展"两大诉求。

## 一、第二轮目标、范围与方法论

### 1.1 第二轮要解决的问题

第一轮已把"有哪些业务、字段什么、规则怎样、异常怎么办"讲清楚。第二轮聚焦四个更深的问题：

| 问题 | 第一轮程度 | 第二轮深化 |
| --- | --- | --- |
| 业务是"怎么动"的？ | 文字步骤 | **时序图（who→what→when→result）** |
| 状态到底怎么流转？ | 状态列表 | **转换表：前置条件、动作、事件、副作用、权限** |
| 模块间怎么协作？ | 引用关系 | **领域事件 + 订阅关系（解耦、可扩展）** |
| 以后怎么加业务？ | 提及可配置 | **扩展点清单 + 工作流引擎 + 插件化 + 版本化** |

### 1.2 第二轮深化范围

- **横向**：贯通"询价→报价→委托单→订舱→操作→报关→在途→签收→结算→关账"全链路（含进口、多式联运、电商小包多条主线）。
- **纵向**：对主干单据（委托单、订舱、报关、出入库、应收应付、工单、异常）给出**严格状态机转换表**。
- **跨切面**：领域事件目录、RBAC 权限矩阵、接口契约模式、SLA 与指标口径、幂等与编号、扩展性框架。

### 1.3 深化方法论（每条深化文档统一模板）

每个 `-v4.0` 模块文档统一包含 7 个部分（模板见 `第十节`）：

1. 业务目标与范围再确认
2. 端到端时序图（含角色、外部系统、前置/后置条件）
3. **状态机转换表**（状态、转换、守卫条件、动作、产生事件、权限）
4. 字段联动与计算规则（重点：自动带出、校验、锁定）
5. 领域事件进出（发布 / 订阅清单）
6. 可扩展点与参数化（本模块支持哪些"加业务不加代码"）
7. 补充异常、指标口径与待 V5 深化项

### 1.4 第二轮不做的事

- 不做具体代码 / DDL 最终落地（保留至技术设计阶段，DDL 以 `02` 为基线延展）。
- 不做 UI 高保真，只给出页面/角色/交互要点与接口所支撑的能力。
- 不锁定单一业务侧重：**先覆盖全链路主达通用模型，再用扩展点支撑细分模式**（直客 / 同行 / 电商 / 项目物流）。

## 二、可扩展性框架（本轮核心）

扩展性是第二轮的"第一诉求"。设计原则：**主链路稳定、业务差异收口到配置与插件**，让新增模式不改主流程、不破坏历史数据。框架分五层。

### 2.1 分层扩展模型

```
┌────────────────────────────────────────────────────────────┐
│  A. 扩展点（Extension Point）      —— 在哪里可以插入新逻辑      │
├────────────────────────────────────────────────────────────┤
│  B. 领域事件（Domain Events）      —— 模块间怎么松耦合协作       │
├────────────────────────────────────────────────────────────┤
│  C. 规则与工作流引擎（Config）     —— 状态机/费用/校验/审批可配置  │
├────────────────────────────────────────────────────────────┤
│  D. 数据扩展（Multi-tenant + EAV + 字典 + 编号） —— 模型怎么扩展 │
├────────────────────────────────────────────────────────────┤
│  E. 集成边界（Adapter / ACL）      —— 换一家船公司/海关/支付不动核 │
└────────────────────────────────────────────────────────────┘
```

### 2.2 扩展点清单（Extension Point Registry）

扩展点 = 业务处理链路中允许"注册新逻辑但不改核心代码"的锚点。统一用事件/钩子承载。

| # | 扩展点 | 所属链路 | 说明 | 承载机制 |
| --- | --- | --- | --- | --- |
| EP-1 | 报价计算前/后 | 报价 | 计价前补充规则、价后调价/审批 | 钩子+规则 |
| EP-2 | 委托单校验/确认前 | 委托单 | 客户自定义必填、信用/风控检查 | 规则引擎 |
| EP-3 | 订舱提交前 | 订舱 | 承运人校验、危险品/合规强校验 | 规则引擎 |
| EP-4 | 单证生成时（BL/SI/装箱单） | 操作 | 按客户/航线定制单据模板、盖章 | 模板+钩子 |
| EP-5 | 跟踪事件入站后 | 跟踪 | 事件归一化、E2E 映射、命中规则 | 管道+规则 |
| EP-6 | 报关申报前后 | 关务 | 预归类、商检唤起、监管证件校验 | 规则引擎 |
| EP-7 | 出入库收放货前后 | WMS | 质检、计量、打包、增值服务 | 作业钩子 |
| EP-8 | 应收/应付生成时 | 财务 | 费用联动（改价/汇率/税）、价目嵌入 | 记账+规则 |
| EP-9 | 付款/收款核销前 | 财务 | 冲抵策略、现金流控制 | 规则引擎 |
| EP-10 | 通知发送前后 | 通知 | 模板变量、渠道选择、去重、发送方验证 | 管道+模板 |
| EP-11 | 工单/异常升级时 | 客服 | SLA 升级、自动分派、动作建议 | 规则+编排 |
| EP-12 | 主数据生效/变更前 | 基础资料 | 唯一性合并、变更审批、级联停用评估 | 审批+钩子 |

> 每个 EP 在 `-v4.0` 模块文档中登记：触发时机、上下文对象、可插入的能力类型（校验/计算/通知/审批/转换）、权限要求。

### 2.3 规则引擎与工作流引擎（配置驱动）

- **规则引擎**：布尔+动作式 DSL（IF 条件 THEN 动作），用于校验、费用计算、审批路由、SLA 判定。规则可版本化、可按租户/客户/模式作用域覆盖。
- **工作流引擎**：审批流与节点编排，支持"顺序/并行/会签/或签/条件分支"，节点可绑定动作（更新状态、发事件、生成任务、调外部）。
- **状态机引擎**：状态转换由配置表驱动（见 `第三节` 转换表），支持**加状态、合并状态、改转换守卫**而无需改码——这是"可扩展"的关键。
- **费用引擎**：费用项/算法/币种/汇率/税均为配置（延续 v3 计价引擎，本轮补齐"价目优先级 + 汇率锁定"的确定性规则）。

### 2.4 数据扩展（多租户、EAV、字典、编号）

| 机制 | 用途 | 约束 |
| --- | --- | --- |
| 多租户隔离 | 组织数据隔离（租户维度字段 `org_id`） | 核心链路所有读写按租户过滤 + 数据权限 |
| 扩展字段（EAV/JSON） | 客户/合作方/单据的个性化字段 | 关键计算仍走显式列，扩展字段仅辅助 |
| 系统字典 | 枚举值可配置（柜型/状态/费用类型…） | 字典项变更需评估历史数据兼容 |
| 编号规则 | 单据号/客户号/船名航次生成规则可配 | 编码规则表 `t_code_rule` 驱动 |
| 版本化 | 主数据、规则、报价模板、关联模板可版本化 | 变更留痕、可回滚、历史引用锚定版本 |
| 数据视图 | 同实体多种业务视图（出口/进口/电商） | 通过类型字段化 + 视图配置，避免表爆炸 |

### 2.5 集成边界（Adapter / Anti-Corruption Layer）

外部系统（船公司、海关单一窗口、航司、GPS、支付、财务 ERP、电子签）一律通过适配器接入：

- **标准内部协议**：内部业务统一使用领域事件 + 内部契约；外部差异在适配器内消化。
- **幂等 + 去重**：外发/入站消息带 `event_id`、`request_id`，消费方幂等。
- **重试 + 死信 + 补偿**：异步失败进重试队列，超限进工单/告警。
- **协议矩阵**：EDI(IFTMIN/IFTSTA)、Cargo IMP、海关报文、REST、MQTT 统一映射为内部跟踪事件/状态（延续 `01/7.1`）。
- **换供商无感**：切换船公司/支付/物流跟踪源，仅改适配器，核心状态机与费用计算不受影响——这是"可集成可扩展"的直接体现。

## 三、端到端主线流程（时序）

> 本轮把主线从"文字步骤"升级为**时序 + 里程碑**。里程碑是跨模块统一节点，用于 SLA 度量、通知触发、状态聚合。

### 3.0 统一里程碑（Milestone）

出海运全链统一里程碑如下（空运/铁路映射适配）：

| Milestone | 含义 | 触发源 | 主依赖单据 |
| --- | --- | --- | --- |
| M-01 已收托 | 委托单确认 | 委托单 | order |
| M-02 已订舱 | 舱位/订舱确认 | booking | booking |
| M-03 已收柜（补料） | SI/装箱信息齐 | ops | bl/si |
| M-04 已装船/艏 | 离港 | tracking | container |
| M-05 已在途 | 航行中 | tracking | container |
| M-06 已到港 | 抵港 | tracking | container |
| M-07 已放行 | 进口清关放行 | customs | customs |
| M-08 已提货/送货 | 提柜/派送 | tracking+ops | delivery |
| M-09 已签收 | 签收 | tracking | delivery |
| M-10 已开票 | 应收生成 | finance | ar_invoice |
| M-11 已回款 | 收款核销 | finance | payment |
| M-12 已结案 | 关账 | finance | close |

> 主委托单状态聚合 = 里程碑映射 + 段状态合并（延续 v3 order `9.3`）。里程碑表驱动 SLA 看板与预警，可在配置层增删。

### 3.1 海运出口 FCL 主链路（时序）

```
客户  →委托单→  销售/操作   →订舱→    船公司/海外代理
销售  →报价→  系统(计价)   →SO下行→    承运人
操作  →补料SI→  系统校验     →预付EDI→  船司
操作  →拖车/装箱→  订舱集装箱 →装船事件→ 跟踪
海关  →报关申报→  单一窗口     →放行→    海关
财务  →费用联动→ 应收/应付    →开票回款→ 核销
跟踪  →里程碑M04..M09 → ETA/异常 → 客服/通知
```

关键时序（简）：

```
1. 客户提交委托单(含货物/目的地/时效)
2. 操作确认并自动/手工下订舱 → 校验舱位/危险品/合规(EP-3)
3. 订舱成功→SO 下行→舱位确认 → 触发委托单"已订舱"(M-02)
4. 拖车/装箱计划生成 → 补料 SI 齐 → 装船前数据闭合(M-03)
5. 报关申报前置(工厂集港前) → 放行为装船必要条件
6. 装船事件入站→委托单"已发运"(M-04)→后续 M05-M09 由跟踪自动推进
7. 目的港放行+提货派送 → 签收(M-09)
8. 全程费用联动 → 应收开票 → 回款核销 → 关账(M-10~M-12)
```

> 完整时序图（含消息/回调/异常回滚）在各模块 `-v4.0` 文档中以 Mermaid 绘制。

### 3.2 空运出口主链路

```
订舱→ 航司 Cargo IMP 预定舱位 → 建单(AWB) → 安检/库收货 → 组板 → 交运 → 起飞
       中间段: 中转/航班衔接 → 目的地 → 清关 → 提货派送 → 签收
```
- 差异点：按航司 Cargo IMP 报文跟踪，AWB 号贯穿；危险品/温控强校验前置。

### 3.3 海运进口主链路

```
国外段(海外代理/船司跟踪) → 到港预告(到货通知) → 换单 → 进口清关申报 → 放行 → 拖车提柜/派送 → 签收
```
- 差异点：以"到港预告 + 换单"为入口，报关主体为进口商，海外代理为上游数据源（EP-5 跟踪归一化）。

### 3.4 多式联运主链路

```
委托单(起运段/中段/末段多子委托/段) → 各段独立状态机 → 段间交接事件(换单/转运)
  海铁/海陆/空铁：段衔接触发"交接"里程碑 → 整体=各段合并 → 异常跨界联动
```
- 差异点：**段状态机中枢**（延续 v3 `9.3`），交接节点异常需跨段回溯责任（`07/3.6`）。

### 3.5 电商小包主链路

```
集货入海外仓/FBA → 出库单 → 装载(打托/贴标/装箱) → 干线订舱 → 在途 → 目的仓入仓 → 派送 → 签收/退货
```
- 差异点：SKU 粒度、批次/箱唛管理、出库即结转成本，WMS 优先，费用按包裹粒度聚合。

## 四、全局状态机族谱与转换表（主干单据）

> 这是"状态机可配置化"的落地。下列给出**主干单据的最核心转换**，守卫条件=可配置规则；每张表在对应 `-v4.0` 文档中扩展为全量并与 `02` 表结构对齐。

### 4.1 委托单（Order）核心转换表

| 始态 | 终态 | 触发（动作/事件） | 守卫（可配置） | 副作用动作 | 产生事件 | 权限 |
| --- | --- | --- | --- | --- | --- | --- |
| 草稿 | 待确认 | 提交 | 必填项完整 | 校验必填 | `order.submitted` | 销售/客户 |
| 待确认 | 已确认 | 确认 | 费用预算齐、风控通过 | 锁价/锁汇率 | `order.confirmed` | 销售/操作 |
| 已确认 | 已订舱 | 下订舱成功 | 主委托含订舱要求 | 生成 booking | `booking.created` | 操作 |
| 已确认 | 已取消 | 撤单/被拒 | 撤单规则、违约金评估 | 释放资源 | `order.cancelled` | 销售/主管 |
| 已订舱 | 操作中 | 开始操作 | 已收到 SO | 生成作业任务 | `ops.started` | 操作 |
| 操作中 | 已发运 | 跟踪"已装船/起飞" | 单证齐全 | 里程碑 M-04 | `milestone.reached` | 系统 |
| 已发运 | 在途 | 跟踪在途事件 | 无 | 推进 M-05 | `milestone.reached` | 系统 |
| 在途 | 已到港 | 跟踪抵港 | 无 | 推进 M-06 | `milestone.reached` | 系统 |
| 已到港 | 已派送 | 提货/派送完成 | 清关放行 | 推进 M-08 | `milestone.reached` | 系统/操作 |
| 已派送 | 已签收 | 签收事件 | 无 | 推进 M-09 | `milestone.reached` | 系统 |
| 已签收 | 已结算 | 费用核对/开票回款 | 余额清零 | 关账前置检查 | `order.settled` | 财务 |
| 已结算 | 已关账 | 关账 | 审计通过 | 锁定/归档 | `order.closed` | 财务/主管 |

> 异常/回滚：订舱失败→回滚"已确认"；改单只在非"已关账"且非关键已发生节点时允许（v3 order 变更规则表）。

### 4.2 订舱（Booking）核心转换表

| 始态 | 终态 | 触发 | 守卫 | 副作用 | 事件 | 权限 |
| --- | --- | --- | --- | --- | --- | --- |
| 草稿 | 待确认 | 提交 | 配额/危险品/合规 | — | `booking.submitted` | 操作 |
| 待确认 | 已订（SO吊下） | 舱位确认 | 舱位配额扣减成功 | 扣舱位、通知委托单 | `booking.confirmed` | 操作/系统 |
| 待确认/已订 | 已取消 | 撤单 | 撤单窗口与规则 | 释放舱位 | `booking.cancelled` | 操作/主管 |
| 已订 | 已装船 | 装船事件 | 单证(补料)齐 | M-04 | `milestone.reached` | 系统 |
| 已装船/已到港 | 已完成 | 航程结束+结费 | 费用核对 | 归档 | `booking.completed` | 操作/财务 |

| --- | --- | --- | --- | --- | --- | --- |

### 4.4 WMS 入库（Inbound）核心转换表

## 五、领域事件目录（Domain Event Catalog）

事件是模块松耦合协作的唯一正式通道（配合 EP 扩展点）。事件统一带 `event_id / event_type / occurred_at / entity_type / entity_id / tenant / payload_version`。

### 5.1 事件分组与消费方

| 事件域 | 事件 | 发布方 | 主要订阅方 | 用途 |
| --- | --- | --- | --- | --- |
| 报价 settlement | `quotation.issued` / `quotation.accepted` | 报价 | 委托单、CRM、销售报表 | 转单、商机回收、命中率 |
| 订单 | `order.*`（submitted/confirmed/cancelled/…） | 订单 | 订舱、财务、通知、跟踪 | 驱动主链路与 SLA |
| 订舱 | `booking.*` | 订舱 | 订单、操作、报关、通知 | 状态联动 |
| 跟踪 | `milestone.reached` / `tracking.changed` / `eta.updated` | 跟踪 | 订单、通知、客服、SLA | 里程碑推进、预警 |
| 报关 | `customs.*` | 关务 | 订单、跟踪、工单、通知 | 放行联动、例外 |
| 仓储 | `inventory.changed` / `inbound.*` / `outbound.*` | WMS | 财务、通知、跟踪 | 成本结转、预警 |
| 财务 | `ar.issued` / `payment.received` / `ap.paid` / `fx.locked` | 财务 | 对账、报表、通知、信用 | 结案、信用额度释放 |
| 客服 | `exception.*` / `ticket.*` | 客服 | 通知、SLA、报表 | 升级、满意度 |
| 主数据 | `partner.statusChanged` / `customer.creditChanged` / `hs.updated` | 基础资料 | 各业务模块、权限 | 合规、风险 |
| 通知 / 审计 | 发送成功/失败、操作日志 | 通知/审计 | 报表、告警 | 可观测性 |

### 5.2 事件使用规则

- **单向流动**：下游订阅方处理失败不阻塞上游（异步、可重放）。
- **Exactly-once / 幂等**：消费端按 `event_id` 幂等，可重放。
- **Saga/补偿**：跨模块事务用 Saga（如订舱失败→回滚订单）而非分布式强一致。
- **版本化 payload**：事件带 `payload_version`，升级兼容、可迁移。
- **审计**：业务关键状态变更同时写操作日志，记录事件来源链（`t_operation_log`）。

## 七、接口契约设计模式（API Contract）

> 目的：让"前端/外部/集成"与"业务能力"对齐，为可扩展打底。所有接口遵守统一风格。

### 7.1 统一约定

- RESTful，路径 `/{tenant}/api/v1/{domain}/{resource}`。
- 成功返回统一信封：`{ code, message, data, request_id, elapsed_ms }`。
- 幂等：写入接口必须带 `Idempotency-Key`（业务唯一键），重复提交返回首次结果。
- 错误码分层：`ERR_<DOMAIN>_<CODE>`（如 `ERR_ORDER_1024`）。
- 分页/过滤/排序约定统一；列表接口数据权限自动叠加。

### 7.2 主干接口清单（示例，`-v4.0` 展开为契约详情）

| 域 | 接口 | 说明 |
| --- | --- | --- |
| 报价 | `POST /quotation/compute` | 报价试算（入参货物/路线/费率，出参费用+利润） |
| 报价 | `POST /quotation` / `POST /quotation/{id}/accept` | 建报价 / 采纳转委托 |
| 委托单 | `POST /orders` / `POST /orders/{id}/confirm` | 建委托 / 确认 |
| 订舱 | `POST /bookings` / `POST /bookings/{id}/cancel` | 下订舱 / 撤单 |
| 跟踪 | `POST /tracking/events` / `GET /orders/{id}/timeline` | 事件入站 / 时间线 |
| 报关 | `POST /customs/declarations/{id}/submit` | 申报 |
| 财务 | `POST /ar/invoices` / `POST /payments/received/allocate` | 开票 / 收款核销 |
| 通知 | `POST /notifications` / `POST /notifications/{id}/events` | 发送 / 回执 |

### 7.3 幂等与一致性示例（订舱→订单回滚 Saga）

```
提交订单 → POST /orders {idempotencyKey}
确认订舱 → POST /bookings {idempotencyKey}（守卫：舱位/合规）
订舱失败 → 发布 booking.cancelled → 订阅方 order 回滚至"已确认"
全部步骤在同一 request_id 下可追踪审计链
```

## 十一、与既有文档的衔接与演进规则

- **版本演进**：新增/修改走新版本号（`v4.0 → v4.1 …`），不覆盖历史版本；README 维护版本清单与状态。
- **一致性**：所有 `-v4.0` 的状态、事件、EP 编号、字段须与 `01`、`02`、`03-12` 对齐；发现冲突时标注并回写相应基线。
- **唯一事实源**：表结构以 `02` 为唯一事实源，`-v4.0` 只深化业务语义不擅自改 DDL；确需新增字段在文档中显式登记"待更新 `02`"。
- **可持续**：每完成一个模块文档，回填本总览 `第九节` 表格状态并更新 README。

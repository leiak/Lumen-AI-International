# 计费失败取证链路的正确性 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把「计费规则求值失败时,账上不留任何痕迹且请求挂 50 秒」这条链路修好,并用端到端 IT 钉死它。

## 三条必须先知道的机制(照着写 IT,别凭直觉)

这三条是本轮 IT 设计的地基,写错一条 IT 就会假绿:

**① Spring 事务是线程绑定的。** `DataSourceUtils` 会把连接绑到线程上 —— 即使被调方**没有** `@Transactional`,只要调用方线程上已有事务,写操作照样加入那个事务。所以「有没有 `@Transactional`」和「有没有外层事务」是两件事。

**② 自调用会绕过代理。** `estimateAndAccrue` 内部调 `accrue(event)` 是同 bean 直接调用 → `accrue` 上的 `@Transactional` **不生效**。后果:
- `estimateAndAccrue` **没有**外层事务时 → `accrue` 的三次写入各自自动提交 → `event_log` 那行**已提交** → REQUIRES_NEW 去 UPDATE 它**不冲突** → **不会挂 50 秒**。
- 生产环境之所以会挂:`createForCustomer` 自带 `@Transactional`(dispatch 模块 `DeliveryOrderServiceImpl:630`),`BusinessEventListener` 是跨 bean 调 `accrue`(走代理 → 自带事务)。**两条路都有外层事务**,`event_log` 那行未提交、持 X 行锁 → REQUIRES_NEW 的 UPDATE 等锁。

> **所以 Task 3 的 IT 必须自己造一个外层事务**,否则测不出锁等待。

**③ 状态字面量**:`t_billing_event_log.process_status` ∈ {`RECEIVED`, `SUCCESS`, `FAILED`, `NO_RULE`};`t_billing_accrual.status` ∈ {`OPEN`, `OPEN_FAILED`, `RELEASED`, `CONVERTED`, `LOCKED`}。

### Task 2: 缺陷 ① —— `rule_id` NOT NULL 让 OPEN_FAILED 取证行写不进去

**背景:** `writeEstimateAndAccrueFailure`(`BillingEngineServiceImpl.java:386`)不设 `ruleId` → MyBatis-Plus 3.5.7 默认 `insertStrategy = NOT_NULL`(全仓无任何 `insert-strategy` 配置覆盖)把该列从 INSERT 里整个省略 → MySQL strict mode 报 **1364 Field 'rule_id' doesn't have a default value** → 异常从 `estimateAndAccrue` 抛出。

两个受害面:
- 门户路径(`createForCustomer`)异常被 `catch (Exception)` 吞掉 → **订单照常提交,账上零行痕迹**。
- 直接调 `estimateAndAccrue` 的调用方会**直接吃到这个异常**(它本该"失败不抛")。

修法:新增迁移把 `rule_id` 改可空。**不用「补 ruleId」** —— `EstimateResult` 的 javadoc 明确「ruleId 仅 SOURCE_RULE 时非空」,override 命中时本就没有 rule 归属;estimate 阶段失败时规则归属**本就未知**,硬填一个值反而是编造。

### Task 3: 缺陷 ② + ③ —— REQUIRES_NEW 锁等待 + 异常类型失真

**背景:** `accrue` 先在**外层未提交事务**里 INSERT `event_log`(持 X 行锁),求值失败时开 `REQUIRES_NEW` 去 UPDATE 同一行 → 内层等外层 → `innodb_lock_wait_timeout`(默认 **50 秒**)。**两条生产调用路径都中招**(`createForCustomer` 与 `BusinessEventListener`)—— 回滚发生在异常抛出**之后**,而在异常抛出之前那一行一直未提交、一直被持锁。

修法(A2):把 `markFailed`(event_log 标 FAILED)移出 `REQUIRES_NEW`,留在 accrue 自己的事务里 —— UPDATE 与 INSERT 同事务 → 自己改自己未提交的行 → 无冲突。`writeFailedAccrual`(写 OPEN_FAILED accrual)留在 `REQUIRES_NEW` —— 它必须活过外层回滚。

修法(A3):取证写库失败不能顶掉要抛的 `FinanceException`。

> **IT 必须自己造外层事务**(见「三条机制」②): 直接调 service 而没有外层事务时, `accrue` 的
> `event_log` INSERT 会自动提交 → REQUIRES_NEW 去 UPDATE 它不冲突 → **测不出锁等待**。

### Task 5: A5 —— `estimateAndAccrue` 的事务护栏

**背景:** `estimateAndAccrue` 是计费引擎的对外入口。今天**没有**自己的事务边界 —— 它靠调用方提供。这是契约隐患:将来若有人从非事务上下文调它,`accrue` 的三次写入会退化成逐语句自动提交,出现「写了一半」。

**先说清楚它今天 0 行为变化**,别在交付说明里夸大:

- Spring 事务是**线程绑定**的 —— 即使没有 `@Transactional`,只要调用方线程上已有事务,写操作照样加入那个事务(DataSourceUtils 复用同一连接)。所以加这个注解**不改变**「有没有外层事务」这件事下的任何行为。

## 五个必须知道的坑（实现前读完，少一个就做错）

### 坑 1: 对账表叫 `t_reconciliation`, 不叫 `t_billing_reconciliation`

`BillingReconciliation` 实体的 `@TableName` 是 `t_reconciliation` (V31 建表)。全仓 `grep -rn t_billing_reconciliation` **零命中**。写错表名, V39 在 Flyway 阶段直接失败, 全盘 IT 挂掉。

### 坑 2: 权限码 V33 就种过两个, 重种会撞唯一键

`sys_permission` 上有 `UNIQUE KEY uk_perm_tenant_code (tenant_id, code)`, 而 V33 的 INSERT 写的是 `ON DUPLICATE KEY UPDATE`。**用新 id 重插已存在的 code, 撞的是这个唯一键而不是主键, MySQL 会就地更新已存在的那一行, 新 id 永远不会被创建。** V37 正是为此擦屁股 (V36 用 166/167 重插 160/161 的 code, 生成两条悬空 `sys_role_permission`)。

已存在: `customer:invoice:view` (162) / `customer:recon:view` (163)。本轮只新增 **3 个**。

### 坑 3: 只种 `sys_permission` 不够, 还要改 `PortalAuthService.CUSTOMER_PERMS`

`CUSTOMER_PERMS` 是**硬编码的权限码清单** (Task 1 之前 8 个, Task 1 之后 11 个), 在 `issueToken` 里原样塞进 JWT 的 `perms` claim —— **它不查 `sys_role_permission`**。漏改的后果: 登录拿到的 token 里没有新权限码, 4 个新 controller 的每个端点都 403, 且日志看不出是 seed 还是鉴权的问题。Task 1 用真实 `JwtUtil` 解析 token 把这条焊死。

### 坑 4: 实体没有 `deleted` 字段, 逻辑删除不会自动生效

`BillingReconciliation` / `BillingPaymentRecord` 的字段表里**没有 `deleted`** (而 DDL 有 `deleted TINYINT NOT NULL DEFAULT 0`), 且全仓**没有配 MyBatis-Plus 全局逻辑删除**。MP 因此不会自动补 `deleted = 0` —— 商家视图必须显式 `.apply("deleted = 0")`, 否则会把已删的账单行展示给商家。(`BillingInvoice` / `BillingAdjustment` 有 `@TableLogic`, 走自动过滤。)

### 坑 5: 既有 `list` 方法漏了 tenantId 过滤, 别照抄

`ReconciliationServiceImpl.list` 与 `PaymentRecordServiceImpl.list` 的 `LambdaQueryWrapper` 里**没有 `.eq(tenantId)`** —— 收了参数不用。商家门户**不得复用这两个方法**。新代码里任何漏掉 tenantId 的地方都是越权面。

**另外**: `PortalErrorCode` 的枚举参数顺序是 `(code, httpStatus, message)`, `FinanceErrorCode` 是 `(code, message, httpStatus)` —— **两者相反**, 照抄错一个编译器不报错, 运行时 httpStatus 全错。

```sql
-- =============================================================
-- V39: t_reconciliation 加商家异议三列 (4.5C-2)
--
-- 背景:
--   ReconciliationServiceImpl.runReconciliation 对每一笔非零差异已经自动建好
--   一张 DRAFT 调账单 (只 create, 从不 submit), 并把 recon 置为 ADJUSTMENT_CREATED。
--   商家看到差异时调账单已经存在 —— 他要表达的是「我不认可这个差额」, 而不是
--   「再建一张调账单」(那是对同一笔差异的双重调账)。
--
--   本迁移给商家一个留下主张的位置: 声明 + 理由 + 时间。非空 dispute_at 即代表
--   该期次已被异议过 (同一期只允许一次), 兼作幂等标记。
--
--   落在 recon 行而非 adjustment 行: 商家异议的自然粒度是
--   (period, direction, counterparty), 正是 recon 的粒度
--   (uk_recon_tenant_period_cpty); 而 t_billing_adjustment 没有 counterparty_id
--   也没有 period, 放那儿得新建关联表。
--
-- 列约定:
--   DATETIME(3) 与该表既有 created_at / updated_at 同精度 (V31)。
--   无 DB 侧 DEFAULT —— 异议时间是事件时间不是行创建时间, 由应用写入。
--   与 V30 的多列批量 ADD COLUMN ... AFTER ... 写法一致。
--
--   不动 V31 本身 —— Flyway 已记录其 checksum, 改动会导致校验失败。
-- =============================================================

ALTER TABLE t_reconciliation
  ADD COLUMN dispute_amount DECIMAL(18,4) NULL COMMENT '商家主张金额, NULL = 仅质疑不主张' AFTER remark,
  ADD COLUMN dispute_reason VARCHAR(500) NULL COMMENT '商家异议理由' AFTER dispute_amount,
  ADD COLUMN dispute_at     DATETIME(3)   NULL COMMENT '异议时间, 非空即该期已被异议' AFTER dispute_reason
;
```

```java
package com.lumen.finance.dto.portal;

import java.util.List;

/**
 * 商家门户分页结果 (Iteration 4.5C-2).
 *
 * <p><b>不复用</b> {@code com.lumen.common.dto.PageResult}: 那个的字段叫
 * {@code pageNum} / {@code pageSize}, 与门户前端契约的 {@code page} / {@code size}
 * 只差一个字。复用它会让每个 controller 里多一层手写改名, 而这类改名每处都是
 * 潜在的 off-by-one 现场。门户契约自己定义一份更便宜。
 *
 * <p>字段名 {@code records} 而非 MyBatis-Plus 的 {@code current}/{@code size},
 * 免得调用方误以为这是 {@code IPage} 的直接投影。
 *
 * @param records 当前页数据
 * @param total   总条数 (前端分页器直接用)
 * @param page    当前页码, 从 1 开始
 * @param size    每页条数
 */
public record MerchantPage<T>(List<T> records, long total, long page, long size) {

    public static <T> MerchantPage<T> of(List<T> records, long total, long page, long size) {
        return new MerchantPage<>(records, total, page, size);
    }

    /** 空结果 — 归属集为空时直接返回, 省掉一次 in () 查询。 */
    public static <T> MerchantPage<T> empty(long page, long size) {
        return new MerchantPage<>(List.of(), 0L, page, size);
    }
}
```

```java
 * 商家视角的账单只读查询 (Iteration 4.5C-2).
 *
 * <p><b>为什么不直接复用 {@code ReconciliationService.list} /
 * {@code PaymentRecordService.list}</b>: 那两个方法的 {@code LambdaQueryWrapper}
 * 里既没有 {@code counterparty_id} 也没有 {@code tenant_id} —— 收了参数不用。
 * 对内是"财务看全部"的既定语义, 对外是越权面。窄接口把商家隔离做成
 * <b>实现细节而不是调用约定</b>: controller 传进来的 {@code counterpartyId}
 * 一定是当前登录商家的 (取自 JWT 的 {@code aud}), 没有第二个值可传。
 *
 * <p><b>三条可见性铁律</b> (每个查询方法都必须满足, 缺一条就是越权):
 * <ol>
 *   <li>{@code tenant_id = :tenantId} —— 收参数不用是最常见的漏洞形态</li>
 *   <li>{@code counterparty_id = :counterpartyId} —— 商家只看自己的</li>
 *   <li>{@code direction = 'RECEIVABLE'} —— 商家门户只呈现应收侧; 应付是平台付给别人的账</li>
 * </ol>
 *
 * <p>软删除另说: {@code BillingReconciliation} / {@code BillingPaymentRecord}
 * 的实体<b>没有</b> {@code deleted} 字段 (DDL 有), 且全仓未配 MyBatis-Plus 全局逻辑删除,
 * 所以这两张表必须显式 {@code .apply("deleted = 0")}。{@code BillingInvoice} 有
 * {@code @TableLogic}, 反而<b>不能</b>手写 —— 写了会与 MP 追加的条件重复。
 */
public interface MerchantBillingViewService {

    /**

     *
     * @throws com.lumen.finance.exception.FinanceException 无查询参数级异常

    MerchantPage<ReconView> listReconciliations(Long tenantId, Long counterpartyId, String period, long page, long size);

    /**
     * 查单条对账单。
     *
     * @throws com.lumen.finance.exception.FinanceException {@link FinanceErrorCode#RECONCILIATION_NOT_FOUND} —
     *         行不存在<b>与</b>行不属于该商家走同一码, 不泄漏别人的资源是否存在

    ReconView getReconciliation(Long tenantId, Long counterpartyId, Long id);

    /** 分页查发票 (期间 / 状态均可选, null = 不过滤)。 */
    MerchantPage<InvoiceView> listInvoices(Long tenantId, Long counterpartyId, String period, String status, long page, long size);

    /**
     * 查单张发票。
     *
     * @throws com.lumen.finance.exception.FinanceException {@link FinanceErrorCode#INVOICE_NOT_FOUND}
     */
    InvoiceView getInvoice(Long tenantId, Long counterpartyId, Long id);

    /** 分页查付款记录 (期间可选, null = 全期可见)。 */
    MerchantPage<PaymentView> listPayments(Long tenantId, Long counterpartyId, String period, long page, long size);

    /**
     * 分页查"我的调账单"。
     *
     * <p>{@code t_billing_adjustment} <b>既没有 {@code counterparty_id} 也没有 {@code period}</b>,
     * 直接查必然越权。归属靠两跳还原: (a) {@code t_reconciliation.adjustment_id} ——
     * 月结跑出来的自动调账单; (b) {@code t_billing_invoice.source_invoice_id} ——
     * 发票上挂的调账单。两跳都先按 {@code counterparty_id} 收口。

    MerchantPage<AdjustmentView> listMyAdjustments(Long tenantId, Long counterpartyId, long page, long size);

    AdjustmentView getMyAdjustment(Long tenantId, Long counterpartyId, Long adjustmentId);
```

```java
import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.baomidou.mybatisplus.core.metadata.IPage;
import com.baomidou.mybatisplus.extension.plugins.pagination.Page;
import com.lumen.finance.FinanceConstants;
import com.lumen.finance.dto.portal.MerchantDtos.AdjustmentView;
import com.lumen.finance.dto.portal.MerchantDtos.InvoiceView;
import com.lumen.finance.dto.portal.MerchantDtos.PaymentView;
import com.lumen.finance.dto.portal.MerchantDtos.ReconView;
import com.lumen.finance.dto.portal.MerchantPage;
import com.lumen.finance.entity.*;
import com.lumen.finance.exception.FinanceErrorCode;
import com.lumen.finance.exception.FinanceException;
import com.lumen.finance.mapper.*;
import com.lumen.finance.service.MerchantBillingViewService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.LocalDateTime;
import java.time.YearMonth;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;
import java.util.stream.Collectors;

/**
 * {@link MerchantBillingViewService} 实现 (Iteration 4.5C-2).
 *
 * <p>五个 mapper 注入, 全部走 {@code LambdaQueryWrapper} —— 本仓零 XML mapper,
 * 一行 mapper 接口都不用改。
 *
 * <p>所有查询都是<b>只读</b>的, 所以类上没有 {@code @Transactional}: 单条 SELECT
 * 自带一致性, 包一层事务只会多占一个连接。
 */
@Slf4j
@Service
@RequiredArgsConstructor
public class MerchantBillingViewServiceImpl implements MerchantBillingViewService {

    private final BillingInvoiceMapper invoiceMapper;
    private final BillingReconciliationMapper reconMapper;
    private final BillingPaymentRecordMapper paymentMapper;
    private final BillingAdjustmentMapper adjustmentMapper;
    private final BillingMonthlyClosingMapper closingMapper;

    /** 分页上限 —— 门户是给人看的, 不该允许一次拉十万行。 */
    private static final long MAX_PAGE_SIZE = 200L;

    // ------------------------------------------------------------------ 对账

    @Override
    public MerchantPage<ReconView> listReconciliations(Long tenantId, Long counterpartyId,
                                                         String period, long page, long size) {
        Page<BillingReconciliation> mp = Page.of(page, clamp(size));
        reconMapper.selectPage(mp, reconScope(tenantId, counterpartyId, period));

        Set<String> closed = closedPeriods(tenantId, mp.getRecords().stream()
                .map(BillingReconciliation::getPeriod).collect(Collectors.toSet()));

        return MerchantPage.of(
                mp.getRecords().stream().map(r -> toReconView(r, closed.contains(r.getPeriod()))).toList(),
                mp.getTotal(), mp.getCurrent(), mp.getSize());
    }

    @Override
    public ReconView getReconciliation(Long tenantId, Long counterpartyId, Long id) {
        BillingReconciliation r = reconMapper.selectOne(
                reconScope(tenantId, counterpartyId, null).eq(BillingReconciliation::getId, id));
        if (r == null) {
            throw new FinanceException(FinanceErrorCode.RECONCILIATION_NOT_FOUND,
                    "Reconciliation " + id + " not found for counterparty " + counterpartyId);
        }
        return toReconView(r, isPeriodClosed(tenantId, r.getPeriod()));
    }

    /**
     * 对账表的软删除必须手写: 实体无 deleted 字段, 且全仓无全局逻辑删除配置。
     *
     * <p>{@code period} 的 if 守卫同样必需 — {@code eq(col, null)} 会生成
     * {@code period = null}, 那会让"不筛期间"变成"只看 period 为空的行", 静默返回空集。
     */
    private static LambdaQueryWrapper<BillingReconciliation> reconScope(Long tenantId, Long counterpartyId,
                                                                        String period) {
        LambdaQueryWrapper<BillingReconciliation> w = new LambdaQueryWrapper<BillingReconciliation>()
                .eq(BillingReconciliation::getTenantId, tenantId)
                .eq(BillingReconciliation::getCounterpartyId, counterpartyId)
                .eq(BillingReconciliation::getDirection, FinanceConstants.DIR_RECEIVABLE)
                .apply("deleted = 0");
        if (period != null) {
            w.eq(BillingReconciliation::getPeriod, period);
        }
        return w;
    }

    private boolean isPeriodClosed(Long tenantId, String period) {
        if (period == null) {
            return false;
        }
        BillingMonthlyClosing c = closingMapper.selectOne(new LambdaQueryWrapper<BillingMonthlyClosing>()
                .eq(BillingMonthlyClosing::getTenantId, tenantId)
                .eq(BillingMonthlyClosing::getPeriod, period)
                .eq(BillingMonthlyClosing::getStatus, FinanceConstants.CLOSING_STATUS_CLOSED)
                .apply("deleted = 0"));
        return c != null;
    }

    /**
     * 列表页一次性把本页涉及的期间全查出来, 避免每行查一次 (N+1)。
     *
     * <p>{@code deleted = 0} 同样必须手写: {@code t_monthly_closing} 的 DDL 有
     * {@code deleted} 列 (且进了唯一键), 但实体没有该字段, 也没有全局逻辑删除配置。
     * 漏掉的后果不是"多查几行脏数据" —— 一条被软删却仍 {@code CLOSED} 的月结会让
     * 商家看到 {@code closed=true}, 而那正是异议闸门的依据, 商家会被静默禁止提异议。
     */
    private Set<String> closedPeriods(Long tenantId, Set<String> periods) {
        if (periods.isEmpty()) {
            return Set.of();
        }
        return closingMapper.selectList(new LambdaQueryWrapper<BillingMonthlyClosing>()
                        .eq(BillingMonthlyClosing::getTenantId, tenantId)
                        .in(BillingMonthlyClosing::getPeriod, periods)
                        .eq(BillingMonthlyClosing::getStatus, FinanceConstants.CLOSING_STATUS_CLOSED)
                        .apply("deleted = 0"))
                .stream().map(BillingMonthlyClosing::getPeriod).collect(Collectors.toSet());
    }

    private static ReconView toReconView(BillingReconciliation r, boolean closed) {
        return new ReconView(r.getId(), r.getPeriod(), r.getCurrency(),
                r.getExpectedAmount(), r.getActualAmount(), r.getVarianceAmount(),
                r.getAdjustmentId(), r.getReconciliationStatus(), r.getRemark(),
                r.getDisputeAmount(), r.getDisputeReason(), r.getDisputeAt(), closed);
    }

    // ------------------------------------------------------------------ 发票

    @Override
    public MerchantPage<InvoiceView> listInvoices(Long tenantId, Long counterpartyId,
                                                   String period, String status, long page, long size) {
        Page<BillingInvoice> mp = Page.of(page, clamp(size));
        invoiceMapper.selectPage(mp, invoiceScope(tenantId, counterpartyId, period, status));

        return MerchantPage.of(mp.getRecords().stream().map(MerchantBillingViewServiceImpl::toInvoiceView).toList(),
                mp.getTotal(), mp.getCurrent(), mp.getSize());
    }

    @Override
    public InvoiceView getInvoice(Long tenantId, Long counterpartyId, Long id) {
        BillingInvoice inv = invoiceMapper.selectOne(invoiceScope(tenantId, counterpartyId, null, null)
                .eq(BillingInvoice::getId, id));
        if (inv == null) {
            throw new FinanceException(FinanceErrorCode.INVOICE_NOT_FOUND,
                    "Invoice " + id + " not found for counterparty " + counterpartyId);
        }
        return toInvoiceView(inv);
    }

    /** 不手写 deleted —— BillingInvoice.deleted 有 @TableLogic, MP 会自动追加。 */
    private static LambdaQueryWrapper<BillingInvoice> invoiceScope(Long tenantId, Long counterpartyId,
                                                                   String period, String status) {
        LambdaQueryWrapper<BillingInvoice> w = new LambdaQueryWrapper<BillingInvoice>()
                .eq(BillingInvoice::getTenantId, tenantId)
                .eq(BillingInvoice::getCounterpartyId, counterpartyId)
                .eq(BillingInvoice::getDirection, FinanceConstants.DIR_RECEIVABLE);
        // 发票表的期间是拆成 period_year / period_month 两列的 (对账表才是 CHAR(7))
        if (period != null) {
            YearMonth ym = YearMonth.parse(period);
            w.eq(BillingInvoice::getPeriodYear, ym.getYear())
             .eq(BillingInvoice::getPeriodMonth, ym.getMonthValue());
        }
        // 同样是 if 守卫: status 为 null 时若直接 eq, MP 生成 `status = null`,
        // "不筛状态"会变成"只看 status 空的行"。
        if (status != null) {
            w.eq(BillingInvoice::getStatus, status);
        }
        return w;
    }

    private static InvoiceView toInvoiceView(BillingInvoice i) {
        return new InvoiceView(i.getId(), i.getInvoiceNo(), periodOf(i.getPeriodYear(), i.getPeriodMonth()),
                i.getBusinessType(), i.getGrossAmount(), i.getTaxAmount(), i.getNetAmount(),
                i.getCurrency(), i.getFxRateAtCreation(), i.getStatus(), i.getCreatedAt());
    }

    private static String periodOf(Integer year, Integer month) {
        if (year == null || month == null) {
            return null;
        }
        return String.format("%04d-%02d", year, month);
    }

    // ------------------------------------------------------------------ 付款

    @Override
    public MerchantPage<PaymentView> listPayments(Long tenantId, Long counterpartyId,
                                                   String period, long page, long size) {
        Page<BillingPaymentRecord> mp = Page.of(page, clamp(size));
        // LambdaQueryWrapper.eq(field, null) 会生成 `field = null` 而不是跳过 —— MP 的
        // 默认行为, 所以过滤条件一律用 if 守卫显式加。
        paymentMapper.selectPage(mp, paymentScope(tenantId, counterpartyId, period));

        return MerchantPage.of(mp.getRecords().stream().map(MerchantBillingViewServiceImpl::toPaymentView).toList(),
                mp.getTotal(), mp.getCurrent(), mp.getSize());
    }

    private static LambdaQueryWrapper<BillingPaymentRecord> paymentScope(Long tenantId, Long counterpartyId,
                                                                           String period) {
        LambdaQueryWrapper<BillingPaymentRecord> w = new LambdaQueryWrapper<BillingPaymentRecord>()
                .eq(BillingPaymentRecord::getTenantId, tenantId)
                .eq(BillingPaymentRecord::getCounterpartyId, counterpartyId)
                .eq(BillingPaymentRecord::getDirection, FinanceConstants.DIR_RECEIVABLE)
                .apply("deleted = 0");
        if (period != null) {
            w.eq(BillingPaymentRecord::getPeriod, period);
        }
        return w;
    }

    private static PaymentView toPaymentView(BillingPaymentRecord p) {
        return new PaymentView(p.getId(), p.getPeriod(), p.getCurrency(), p.getAmount(),
                p.getSourceRef(), p.getPaymentDate(), p.getSource(), p.getRemark());
    }

    // ------------------------------------------------------------------ 我的调账单

    @Override
    public MerchantPage<AdjustmentView> listMyAdjustments(Long tenantId, Long counterpartyId,
                                                          long page, long size) {
        Set<Long> ids = ownedAdjustmentIds(tenantId, counterpartyId);
        if (ids.isEmpty()) {
            return MerchantPage.empty(page, size);
        }
        Page<BillingAdjustment> mp = Page.of(page, clamp(size));
        adjustmentMapper.selectPage(mp, new LambdaQueryWrapper<BillingAdjustment>()
                .eq(BillingAdjustment::getTenantId, tenantId)
                .in(BillingAdjustment::getId, ids)
                .orderByDesc(BillingAdjustment::getCreatedAt));

        return MerchantPage.of(mp.getRecords().stream().map(MerchantBillingViewServiceImpl::toAdjustmentView).toList(),
                mp.getTotal(), mp.getCurrent(), mp.getSize());
    }

    @Override
    public AdjustmentView getMyAdjustment(Long tenantId, Long counterpartyId, Long adjustmentId) {
        if (!ownedAdjustmentIds(tenantId, counterpartyId).contains(adjustmentId)) {
            throw new FinanceException(FinanceErrorCode.ADJUSTMENT_NOT_FOUND,
                    "Adjustment " + adjustmentId + " not found for counterparty " + counterpartyId);
        }
        BillingAdjustment a = adjustmentMapper.selectOne(new LambdaQueryWrapper<BillingAdjustment>()
                .eq(BillingAdjustment::getTenantId, tenantId)
                .eq(BillingAdjustment::getId, adjustmentId));
        if (a == null) {
            // 归属集里有但行没了 —— 并发删除 / 归属两跳之间被改。不泄漏区别, 仍按 404。
            throw new FinanceException(FinanceErrorCode.ADJUSTMENT_NOT_FOUND,
                    "Adjustment " + adjustmentId + " not found");
        }
        return toAdjustmentView(a);
    }

    /**
     * 两跳还原"属于该商家的调账单 id 集"。
     *
     * <p>跳 1: {@code t_reconciliation.adjustment_id} —— 月结建出来的自动调账单,
     * recon 本身带 {@code counterparty_id}, 一句就收得住。
     * 跳 2: {@code t_billing_invoice.source_invoice_id} —— 发票上挂的调账单,
     * 走 invoice 的 {@code counterparty_id} 收口, 同样一句。
     *
     * <p>两张表都是先按商家过滤再取 id, 所以这里不存在"先全量取 id 再比对"的写法 ——
     * 那样会把别家商家的 id 短暂拉进内存。
     */
    private Set<Long> ownedAdjustmentIds(Long tenantId, Long counterpartyId) {
        Set<Long> ids = new LinkedHashSet<>();

        reconMapper.selectList(new LambdaQueryWrapper<BillingReconciliation>()
                        .select(BillingReconciliation::getAdjustmentId)
                        .eq(BillingReconciliation::getTenantId, tenantId)
                        .eq(BillingReconciliation::getCounterpartyId, counterpartyId)
                        .eq(BillingReconciliation::getDirection, FinanceConstants.DIR_RECEIVABLE)
                        .apply("deleted = 0")
                        .isNotNull(BillingReconciliation::getAdjustmentId))
                .stream().map(BillingReconciliation::getAdjustmentId).forEach(ids::add);

        Set<Long> invoiceIds = invoiceMapper.selectList(new LambdaQueryWrapper<BillingInvoice>()
                        .select(BillingInvoice::getId)
                        .eq(BillingInvoice::getTenantId, tenantId)
                        .eq(BillingInvoice::getCounterpartyId, counterpartyId)
                        .eq(BillingInvoice::getDirection, FinanceConstants.DIR_RECEIVABLE))
                .stream().map(BillingInvoice::getId).collect(Collectors.toSet());

        // 一次 IN 查完, 不按发票逐张查 —— 商家一年几百张发票就是几百次往返。
        if (!invoiceIds.isEmpty()) {
            adjustmentMapper.selectList(new LambdaQueryWrapper<BillingAdjustment>()
                            .select(BillingAdjustment::getId)
                            .eq(BillingAdjustment::getTenantId, tenantId)
                            .in(BillingAdjustment::getSourceInvoiceId, invoiceIds))
                    .stream().map(BillingAdjustment::getId).forEach(ids::add);
        }

        return ids;
    }

    private static AdjustmentView toAdjustmentView(BillingAdjustment a) {
        return new AdjustmentView(a.getId(), a.getAdjustmentNo(), a.getAdjustmentType(), a.getAmount(),
                a.getCurrency(), a.getGrossAmount(), a.getTaxAmount(), a.getNetAmount(),
                a.getStatus(), a.getReason(), a.getCreatedAt(), a.getL1Comment(), a.getL2Comment());
    }

    // ------------------------------------------------------------------ 杂项

    /**
     * {@code LambdaQueryWrapper.eq(col, null)} 生成的是 {@code col = null} 而不是跳过 ——
     * MP 默认如此 (要跳过得用 {@code eq(col, null)} + 手工 if, 或 {@code eq(boolean, ...)})。
     * 所以每个可选过滤条件都显式 if 守卫, 不靠传 null 蒙混。
     */
    private static long clamp(long size) {
        if (size <= 0) {
            return 20L;
        }
        return Math.min(size, MAX_PAGE_SIZE);
    }
```

### 附: "我的调账单" 归属两跳的设计约定 (Task 2 审查补记)

`t_billing_adjustment` **没有** `counterparty_id` / `direction` / `period` / `deleted` 列,
所以"这张调账单是不是我的"只能靠跳出来。约定如下 —— **Task 3/4/5 若再动归属逻辑,
必须先读这一节**:

**跳 1 (按 recon 行认领)**: 查 `t_reconciliation`, 条件 `tenant_id + counterparty_id +
direction=RECEIVABLE + deleted=0`, 取 `adjustment_id`。这是**归属的唯一权威来源**。

**跳 2 (按锚定发票命中)**: 查 `t_billing_adjustment`, 条件 `tenant_id + source_invoice_id IN
(我的发票 id 集)`。这跳本身**不判归属**, 只用来捞候选。

**认领表 (读侧消歧)**: 全租户查 `t_reconciliation` 的 `adjustment_id → counterparty_id`
映射, 跳 2 的候选里凡是 `owner != null && owner != 我的 counterpartyId` 的**一律剔除**。

四条容易踩的约定:

1. **认领表不过滤 `deleted`**。软删只是把 recon 藏起来, 不是解除归属。若按 `deleted=0`
   过滤, 被软删 recon 的调账单会重新从跳 2 漏给锚点所在商家 —— 反而打开泄漏。
2. **认领表不过滤 `direction`**。**加了会打开泄漏**: 跳 2 找的是"锚点在我的发票上的调账单",
   若把 PAYABLE 方向的认领滤掉, 被 PAYABLE recon 认领的调账单就会从跳 2 漏给锚点所在
   商家 —— 那才是真跨商家泄漏。当前不过滤的方向是"宁可多剔", 与全模块
   **漏看 ≠ 看错家** 的一致性相符。
3. **方向不对称是刻意的**: 跳 1 过滤 `direction=RECEIVABLE` (门户只看应收), 认领表不过滤。
   于是可能出现"我的调账单里有, 我的对账单里没有对应行"(PAYABLE 对手方的调账单恰好锚在
   我自己的发票上)。数据仍是我自己的, 只是观感不一致 —— 不要为了"对齐观感"去改跳 1。
4. **写侧同步修**: `AdjustmentDtos.CreateRequest.counterpartyId` (可选) → `resolveSourceInvoiceId`
   按 counterparty + direction 过滤 → `ReconciliationServiceImpl` 透传。**读侧认领表与写侧锚点
   共同闭环**, 两者都要在: 只改读侧 → 锚点仍可能串家 (只是被认领表挡住); 只改写侧 →
   存量脏数据仍会串。

`MerchantBillingViewServiceImpl.java`:
- import 区补 `import com.lumen.finance.dto.portal.MerchantDtos.DisputeRequest;` 和 `import com.lumen.finance.dto.portal.MerchantDtos.DisputeResult;`

```java
    // ------------------------------------------------------------------ 异议

    /**
     * {@inheritDoc}
     *
     * <p>执行顺序是刻意的: <b>先 submit 成功, 再写 recon 三列</b>。反过来做的话,
     * submit 失败 (调账单已不在 DRAFT) 会留下一条"已异议"的标记而审批没启动,
     * 商家再提会被已异议分支挡死 —— 异议卡死, 只能人工改库。
     */
    @Override
    @Transactional
    public DisputeResult raiseDispute(Long tenantId, Long counterpartyId, Long userId,
                                      DisputeRequest req) {
        // reconScope 的签名是 (tenantId, counterpartyId, period) —— period 传 null = 不按期间筛。
        // scope 里已经带了 tenant + counterparty + direction=RECEIVABLE + deleted=0, 所以这一句
        // 本身就完成了"是不是我的对账单"的归属判定, 不需要再补 eq。
        BillingReconciliation r = reconMapper.selectOne(
                reconScope(tenantId, counterpartyId, null).eq(BillingReconciliation::getId, req.reconId()));
        if (r == null) {
            throw new FinanceException(FinanceErrorCode.RECONCILIATION_NOT_FOUND,
                    "Reconciliation " + req.reconId() + " not found for counterparty " + counterpartyId);
        }
        if (r.getDisputeAt() != null) {
            throw new FinanceException(FinanceErrorCode.RECON_NOT_DISPUTABLE,
                    "Reconciliation " + r.getId() + " already disputed at " + r.getDisputeAt());
        }
        if (isPeriodClosed(tenantId, r.getPeriod())) {
            throw new FinanceException(FinanceErrorCode.RECON_NOT_DISPUTABLE,
                    "Period " + r.getPeriod() + " is already CLOSED, dispute window closed");
        }
        if (r.getAdjustmentId() == null) {
            throw new FinanceException(FinanceErrorCode.RECON_NOT_DISPUTABLE,
                    "Reconciliation " + r.getId() + " has no linked adjustment to push into approval");
        }
        // reason 为空的兜底: 门户 controller 会先校验 (DISPUTE_REASON_REQUIRED), 但 service
        // 不能依赖调用方 —— 少了这一句, reason=null 时 MP 的 updateById 会**跳过** null 字段
        // (默认 FieldStrategy.NOT_NULL), 于是 disputeAt 写进去了、dispute_reason 没写进去:
        // 对账单变成"已异议但没有理由", 而商家再提会被上面的"已提过"分支挡死 —— 异议彻底卡住,
        // 且没有任何人知道为什么。用 BAD_REQUEST 兜住, Task 4 的翻译表会把它映成
        // PORTAL_PARAM_INVALID (400), 与 controller 的专属提示不冲突。
        if (req.reason() == null || req.reason().isBlank()) {
            throw new FinanceException(FinanceErrorCode.BAD_REQUEST,
                    "Dispute reason must not be blank for reconciliation " + r.getId());
        }

        // 推进审批。submit 内部已校验 status=DRAFT + 状态机 DRAFT->PENDING_L1,
        // 这里把它翻译成"当前不可异议"这一个对外码, 不把内部状态机细节漏给商家。
        BillingAdjustment adj;
        try {
            adj = adjustmentService.submit(tenantId, r.getAdjustmentId(), userId);
        } catch (FinanceException e) {
            if (FinanceErrorCode.INVALID_STATE_TRANSITION.equals(e.getErrorCode())) {
                throw new FinanceException(FinanceErrorCode.RECON_NOT_DISPUTABLE,
                        "Linked adjustment " + r.getAdjustmentId() + " is no longer in DRAFT: " + e.getMessage());
            }
            throw e;
        }

        LocalDateTime now = LocalDateTime.now();
        r.setDisputeAmount(req.claimedAmount());
        r.setDisputeReason(req.reason());
        r.setDisputeAt(now);
        reconMapper.updateById(r);
        log.info("raiseDispute: tenant={} counterparty={} reconId={} adjustmentId={} user={} claimed={}",
                tenantId, counterpartyId, r.getId(), adj.getId(), userId, req.claimedAmount());

        return new DisputeResult(r.getId(), adj.getId(), adj.getStatus(), now);
    }
```

```java
    @Override

                str(row, 2, v.businessType());

                money(row, 5, v.taxAmount());
                money(row, 6, v.netAmount());
                money(row, 7, v.fxRateAtCreation());

                str(row, 9, v.createdAt() == null ? null : v.createdAt().toString());

            return writeOut(wb);
        } catch (IOException e) {
            throw new FinanceException(FinanceErrorCode.REPORT_GENERATION_FAILED,
                    "Failed to export invoices: " + e.getMessage());

    @Override
    public byte[] exportReconciliations(Long tenantId, Long counterpartyId, String period) {
        // 同 exportInvoices: 先校验, 让格式非法的期间变成 400 而不是 500。
        validatePeriod(period);
        // 同 exportInvoices: 用返回值, 不用传进去的局部 Page。
        Page<BillingReconciliation> mp = reconMapper.selectPage(
                Page.of(1, EXPORT_MAX_ROWS), reconScope(tenantId, counterpartyId, period));
        Set<String> closed = closedPeriods(tenantId, mp.getRecords().stream()
                .map(BillingReconciliation::getPeriod).collect(Collectors.toSet()));
        List<MerchantDtos.ReconView> rows = mp.getRecords().stream()
                .map(x -> toReconView(x, closed.contains(x.getPeriod()))).toList();

        try (SXSSFWorkbook wb = new SXSSFWorkbook(EXPORT_WINDOW)) {
            Sheet sheet = wb.createSheet("对账单");
            CellStyle head = headerStyle(wb);
            String[] cols = {"期间", "币种", "应收", "实收", "差异", "状态", "期间是否闭期",
                    "异议时间", "异议金额", "异议理由", "关联调账单ID"};
            writeHeader(sheet, cols, head);

            int r = 1;
            for (MerchantDtos.ReconView v : rows) {
                Row row = sheet.createRow(r++);
                str(row, 0, v.period());
                str(row, 1, v.currency());
                money(row, 2, v.expectedAmount());
                money(row, 3, v.actualAmount());
                money(row, 4, v.varianceAmount());
                str(row, 5, v.reconciliationStatus());
                str(row, 6, v.closed() ? "已闭期" : "开放");
                str(row, 7, v.disputeAt() == null ? null : v.disputeAt().toString());
                money(row, 8, v.disputeAmount());
                str(row, 9, v.disputeReason());
                str(row, 10, v.adjustmentId() == null ? null : String.valueOf(v.adjustmentId()));
            }
            return writeOut(wb);
        } catch (IOException e) {
            throw new FinanceException(FinanceErrorCode.REPORT_GENERATION_FAILED,
                    "Failed to export reconciliations: " + e.getMessage());
        }
    }

    private static CellStyle headerStyle(SXSSFWorkbook wb) {
        CellStyle style = wb.createCellStyle();
        Font bold = wb.createFont();
        bold.setBold(true);
        style.setFont(bold);
        return style;
    }

    private static void writeHeader(Sheet sheet, String[] cols, CellStyle style) {
        Row head = sheet.createRow(0);
        for (int i = 0; i < cols.length; i++) {
            head.createCell(i).setCellValue(cols[i]);
            head.getCell(i).setCellStyle(style);
        }
    }

    private static void str(Row row, int col, String value) {
        row.createCell(col).setCellValue(value == null ? "" : value);
    }

    private static void money(Row row, int col, BigDecimal value) {
        // null 写成空串而不是 0: 商家分不清 "0 元" 和 "没有这个数"
        row.createCell(col).setCellValue(value == null ? "" : value.toPlainString());
    }

    private static byte[] writeOut(SXSSFWorkbook wb) throws IOException {
        try (ByteArrayOutputStream out = new ByteArrayOutputStream()) {
            wb.write(out);
            return out.toByteArray();
        }
    }
```

```java
package com.lumen.customer.web;

import org.springframework.http.ContentDisposition;
import org.springframework.http.HttpHeaders;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;

import java.nio.charset.StandardCharsets;

/**
 * 门户文件下载响应 (Iteration 4.5C-2).
 *
 * <p>唯一职责: 把 byte[] 包成带正确下载头的 {@code ResponseEntity}。
 * 2 个导出端点共用, 免得两处各自拼一遍 Content-Disposition 而其中一个忘了
 * UTF-8 转义 —— 那会让中文文件名在浏览器里变成乱码。
 */
public final class PortalDownloads {

    private static final MediaType XLSX =
            MediaType.parseMediaType("application/vnd.openxmlformats-officedocument.spreadsheetml.sheet");

    private PortalDownloads() {
    }

    /**
     * @param filename 建议的文件名, 可含中文
     * @param body     POI 生成的 xlsx 字节
     */
    public static ResponseEntity<byte[]> xlsx(String filename, byte[] body) {
        HttpHeaders h = new HttpHeaders();
        // RFC 5987: filename* 存 UTF-8 百分号编码; filename 保留 ASCII 兜底给老客户端
        h.setContentDisposition(ContentDisposition.attachment()
                .filename(filename, StandardCharsets.UTF_8)
                .build());
        h.setContentType(XLSX);
        h.setContentLength(body.length);
        return new ResponseEntity<>(body, h, org.springframework.http.HttpStatus.OK);
    }
}
```

```java
     * Finance 码 → 门户码的显式翻译表 (4.5C-2).
     *
     * <p><b>为什么需要这张表。</b> {@link FinanceException} 继承 {@code BizException},
     * 所以 {@code GlobalExceptionHandler.handleBiz} 本来就会照它自己的 httpStatus
     * 返回 —— 也就是说这<b>不是</b>把 500 救回 4xx 的问题, 而是 code 与 http 的语义对齐问题。
     * 但仍必须显式翻译, 理由有两条:
     *
     * <ul>
     *   <li><b>ADJUSTMENT_NOT_FOUND 的 httpStatus 是 400, 不是 404</b> (V29 定的, 改不动:
     *       已有数据与既有调用方都依赖它)。商家视角下"调账单不是我的"必须是 404 ——
     *       返回 400 等于告诉他"东西存在, 只是你不能动", 泄露存在性。</li>
     *   <li>门户前端按 {@code 404_00x} 族做统一空态渲染, finance 的 {@code 404_006} /
     *       {@code 404_007} 门户根本不认识, 会掉进兜底分支显示原始错误串。</li>
     * </ul>
     *
     * <p>表里没有的 finance 码一律降级成 {@link PortalErrorCode#EXPORT_FAILED} 语义
     * 的 HTTP 500 —— 走到这里说明 finance 抛了个门户没预料的码, 属于服务端 bug,
     * 不该伪装成业务错误码。
     *
     * <p><b>{@code BAD_REQUEST} 必须在这张表里</b>。finance 侧对 {@code period}
     * 格式非法抛的是 {@code FinanceErrorCode.BAD_REQUEST} (400_022 / HTTP 400) ——
     * 商家传 {@code ?period=2026-13} 属于入参错误, 该回 400。表里没有它的话,
     * 那把 400 会被降级规则翻成 HTTP 500, 等于把"你参数写错了"报成"服务器内部错误"。
     */
    private static final Map<FinanceErrorCode, PortalErrorCode> FINANCE_TO_PORTAL = Map.of(
            FinanceErrorCode.INVOICE_NOT_FOUND,         PortalErrorCode.INVOICE_NOT_FOUND,
            FinanceErrorCode.RECONCILIATION_NOT_FOUND,  PortalErrorCode.RECON_NOT_FOUND,
            FinanceErrorCode.PAYMENT_RECORD_NOT_FOUND,  PortalErrorCode.PAYMENT_NOT_FOUND,
            FinanceErrorCode.ADJUSTMENT_NOT_FOUND,       PortalErrorCode.ADJUSTMENT_NOT_FOUND,
            FinanceErrorCode.RECON_NOT_DISPUTABLE,      PortalErrorCode.RECON_NOT_DISPUTABLE,
            FinanceErrorCode.BAD_REQUEST,               PortalErrorCode.PORTAL_PARAM_INVALID,
            FinanceErrorCode.REPORT_GENERATION_FAILED,  PortalErrorCode.EXPORT_FAILED);

    /**
     * 4.5C-2 — 把 finance 域的 {@link FinanceException} 翻成门户码。
     *
     * <p>{@code @RestControllerAdvice(basePackageClasses = CustomerModuleMarker.class)}
     * + {@code @Order(HIGHEST_PRECEDENCE)} 让本 advice 抢在
     * {@code GlobalExceptionHandler} 前面拿到 portal 包里的异常, 所以这个分支一定会命中。
     */
    @ExceptionHandler(FinanceException.class)
    public ResponseEntity<R<Void>> handleFinance(FinanceException ex) {
        PortalErrorCode mapped = FINANCE_TO_PORTAL.get(ex.getErrorCode());
        int code = mapped != null ? mapped.getCode() : PortalErrorCode.EXPORT_FAILED.getCode();
        int http = mapped != null ? mapped.getHttpStatus() : 500;
        return ResponseEntity.status(http).body(R.fail(code, ex.getMessage()));
```

```java
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.core.annotation.AnnotatedElementUtils;

import org.springframework.web.bind.annotation.RequestMapping;

/**
 * 4.5C-2 — 10 个账单端点的 {@code @PreAuthorize} 契约。
 *
 * <p>本仓<b>没有</b> spring-security-test, controller 测试也没有先例用 MockMvc,
 * 所以这里用反射锁注解字面量。这不是"退而求其次": 权限注解写错 (抄错码、漏写)
 * 在编译期和运行期都不报错, 只在真有人拿错 token 打进来时才炸, 而且炸的是 403
 * 而不是测试。用反射在 CI 里就把它炸出来。

@DisplayName("PortalBilling controllers — 权限注解契约")
class PortalBillingControllerSecurityTest {

    private static String authz(Class<?> type, String method, Class<?>... params) throws Exception {
        Method m = AnnotatedElementUtils.findMergedAnnotation(type.getDeclaredMethod(method, params), PreAuthorize.class);
        assertThat(m).as("%s#%s 必须有 @PreAuthorize", type.getSimpleName(), method).isNotNull();
        return m.value();
    }

    private static String routeOf(Class<?> type) {
        RequestMapping rm = AnnotatedElementUtils.findMergedAnnotation(type, RequestMapping.class);
        assertThat(rm).as("%s 必须有 @RequestMapping", type.getSimpleName()).isNotNull();
        assertThat(rm.value()).hasSize(1);
        return rm.value()[0];
    }

    @Test
    @DisplayName("4 个 controller 的路由前缀都是 /api/customer/*")
    void routePrefixes() {
        assertThat(routeOf(PortalReconController.class)).isEqualTo("/api/customer/recon");
        assertThat(routeOf(PortalInvoiceController.class)).isEqualTo("/api/customer/invoice");
        assertThat(routeOf(PortalPaymentController.class)).isEqualTo("/api/customer/payment");
        assertThat(routeOf(PortalAdjustmentController.class)).isEqualTo("/api/customer/adjustment");
    }

    @Test
    @DisplayName("GET / 端点")

        // 反射签名 = 控制器方法的**参数表**, 与实现必须逐个对上。
        // 注意 tenantId/counterpartyId 走的是 PortalIdentity 的静态方法,
        // 在方法体内取值, **不是**参数 —— 所以这里没有那两个 Long。
        assertThat(authz(PortalReconController.class, "list", String.class))
                .isEqualTo("hasAuthority('customer:recon:view')");

        assertThat(authz(PortalPaymentController.class, "list", String.class))
                .isEqualTo("hasAuthority('customer:payment:view')");
        assertThat(authz(PortalAdjustmentController.class, "list", Long.class, Long.class))
                .isEqualTo("hasAuthority('customer:adjustment:view')");

    @DisplayName("GET /{id} 端点")

        assertThat(countHandlers(PortalAdjustmentController.class)).isEqualTo(2);

    private static int countHandlers(Class<?> type) {
        int n = 0;
        for (Method m : type.getDeclaredMethods()) {
            if (AnnotatedElementUtils.hasAnnotation(m, org.springframework.web.bind.annotation.RequestMapping.class)) {
                n++;
            }
        }
        return n;
    }
```

```java
package com.lumen.customer.controller;

import com.lumen.common.api.R;
import com.lumen.customer.error.PortalErrorCode;
import com.lumen.customer.exception.CustomerException;
import com.lumen.customer.web.PortalDownloads;

import com.lumen.finance.dto.portal.MerchantPage;
import com.lumen.finance.service.MerchantBillingViewService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.ResponseEntity;
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

import java.math.BigDecimal;

/**
 * 客户门户对账 controller (Iteration 4.5C-2).
 *
 * <p>4 个端点 (路由前缀 {@code /api/customer/recon}):
 * <ol>
 *   <li>GET  {@code /}          — {@code customer:recon:view}       — 列表</li>
 *   <li>GET  {@code /{id}}      — {@code customer:recon:view}       — 详情</li>
 *   <li>GET  {@code /export}    — {@code customer:recon:view}       — xlsx 导出</li>
 *   <li>POST {@code /dispute}   — {@code customer:adjustment:create} — 提异议</li>
 * </ol>
 *
 * <p><b>{@code /dispute} 不带路径参数, {@code reconId} 走 body。</b> 一次提异议只针对
 * 一张对账单, 走 body 与其余写操作的形状一致 (4.5B.2 的
 * {@code POST /api/customer/order/{doId}/cancel} 带路径参数是因为"取消哪一单"是路径
 * 语义的一部分, 而异议更像一次针对账单的声明)。
 *
 * <p><b>/export 与 /{id} 的优先级</b>: Spring MVC 的模式比较器把字面量段排在模板段
 * 之上, 所以 {@code /export} 不会被 {@code /{id}} 抢走 —— 这与声明顺序无关, 调换
 * 声明位置也不影响。但如果哪天 {@code {id}} 的类型从 {@code Long} 放宽成
 * {@code String}, 这个保证会消失, 导出端点会静默变成"查 id 为 export 的对账单"。
 *
 * <p>tenantId / counterpartyId / userId 一律走 {@link PortalIdentity} 从 JWT 取,
 * <b>不接受任何来自请求体的 counterpartyId</b>。body 里的 {@code reconId} 是"对哪张
 * 单提异议", 与"我是哪个商家"是两件事, 后者永远来自 JWT。
 *
 * <p><b>{@code period} 的格式校验刻意放在 service 层, 不在这里加
 * {@code @Pattern}</b>。本仓的 {@code GlobalExceptionHandler} 处理的是
 * {@code MethodArgumentNotValidException} (即 {@code @Valid @RequestBody} 的 DTO 校验),
 * <b>没有 {@code ConstraintViolationException} 的分支</b> —— 而类级 {@code @Validated}
 * + 方法参数 {@code @Pattern} 抛的正是后者, 会落 catch-all 变成 HTTP 500。
 * 商家传 {@code ?period=2026-13} 该回 400, 不是"服务器内部错误"。
 * service 层抛 {@code FinanceErrorCode.BAD_REQUEST} (400_022) 由 Task 4 的翻译表
 * 翻成门户 400, 这条链路是通的。
 */
@Slf4j
@RestController
@RequestMapping("/api/customer/recon")
@RequiredArgsConstructor
public class PortalReconController {

    private final MerchantBillingViewService billingView;

    /**
     * {@code dispute_amount} 是 {@code DECIMAL(18,4)} — 14 位整数 + 4 位小数。
     * 超了不是"显示精度不够", 是 MySQL 直接报 Data truncation 让整个请求 500,
     * 所以在入口挡掉。
     */
    private static final BigDecimal MAX_CLAIM = new BigDecimal("99999999999999.9999");

    // GET / — 列表
    @GetMapping
    @PreAuthorize("hasAuthority('customer:recon:view')")
    public R<MerchantPage<ReconView>> list(@RequestParam(required = false) String period) {
        return R.ok(billingView.listReconciliations(
                PortalIdentity.requireTenantId(),
                PortalIdentity.requireCounterpartyId(),
                period, 1, 20));
    }

    // GET /{id} — 详情
    @GetMapping("/{id}")
    @PreAuthorize("hasAuthority('customer:recon:view')")
    public R<ReconView> detail(@PathVariable Long id) {
        return R.ok(billingView.getReconciliation(
                PortalIdentity.requireTenantId(), PortalIdentity.requireCounterpartyId(), id));
    }

    // GET /export — 导出
    @GetMapping("/export")
    @PreAuthorize("hasAuthority('customer:recon:view')")
    public ResponseEntity<byte[]> export(
            @RequestParam(required = false) String period) {
        byte[] body = billingView.exportReconciliations(
                PortalIdentity.requireTenantId(), PortalIdentity.requireCounterpartyId(), period);
        return PortalDownloads.xlsx("对账单.xlsx", body);
    }

    /**
     * {@code POST /dispute} — 对某张对账单的差异提异议。
     *
     * <p>形状校验在这里 (reason 非空 / amount 在 DECIMAL(18,4) 范围内),
     * 业务校验在 finance 侧 (已异议过 / 已闭期 / 无关联调账单)。
     *
     * @throws CustomerException 400_003 理由为空 / 400_004 金额超范围 / 404_002 不属于该商家
     */
    @PostMapping("/dispute")
    @PreAuthorize("hasAuthority('customer:adjustment:create')")
    public R<DisputeResult> dispute(@RequestBody DisputeRequest body) {
        Long tenantId = PortalIdentity.requireTenantId();
        Long counterpartyId = PortalIdentity.requireCounterpartyId();
        Long userId = PortalIdentity.requireUserId();

        if (body == null || body.reconId() == null) {
            throw new CustomerException(PortalErrorCode.RECON_NOT_FOUND.getCode(),
                    PortalErrorCode.RECON_NOT_FOUND.getMessage());
        }
        if (body.reason() == null || body.reason().isBlank()) {
            throw new CustomerException(PortalErrorCode.DISPUTE_REASON_REQUIRED.getCode(),
                    PortalErrorCode.DISPUTE_REASON_REQUIRED.getMessage());
        }
        BigDecimal claimed = body.claimedAmount();
        if (claimed != null && (claimed.abs().compareTo(MAX_CLAIM) > 0
                || Math.max(claimed.scale(), 0) > 4)) {
            throw new CustomerException(PortalErrorCode.DISPUTE_AMOUNT_INVALID.getCode(),
                    PortalErrorCode.DISPUTE_AMOUNT_INVALID.getMessage());
        }

        return R.ok(billingView.raiseDispute(tenantId, counterpartyId, userId,
                new DisputeRequest(body.reconId(), claimed, body.reason().trim())));
    }
}
```

```java
package com.lumen.integration;

import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;

import java.math.BigDecimal;
import java.time.LocalDate;
import java.util.concurrent.atomic.AtomicLong;

/**
 * 4.5C-2 — 商家门户账单 IT 的数据 fixture.
 *
 * <p>继承 {@link PortalOrderFixtureBase} 拿到 alice→customer42 / carol→customer99
 * 两套 portal 身份, 本类只负责往 billing 五张表里种数据。
 *
 * <p><b>为什么手写 SQL 而不是调 finance 的 service。</b> 服务会连带跑应计、开票、
 * 过账、状态机一整套, IT 就从"验证商家能看到什么"变成"验证整个计费引擎" ——
 * 跑得慢、失败时定位困难, 而且月结快照会被别处的定时任务污染。直接 INSERT 只写
 * 商家视图关心的那几列, 无关列全部塞 0/占位值。
 *
 * <p><b>id 段</b>: 970_001 起, 与 {@link PortalOrderFixtureBase} 的 960_001 段
 * 完全错开, 两组 IT 各自 {@code @BeforeEach} 重建、互不干扰。
 *
 * <p><b>调账单按 {@code ADJ-45C2-} 前缀清理</b> 而不是按 counterparty ——
 * {@code t_billing_adjustment} 既没有 {@code counterparty_id} 也没有 {@code period},
 * 只能靠单号前缀认领。它有 {@code uk_adj_no (tenant_id, adjustment_no)} 唯一键,
 * 所以 {@code @BeforeEach} 也做一次同样的前置删除: 上一次跑崩了留下的行不会让
 * 这次的 INSERT 撞唯一键。
 */
abstract class PortalMerchantBillingFixture extends PortalOrderFixtureBase {

    private static final AtomicLong BILLING_ID = new AtomicLong(970_001L);

    /** 调账单号前缀 —— 本 fixture 的专属认领标记, 清理靠它。 */
    protected static final String ADJ_NO_PREFIX = "ADJ-45C2-";

    /** 开放期 (可提异议) */
    protected static final String PERIOD_OPEN = "2026-08";
    /** 已闭期 (不可提异议) */
    protected static final String PERIOD_CLOSED = "2026-07";
    /**
     * "无关联调账单"那条专用的独立期间。
     *
     * <p>必须与 {@link #PERIOD_OPEN} 分开: {@code uk_recon_tenant_period_cpty} 的列是
     * (tenant_id, period, direction, counterparty_id, currency, deleted), 同商家同期间
     * 只能有一条 {@code deleted=0} 的行。共用 2026-08 的话, "无调账单"和"主路径"
     * 两条 recon 会直接撞唯一键。
     */
    protected static final String PERIOD_NOA = "2026-06";

    protected long adjDraftId;
    /** 开放期 + 挂了 DRAFT 调账单 —— 异议主路径 */
    protected long reconOpenId;
    /** 闭期 —— 闭期不可异议 */
    protected long reconClosedId;
    /** 开放期 + 零差异 + 无关联调账单 —— 专测"没单可推", 与闭期那条分开, 否则两条分支都是 409_002 */
    protected long reconNoAdjId;

    @BeforeEach
    void seedBillingFixture() {
        long tenant = 1L;
        // 上一次跑崩的残留 — uk_adj_no 会让 INSERT 直接失败
        jdbc.update("DELETE FROM t_billing_adjustment WHERE tenant_id = 1 AND adjustment_no LIKE ?", ADJ_NO_PREFIX + "%");

        // ---- 发票: alice 2 张 (闭期/开放各一) + carol 1 张 ----
        seedInvoice(tenant, customer42Id, "INV-45C2-A1", 2026, 7, "113.00", "13.00", "100.00", "PUSHED");
        seedInvoice(tenant, customer42Id, "INV-45C2-A2", 2026, 8, "226.00", "26.00", "200.00", "PUSHED");
        seedInvoice(tenant, customer99Id, "INV-45C2-C1", 2026, 8, "339.00", "39.00", "300.00", "PUSHED");

        // ---- 调账单: 一张 DRAFT (挂到开放期 recon 上, 供异议推进) ----
        adjDraftId = BILLING_ID.incrementAndGet();
        jdbc.update(
            "INSERT INTO t_billing_adjustment (id, tenant_id, adjustment_no, source_invoice_id, adjustment_type, "
                + "amount, currency, fx_rate_at_creation, tax_rate, gross_amount, tax_amount, net_amount, "
                + "reason, status, created_at, updated_at) "
                + "VALUES (?, ?, ?, 0, 'DEBIT', ?, 'CNY', 1.00000000, 0.1300, ?, ?, ?, ?, 'DRAFT', NOW(3), NOW(3))",
            adjDraftId, tenant, ADJ_NO_PREFIX + "0001",
            new BigDecimal("11.30"), new BigDecimal("11.30"), new BigDecimal("1.30"), new BigDecimal("10.00"),
            "月结差异自动调账");

        // ---- 对账 ----
        reconClosedId = seedRecon(tenant, customer42Id, PERIOD_CLOSED, "100.00", "100.00", "0.00", "ADJUSTMENT_CREATED");
        reconOpenId = seedRecon(tenant, customer42Id, PERIOD_OPEN, "100.00", "90.00", "-10.00", "ADJUSTMENT_CREATED");
        jdbc.update("UPDATE t_reconciliation SET adjustment_id = ? WHERE id = ?", adjDraftId, reconOpenId);

        reconNoAdjId = seedRecon(tenant, customer42Id, PERIOD_NOA, "60.00", "60.00", "0.00", "MATCHED");

        long reconSoftDeleted = seedRecon(tenant, customer42Id, PERIOD_OPEN, "50.00", "50.00", "0.00", "MATCHED");
        jdbc.update("UPDATE t_reconciliation SET deleted = 1 WHERE id = ?", reconSoftDeleted);

        seedRecon(tenant, customer99Id, PERIOD_OPEN, "300.00", "280.00", "-20.00", "ADJUSTMENT_CREATED");

        // ---- 付款: alice 2 条 (含 1 条软删) + carol 1 条 ----

        long paySoftDeleted = seedPayment(tenant, customer42Id, PERIOD_OPEN, "77.00", LocalDate.of(2026, 8, 29));
        jdbc.update("UPDATE t_payment_record SET deleted = 1 WHERE id = ?", paySoftDeleted);
        seedPayment(tenant, customer99Id, PERIOD_OPEN, "300.00", LocalDate.of(2026, 8, 30));

        // ---- 月结: 2026-07 已 CLOSED, 2026-06 / 2026-08 开放 ----
        jdbc.update("INSERT INTO t_monthly_closing (tenant_id, period, status, created_at, updated_at, deleted) "
                + "VALUES (?, ?, 'CLOSED', NOW(3), NOW(3), 0)", tenant, PERIOD_CLOSED);
        jdbc.update("INSERT INTO t_monthly_closing (tenant_id, period, status, created_at, updated_at, deleted) "
                + "VALUES (?, ?, 'OPEN', NOW(3), NOW(3), 0)", tenant, PERIOD_NOA);
        jdbc.update("INSERT INTO t_monthly_closing (tenant_id, period, status, created_at, updated_at, deleted) "
                + "VALUES (?, ?, 'OPEN', NOW(3), NOW(3), 0)", tenant, PERIOD_OPEN);
    }

    @AfterEach
    void cleanBillingFixture() {
        jdbc.update("DELETE FROM t_billing_adjustment WHERE tenant_id = 1 AND adjustment_no LIKE ?", ADJ_NO_PREFIX + "%");
        // recon / payment / invoice 三张表都带 counterparty_id, 按商家扫最不容易漏
        for (long cid : new long[]{customer42Id, customer99Id}) {
            jdbc.update("DELETE FROM t_reconciliation WHERE tenant_id = 1 AND counterparty_id = ?", cid);
            jdbc.update("DELETE FROM t_payment_record WHERE tenant_id = 1 AND counterparty_id = ?", cid);
            jdbc.update("DELETE FROM t_billing_invoice WHERE tenant_id = 1 AND counterparty_id = ?", cid);
        }
        jdbc.update("DELETE FROM t_monthly_closing WHERE tenant_id = 1 AND period IN (?, ?, ?)",
                PERIOD_CLOSED, PERIOD_NOA, PERIOD_OPEN);
    }

    private long nextBillingId() {
        return BILLING_ID.incrementAndGet();
    }

    private void seedInvoice(long tenantId, long counterpartyId, String no, int year, int month,
                             String gross, String tax, String net, String status) {
        jdbc.update(
            "INSERT INTO t_billing_invoice (id, invoice_no, tenant_id, direction, counterparty_id, counterparty_type, "
                + "business_type, period_year, period_month, gross_amount, tax_amount, net_amount, currency, status, "
                + "rule_id, rule_version, deleted, version, created_at, updated_at) "
                + "VALUES (?, ?, ?, 'RECEIVABLE', ?, 'CUSTOMER', 'LAST_MILE', ?, ?, ?, ?, ?, 'CNY', ?, 1, 1, 0, 0, NOW(3), NOW(3))",
            nextBillingId(), no, tenantId, counterpartyId, year, month,
            new BigDecimal(gross), new BigDecimal(tax), new BigDecimal(net), status);
    }

    private long seedRecon(long tenantId, long counterpartyId, String period,
                           String expected, String actual, String variance, String status) {
        long id = nextBillingId();
        jdbc.update(
            "INSERT INTO t_reconciliation (id, tenant_id, period, direction, counterparty_id, counterparty_type, "
                + "currency, expected_amount, actual_amount, variance_amount, reconciliation_status, "
                + "created_at, updated_at, deleted) "
                + "VALUES (?, ?, ?, 'RECEIVABLE', ?, 'CUSTOMER', 'CNY', ?, ?, ?, ?, NOW(3), NOW(3), 0)",
            id, tenantId, period, counterpartyId,
            new BigDecimal(expected), new BigDecimal(actual), new BigDecimal(variance), status);
        return id;
    }

    private long seedPayment(long tenantId, long counterpartyId, String period,
                             String amount, LocalDate paymentDate) {
        long id = nextBillingId();
        jdbc.update(
            "INSERT INTO t_payment_record (id, tenant_id, period, direction, counterparty_id, counterparty_type, "
                + "currency, amount, source_ref, payment_date, source, created_at, created_by, deleted) "
                + "VALUES (?, ?, ?, 'RECEIVABLE', ?, 'CUSTOMER', 'CNY', ?, ?, ?, 'BANK_TRANSFER', NOW(3), 1, 0)",
            id, tenantId, period, counterpartyId,
            new BigDecimal(amount), "REF-" + id, paymentDate);
        return id;
    }
}
```

```ts
/** 触发浏览器下载。后缀留给调用方, 避免这里硬编码成 xlsx —— 将来加 CSV 时不用改。 */
function saveBlob(data: Blob, filename: string): void {
  const url = URL.createObjectURL(data);
  const a = document.createElement('a');
  a.href = url;
  a.download = filename;
  document.body.appendChild(a);
  a.click();
  document.body.removeChild(a);
  URL.revokeObjectURL(url);
}
```

```tsx
      .reconDetail(reconId)
      .then((r) => {
        if (alive) setRecon(r);
      })
      .finally(() => {
        if (alive) setLoading(false);
      });
    return () => {
      alive = false;
    };
  }, [reconId]);

  const disputed = Boolean(recon?.disputeAt);
  const canDispute = Boolean(recon) && !recon!.closed && !disputed;

  const onSubmit = async (values: { reason: string; claimedAmount?: number | null }) => {
    setSubmitting(true);
    try {
      const out = await portalBillingService.raiseDispute(reconId, {
        reason: values.reason,
        claimedAmount: values.claimedAmount ?? null,
      });
      message.success(zhCN.billing.disputeSubmitted(out.adjustmentStatus ?? ''));
      navigate('/reconciliation');
    } catch {
      message.error(zhCN.billing.disputeFailed);
    } finally {
      setSubmitting(false);
    }
  };

  if (loading) return <Spin />;
  if (!recon) return <Alert type="error" message={zhCN.billing.reconNotFound} />;

  return (
    <Space direction="vertical" style={{ width: '100%' }} size="middle">
      <Card title={`${zhCN.billing.reconTitle} — ${recon.period ?? '-'}`}>
        <Descriptions column={2} bordered size="small">
          <Descriptions.Item label={zhCN.billing.expected}>
            {recon.expectedAmount ?? '-'} {recon.currency}
          </Descriptions.Item>
          <Descriptions.Item label={zhCN.billing.actual}>
            {recon.actualAmount ?? '-'} {recon.currency}
          </Descriptions.Item>
          <Descriptions.Item label={zhCN.billing.variance}>
            {recon.varianceAmount ?? '-'} {recon.currency}
          </Descriptions.Item>
          <Descriptions.Item label={zhCN.billing.periodClosed}>
            {recon.closed ? zhCN.billing.closed : zhCN.billing.open}
          </Descriptions.Item>
        </Descriptions>
      </Card>

      {recon.closed && (
        <Alert type="info" showIcon message={zhCN.billing.closedNoDispute} />
      )}
      {disputed && (
        <Alert
          type="warning"
          showIcon
          message={zhCN.billing.alreadyDisputed}
          description={recon.disputeReason ?? undefined}
        />
      )}

      {canDispute && (
        <Card title={zhCN.billing.raiseDispute}>
          <Form form={form} layout="vertical" onFinish={onSubmit}>
            <Form.Item
              name="reason"
              label={zhCN.billing.disputeReason}
```

```markdown
## 15.16 4.5C-2 商家门户对账/发票/付款 + 对账异议

商家在门户自助查看自己的月结对账单、发票、付款记录、调账单, 对不认可的差异提异议,
异议直接推进已存在的自动调账单进 L1 审批 —— 取代「财务导出 Excel 发邮件 → 商家核对
→ 再发邮件反馈 → 手工建调账单」这条链路。

### 迁移

| 版本 | 内容 |
|---|---|
| V39 | `t_reconciliation` 加 `dispute_amount` / `dispute_reason` / `dispute_at` 三列 (均 NULL) |
| V40 | seed 3 个权限码 (`customer:payment:view` / `customer:adjustment:view` / `customer:adjustment:create`, id 169-171) + 绑 customer 角色 (id 14) |

> ⚠️ V40 **只新增 3 个**。`customer:invoice:view` (162) / `customer:recon:view` (163)
> V33 就已 seed, 重插会撞 `uk_perm_tenant_code (tenant_id, code)` ——
> `ON DUPLICATE KEY UPDATE` 会就地更新已存在那行, 新 id 永不生成。V37 正是为此擦屁股。

### 后端

- `MerchantBillingViewService` (lumen-finance): 10 个方法的商家视角窄接口。
  商家过滤 (`counterparty_id` + `direction=RECEIVABLE`) / 字段裁剪 / 状态判定全在
  finance 侧, 三个 mapper 一行没改。
- 4 个 controller 共 10 个端点 (lumen-customer), 路由前缀 `/api/customer/*`。
- `CustomerExceptionHandler` 加 `FinanceException` 分支, 5 个 finance 码翻成门户码。

### 已知缺口

1. **`BillingReconciliation` / `BillingPaymentRecord` 实体没有 `deleted` 字段**, 而 DDL 有,
   且全仓未配 MyBatis-Plus 全局逻辑删除 —— 所以商家视图必须显式 `.apply("deleted = 0")`。
   `BillingInvoice` / `BillingAdjustment` 有 `@TableLogic`, 反而不能手写。
2. **既有 `ReconciliationServiceImpl.list` / `PaymentRecordServiceImpl.list` 收了
   `tenantId` 但没放进 `LambdaQueryWrapper`**, 商家视图因此不复用它们, 另起窄接口。
   那两个方法的缺陷本身未修 (属财务内部读, 暂不构成越权面), 留给后续迭代。
3. **「我的调账单」只覆盖两条来源链** (recon.adjustment_id / invoice.source_invoice_id)。
   将来出现第三种建调账单的入口必须补第三跳, 否则商家看不到自己有权看到的调账单。
4. **`t_state_transition.guard_expression` 形同虚设** —— V30 给
   `billing_adjustment` 的 `DRAFT → PENDING_L1` 写了 `role:finance_ops`, 但
   `StateMachineEngine.assertTransition` 只比对跃迁是否存在, **不求值 guard**。
   所以商家能推调账单进审批不是漏洞 —— 它是设计意图 (商家提异议 = 发起审批),
   真正的边界在 controller 的 `@PreAuthorize('customer:adjustment:create')`。
5. **门户没有调账单审批端点**。调账单审批是财务的动作; 商家想改金额走对账异议。
6. **导出未做行数硬上限提示** —— finance 侧截到 10000 行, 超出部分静默丢弃,
   商家不会知道数据被截了。量级到 10000 行时需要补一个提示。
```

# 4.5C-1 门户取消订单的计费冲销 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 客户在门户取消 `PENDING_DISPATCH` 订单时，把 4.5B 下单时写下的计费应计 (accrual) 从 `OPEN` / `OPEN_FAILED` 释放为 `RELEASED`，消除「订单已取消但账上仍有应计收入」。

**Architecture:** 复用 `AccrualService.release()`（OPEN → RELEASED），新增 V38 迁移让 `OPEN_FAILED` 也能释放。在 `BillingEngineService` 加 `assertReversible`（纯读预检，写 DO 状态前调）与 `reversalForSourceEventId`（写，写 DO 状态后调）。冲销动作放进 `BillingEngineServiceImpl` 里既有的 `requiresNewTx`（REQUIRES_NEW）事务模板，与 `cancelForCustomer` 的外层事务完全隔离 —— 这样冲销失败只记 ERROR 日志，不会把整个取消 rollback 掉。

**Tech Stack:** Spring Boot 3.2.5 / MyBatis-Plus 3.5.7 / Flyway / JUnit 5 / Mockito / AssertJ / Testcontainers.

**Spec:** `docs/superpowers/specs/2026-10-21-iteration-4.5C-1-portal-cancel-billing-reversal-design.md`

## 背景：这个 bug 是什么

4.5B 的 `DeliveryOrderServiceImpl.createForCustomer` 建单成功后同步调 `BillingEngineService.estimateAndAccrue`，写一行 `t_billing_accrual`（`status=OPEN`，`source_event_id = String.valueOf(doId)`，`business_type = 'LAST_MILE'`）。

`cancelForCustomer` 完全不碰 accrual。所以订单取消了，accrual 永远停在 `OPEN`。

没有任何机制会清理它：
- `BillingReconciliationService` / `ReportService` / `BillingMonthlyClosingService` 都只读 `BillingInvoice`，不读 accrual
- 全仓 3 个 `@Scheduled`（`SlaEscalationScheduler` / `OutboxDispatcher` / `RateSyncService`）都不碰 accrual
- outbox 轮询也兜不住 —— `BusinessEventListener.onEvent` 只映射 `toState=SIGNED`，而 `PENDING_DISPATCH → CANCELLED` 永远不经 `SIGNED`

**这是一颗埋着的雷，不是已爆的雷。** 月底有人手工 finalize 那批 accrual 时，这笔根本不存在的收入会被开成 invoice。

## 三个必须知道的坑（实现前读完，少一个就做错）

### 坑 1: `release` 要改两处，不是一处

`AccrualServiceImpl.release` 的状态机断言 `from_state` 是**硬编码** `ACCRUAL_STATUS_OPEN`（L178-181）：

```java
assertSmTransition(
    FinanceConstants.SM_BILLING_ACCRUAL,
    FinanceConstants.ACCRUAL_STATUS_OPEN,   // ← 硬编码, 不是 accrual.getStatus()
    FinanceConstants.ACCRUAL_STATUS_RELEASED);
```

只放宽状态 guard 而不改这里的话，OPEN_FAILED 的行会走 `assertTransition(billing_accrual, OPEN, RELEASED)` —— 这条边 V26 就有，**永远通过**。V38 那条新边永远不会被断言到，Task 5 的 IT 即使删掉 V38 也会绿。

必须改成 `accrual.getStatus()`。

### 坑 2: `cancelForCustomer` 的 `@Transactional` 不能动

`DefaultEventBus.publish` 标的是 `@Transactional(propagation = Propagation.MANDATORY)`（`DefaultEventBus.java:17`）—— 没有外层事务直接抛 `IllegalTransactionStateException`。

所以「去掉 `@Transactional` 让 `updateById` 走 auto-commit」这条路是**堵死的**，那会拆掉 DO 状态与 outbox 行之间的事务原子性。

### 坑 3: 内层 REQUIRES_NEW 失败会污染外层事务

`release` 是 `@Transactional` REQUIRED。若直接在外层事务里调它，它抛异常时 Spring 的 `globalRollbackOnParticipationFailure` 会把外层标 **rollback-only**；dispatch 侧 catch 掉继续走，commit 时抛 `UnexpectedRollbackException` → **整单取消 500**。这与「冲销失败不阻塞取消」的设计决策正好相反。

解法是把释放放进 REQUIRES_NEW（`BillingEngineServiceImpl` 里已有现成的 `requiresNewTx` 模板）。内层事务回滚时，外层事务从未被标记，照常提交。

```sql
-- V38: billing_accrual 状态机补 OPEN_FAILED → RELEASED 边
--
-- 背景 (4.5C-1 设计阶段发现):
--   V26 (L212-220) 给 billing_accrual 种了 4 条边, 其中 OPEN_FAILED 是终点 ——

--
--   4.5C-1 要做的是: 客户在门户取消了订单, 如果这单的 accrual 当初因表达式
--   求值失败而落在 OPEN_FAILED, 取消之后这行仍然是"失败取证", 账单侧永远动不了它。
--
-- 处理:
--   补一条 OPEN_FAILED → RELEASED 边 (transition_name=releaseFailed), 让
--   AccrualServiceImpl.release 的状态机校验 (assertSmTransition, 4.5C-1 已改成
--   用 accrual.getStatus() 而非硬编码 OPEN) 在 OPEN_FAILED 状态下也能通过。
--
--   sort_order=13 接在 OPEN 的三条 (10/11/12) 之后, 与 20 组的 LOCKED 边隔开。
--   guard_expression='role:system' 沿用 V20/V22/V26 惯例 ——
--   StateMachineEngine.assertTransition 只校验边是否存在, 从不读这个字段。
--
--   不动 V26 本身 —— Flyway 已记录其 checksum, 改动会导致校验失败。
-- =============================================================

INSERT INTO t_state_transition
    (state_machine_code, from_state, to_state, transition_name, guard_expression, description, sort_order, tenant_id, created_at, updated_at, deleted, version)
VALUES
('billing_accrual', 'OPEN_FAILED', 'RELEASED', 'releaseFailed', 'role:system', '计费失败后释放', 13, 0, NOW(), NOW(), 0, 1)
ON DUPLICATE KEY UPDATE description = VALUES(description), sort_order = VALUES(sort_order);
```

`ON DUPLICATE KEY UPDATE` 沿用仓库既有惯例（V25 / V26 / V27 / V30 都是这个写法），命中 `uk_machine_from_to_tenant (state_machine_code, from_state, to_state, tenant_id)` 时幂等。

```java
    @Override
    public BillingReversalResult reversalForSourceEventId(
            Long tenantId, String sourceEventId, String reason) {
        BillingAccrual accrual = findBySourceEventId(tenantId, sourceEventId);
        if (accrual == null) {
            // createForCustomer 有多条"不写 accrual"的路径 (无规则命中 / 唯一键冲突
            // 静默 return null), 这时本就没有应计, 不算失败。
            return new BillingReversalResult("NOT_FOUND", null);
        }

        String status = accrual.getStatus();
        if (FinanceConstants.ACCRUAL_STATUS_CONVERTED.equals(status)
                || FinanceConstants.ACCRUAL_STATUS_LOCKED.equals(status)) {
            throw new FinanceException(FinanceErrorCode.ACCRUAL_ALREADY_CONVERTED,
                "应计 " + accrual.getId() + " 已是 " + status + ", 不可冲销");
        }
        if (FinanceConstants.ACCRUAL_STATUS_RELEASED.equals(status)) {
            // 幂等: 已经释放过就不再动。放在这里而不是让 release 去容错, 是为了
            // 保住 release 对 staff 路径的严格语义 (重复释放仍然报错)。
            return new BillingReversalResult("ALREADY_RELEASED", accrual.getId());
        }

        // OPEN / OPEN_FAILED → 释放。
        //
        // 为什么必须走 requiresNewTx (REQUIRES_NEW) 而不是直接调:
        // 调用方 cancelForCustomer 有自己的事务, 而 release 是 REQUIRED 会加入它。
        // release 一旦抛异常, Spring 会把外层事务标 rollback-only, 我们在 dispatch
        // 侧 catch 掉继续走的话, commit 时会抛 UnexpectedRollbackException ——
        // "冲销失败不阻塞取消" 就变成了"整单取消失败"。独立事务里失败只回滚自己。
        //
        // 用 TransactionTemplate 而非 @Transactional(REQUIRES_NEW): 同 bean 自调用
        // 会绕过代理。这与 accrue() 的失败取证是同一套写法。
        String outcome = requiresNewTx.execute(txStatus -> {
            accrualService.release(tenantId, accrual.getId(), reason, null);
            return "RELEASED";
        });
        return new BillingReversalResult(outcome, accrual.getId());
    }
```

```markdown
### §15.15 4.5C-1 门户取消订单的计费冲销

**问题**: 4.5B 的 `createForCustomer` 写 accrual (`status=OPEN`), `cancelForCustomer`
完全不碰它。客户取消后这笔应计永远停在 `OPEN` —— `Reconciliation` / `Report` /
`MonthlyClosing` 都只读 `BillingInvoice`, 3 个 `@Scheduled` 都不碰 accrual,
`BusinessEventListener` 只映射 `toState=SIGNED` 而取消不经 `SIGNED`。
月底手工 finalize 时这笔不存在的收入会被开成 invoice。

**做法**: 复用 `AccrualService.release()` (OPEN/OPEN_FAILED → RELEASED), 门户取消时同步调用。

| 项 | 结果 |
|---|---|
| finance 单测 | +10 (AccrualServiceTest +1 / BillingEngineServiceTest +9) |
| dispatch 单测 | +3 (cancelForCustomer 冲销编排) |
| IT | +2 (PortalCancelAccrualReversalIT) |
| FE | 0 改动 (异常翻译链每环 4.5B 已建好) |

**两个非显然的点**:

1. `AccrualServiceImpl.release` 的 `assertSmTransition` 的 `from_state` 原本是硬编码
   `OPEN`。不改它的话 `OPEN_FAILED` 会去断言 `OPEN→RELEASED` (V26 已有, 永远通过),
```

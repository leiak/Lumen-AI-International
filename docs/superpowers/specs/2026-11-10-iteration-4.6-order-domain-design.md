## 〇、背景：为什么这一刀落在委托单

本仓的 README 第 3 行定位是「面向货代、跨境电商、进出口企业的**全链路国际物流业务平台**」。但实测实现面（不是文档声称）：

| 事实 | 证据 |
| --- | --- |
| 已实现 61 张表（V42 之前 58 张，V42 再加委托单 3 张），全部集中在 WMS / 末端配送 / 计费财务 / 客服 SLA / 门户 | 全仓 `src/main/resources/db/migration/*.sql` 的 `CREATE TABLE` 全集 |
| `docs/02-业务表结构设计-v2.1` 设计了 93 张表，扣掉 14 张「命名等价已实现」（设计 `t_customer` ≡ 实现 `wms_customer` 等），**纯缺口 70 张** | 设计表名 vs 已建表名 diff |
| **11 个 Maven 模块里没有 `lumen-order` / `lumen-quotation` / `lumen-booking` / `lumen-customs` / `lumen-tracking`** | `lumen-parent/pom.xml` `<modules>` |
| 门户「客户下单」建的是**城配单**不是国际货运委托单 | `PortalCreateOrderRequest` 字段 = 仓库/收发地址/重量体积/站点数/取件窗口，落到 `wms_delivery_order` |
| `docs/19` 第 3 行「✅ 已按本对照补齐全部缺口」——**指的是设计文档 20–24 补齐，不是实现** | 同一文档矩阵里「订单处理 询价报价、委托单 ✅ 完整闭环」在实现层为零 |

**委托单是货代行业的合同级主干单据**（`docs/business/order/05-委托单业务细化-v4.0.md`）：向上承接询价报价，向下驱动订舱、操作、报关、干线、仓储、结算与跟踪。它是整个国际物流主干唯一真正缺失的地基，且已有 3 样现成基建可挂靠：

- 编号：`sys_number_rule` 已 seed `('ORDER','ORD','yyyyMMdd',6,'DAY')`（`V4__numbering.sql:52`），**至今无人消费**——这是给委托单预留的号段。
- 状态机：`t_state_transition` 表驱动 + `StateMachineEngine.assertTransition/allowedNext`（`lumen-extension`）。
- 事件：`EventBus` + `t_event_outbox` + `DefaultEventBus`（同事务写 outbox + `ApplicationEventPublisher.publishEvent`）。

## 一、目标与非目标

### 目标（Must）

1. 国际货运委托单的**建单 → 提交 → 确认 → 操作 → 交付 → 结算 → 关账**主链路端到端跑通，并可撤单 / 作废 / 退回修改。
2. 委托单落 **9 个状态**（当前无下游模块可驱动的状态一律不做，见 §四）。
3. 委托单费用项接入**已实现的计费链路**（`t_billing_accrual` → `t_billing_invoice` → 对账 → 客户门户看发票），使委托单不是一个孤岛。
4. 客户门户新增**独立的「货运委托」入口**（既有城配下单流程与其 IT 一行不改）。
5. 管理端 + 门户端**前端页面**可见可用。
6. 配套文档订正，消除本轮摸底抓到的假事实。

### 非目标（Out of Scope，本轮明确不做）

| 不做 | 理由 |
| --- | --- |
| 询价 / 报价 / 运价库 / 附加费 / 自动算价 | 报价引擎缺「计价基准 price_basis」等 5 个字段，且 4 级降级匹配 + 5 级优先级 + 6 种附加费算法**没有任何规则 DSL**。下一切片单独做，届时以 `t_billing_rule` 的 Aviator 表达式机制为模板 |
| 订舱 / 提单 / 补料 / 集装箱 / 集装箱动态 | 依赖承运人（`t_partner`）、港口（`t_port`）、柜型（`t_container_type`）三张未落库主数据表 + EDI 适配器 |
| 报关 / 关务全模块 | 依赖 `t_hs_code` / `t_country_region` / `t_customer_address` 三张未落库主数据表 + 单一窗口报文 |
| 干线运输 / 跟踪事件 / ETA / 里程碑 / 多式联运段 | 设计自己把「段级状态机」列为 V5 待深化项（`05v4:200`） |
| `t_port` / `t_partner` / `t_hs_code` / `t_container_type` / `t_customer` 等主数据表 | 见 §三·决策 4：用可空外键位 + 自由文本兜底，不在本轮建主数据表 |
| 改单 / 撤单 / 关账的完整费用规则（违约金、改单费） | `05v3:606-680` 体量大且依赖尚不存在的账单链路。本轮：**确认前可改、确认后只读；撤单不计违约金** |
| 保险 / 信用额度 / 危险品强校验 / 授信占用 | 依赖尚未落库的授信与资质主数据 |
| 利润快照 / `t_order_segment` / `t_milestone_instance` / `t_eta` | `docs/16` 有 DDL 但代码未建表，本轮不引入 |

| 切片 B「全局错误语义」 | 已呈交设计但本轮未获批准，暂缓；本轮新增的错误码沿用**现有数字前缀式**风格，不动全局 advice |

## 二、模块落点

**新建 Maven 模块 `lumen-order`**（`lumen-parent/lumen-order/`）。

理由：
- 与既有 11 个模块的粒度一致（wms / dispatch / cs / finance / customer / masterdata…），国际货运是独立业务域，不该塞进 wms 或 dispatch。
- 委托单是「合同级上游单据」，而 `wms_delivery_order` 是「末端派送需求」，两者是上下游关系不是同义关系。

依赖（单向，无环）：

```
lumen-order    →  lumen-common, lumen-extension, lumen-numbering
lumen-customer →  lumen-order          (门户端委托单 API，PortalFreightOrderController)
lumen-bootstrap→  lumen-order          (显式声明，保证 V42 迁移与 order 控制器在 classpath 上)
lumen-finance  →  (不依赖 order；用反射消费 order 事件，见 §七)
```

- `lumen-order` 需要 `lumen-extension`（`StateMachineEngine` + `DomainEvent`/`EventBus`）、`lumen-numbering`（`NumberGenerator`）、`lumen-common`（`BaseEntity` / `R` / `BizException` / `TenantContext`）。**不需要显式依赖 `lumen-rbac`**——`@PreAuthorize` 来自 `spring-boot-starter-security`（`lumen-common` 已带），`JwtUtil` 也在 `lumen-common`。
- **`lumen-order` 不依赖 `lumen-wms`**：`t_order.customer_id` 只是一个指向 `wms_customer.id` 的普通 `Long`（DDL 不建 FK，与仓库既有做法一致），不需要引用 `WmsCustomer` 实体。**`OrderView` 也不带 `customerName`**——照 `lumen-dispatch` 的既有做法（`WmsDeliveryOrder` 只有 `customerId`，DTO 里没有客户名）：管理端前端用已有的 `lumen-admin-web/src/services/wms/customer.ts`（`GET /api/v1/wms/customers`）做 id→名称映射；门户端用已有的 `GET /api/customer/profile` 拿自己的客户名。
- `lumen-customer` **已经**依赖 `lumen-wms`（`PortalCommonController` 直接用 `WmsCustomerMapper` 读 `wms_customer`），所以门户端要显示客户名时**不需要** order 模块参与。

迁移落点：`lumen-order/src/main/resources/db/migration/V42__order_schema.sql`。
Flyway 配置是 `locations: classpath:db/migration`（`application-test.yml` / `application-dev.yml`），会扫描 classpath 上**所有**模块的 `db/migration` 目录 —— `lumen-customer` 自己的 `V24/V24.2/V24.3` 就是这么被 bootstrap 应用的。V42 高于当前最大值 V41，且 V1..V41 已冻结不可改。

### 最小字段集裁决（相对 `docs/02` 的取舍）

`docs/02` 的 `t_order` 字段表缺 `05v3` 要求的 `version`（改单递增）/ `settlement_currency` / `exchange_rate_type` / `locked_exchange_rate` / `is_locked`/`lock_at`/`lock_by` / `submitted_at`/`confirmed_at`。

本轮**落**：设计表里有的全部字段 + 上列 8 个最小补充字段（其中 `version` 由 `BaseEntity` 提供）。
本轮**不落**（避免字段膨胀，且无消费方）：`05v3` 的 `need_*` 9 个服务需求标志、保险三字段（`insurance_currency`/`insurance_provider_id`/`insurance_policy_no`）、`is_prepaid`/`is_collect`、`payment_term`/`credit_period_days`、`is_archived`/`archived_at`。

**理由**：本切片无保险、无预付/到付、无账期、无归档的业务规则在跑，落这些列就等于「有列无语义」的假字段。`docs/02` 的 `is_insurance_required` / `insurance_amount` / `insurance_rate` 三列本轮**同样不落**（虽有设计，但保险业务不在本轮）。

## 四、状态机：9 态 / 15 条转换

### 4.1 为什么是 9 态

`docs/business/order/05-委托单业务细化-v4.0.md` §三 定义了 15 态全量转换表。其中 6 态（`BOOKED` / `SHIPPED` / `IN_TRANSIT` / `ARRIVED_PORT` / `CLEARING` / `DELIVERING`）的**驱动方全部尚未实现**：

- `BOOKED` ← 订舱模块的 `booking.confirmed` 事件（`t_booking` 未落库）
- `SHIPPED` / `IN_TRANSIT` / `ARRIVED_PORT` ← 跟踪模块的里程碑（`t_tracking_event` 未落库）
- `CLEARING` / `DELIVERING` ← 报关模块的 `customs.submitted` / `customs.released`（`t_customs_declaration` 未落库）

若本轮就 seed 这 6 态，得到的是**没有任何模块能驱动的死边**——`allowedNext()` 会向调用方暴露一个走不通的选项。留到对应切片落地时再补迁移边（补 seed 行即可，`t_state_transition` 是配置表，加行不改代码）。

### 4.2 本轮 9 态

```
DRAFT ──submit──▶ PENDING_CONFIRM ──confirm──▶ CONFIRMED ──startOperation──▶ IN_OPERATION
                                                                                    │
                                                                          deliver ───┘
                                                                                     ▼
                                                            SETTLED ──close──▶ CLOSED

DRAFT / PENDING_CONFIRM / CONFIRMED / IN_OPERATION ──cancel──▶ CANCELLED (终态)
DRAFT / PENDING_CONFIRM / CONFIRMED / IN_OPERATION ──void────▶ VOID     (终态)
PENDING_CONFIRM ──return──▶ DRAFT (要求修改)
```

状态码：`DRAFT` / `PENDING_CONFIRM` / `CONFIRMED` / `IN_OPERATION` / `DELIVERED` / `SETTLED` / `CLOSED` / `CANCELLED` / `VOID`

### 4.3 转换表（本轮 seed 的 15 行）

`state_machine_code = 'ORDER'`，`tenant_id = 0`，`guard_expression` 沿用 `'role:<code>'` 字符串惯例（documentary，不求值）。

> **`<code>` 必须是 `sys_role` 里真实存在的 code** —— 本轮用的是 `order_sales` / `order_operator` /
> `order_supervisor` / `customer` / `finance_ops` / `finance_manager`。
> 自造一个不存在的 code 等于写了句永远对不上的注释（`OrderSchemaIT` 有一条断言专门守这个）。

**与设计文档的偏离（已裁决）**：
- 设计是 `PENDING_CONFIRM → CONFIRMED`，本轮**保留**；但 `CONFIRMED → IN_OPERATION` 取代了设计的 `BOOKED → IN_OPERATION`（因为 `BOOKED` 不在本轮）。这是**唯一**一条「因裁剪状态而产生的跨态直连**。
- 设计 `DELIVERING → DELIVERED` 同样因裁剪合并为 `IN_OPERATION → DELIVERED`。
- 设计 `PENDING_CONFIRM → VOID` 的触发是「超时未确认」，本轮**不做超时任务**（无调度器），该行保留在转换表里供手动作废使用，`description` 保留设计语义。
- 设计 `*（有效态）→ VOID` 展开为 4 行（DRAFT / PENDING_CONFIRM / CONFIRMED / IN_OPERATION）；**不含 `DELIVERED` / `SETTLED`**（货已交付或已结算，单据性质已改变，不该作废）。
- 设计 `*（各进行态）→ CANCELLED` 展开为 4 行，同样不含 `DELIVERED` / `SETTLED`。

### 4.4 守卫（写在代码里，不在表里）

| 转换 | 守卫（service 层校验） |
| --- | --- |
| `DRAFT → PENDING_CONFIRM` | 必填完整：`customer_id` / `business_type` / `trade_direction` / `incoterms` / `service_type` 非空；至少 1 条货物明细；至少 1 条服务项 |
| `PENDING_CONFIRM → CONFIRMED` | 服务项金额合计 > 0；`settlement_currency` 非空 |
| `PENDING_CONFIRM → DRAFT` | 无（仅权限） |
| `CONFIRMED → IN_OPERATION` | 无 |
| `IN_OPERATION → DELIVERED` | 无 |
| `DELIVERED → SETTLED` | 无（费用闭环由财务侧另行核对，本轮不阻断） |
| `SETTLED → CLOSED` | 无 |
| `* → CANCELLED` | 取消原因必填（非空非空白，≥ 5 字符）；`DRAFT` 之外不计违约金（本轮无违约金规则） |
| `* → VOID` | 作废原因必填（非空非空白，≥ 5 字符） |

### 4.5 只读规则

`CLOSED` / `CANCELLED` / `VOID` 为终态：进入后**不可再编辑业务字段**，只能读。

### 5.4 汇总口径

`t_order.total_qty` / `total_weight_kg` / `total_volume_cbm` 由 `t_order_cargo` 明细**聚合**（`SUM(pkg_qty)` / `SUM(weight_kg)` / `SUM(volume_cbm)`），在**每次保存明细后**重算回主表。`is_dangerous` 主表字段 = `EXISTS(明细.is_dangerous = 1)`（**派生，不接受直接赋值**）。

`is_oversized` **不派生**——货物明细里没有「超限」这个概念（只有长/宽/高），它是主表上的独立录入字段。

1. 上述 3 张 `CREATE TABLE`。
2. `t_state_transition` seed **15 行**（§4.3）。**`tenant_id = 0`**（全局行）——`MybatisPlusConfig.ignoreTable` 显式豁免了 `t_state_transition` 的租户拦截（"任何租户上下文下都应该能看到全部转移规则"），V16/V20 的 WMS/DISPATCH 状态机也都是 `tenant_id=0`，照抄即可。**若错填 `tenant_id=1`，其它租户看不到转换规则，`assertTransition` 会误判为"未定义转移"。**

4. `sys_role` seed **3 个新角色**（id 15/16/17，见 §六·4b）。
5. `sys_role_permission` seed **27 行**（见 §六·4c）。
6. **不 seed `sys_number_rule`** —— `code='ORDER'` 的规则 V4 已经 seed 好了（`prefix='ORD'` / `yyyyMMdd` / 6 位 / DAY），直接 `NumberGenerator.generate("ORDER")` 即可。本轮只是**第一次真正消费**这条一直空转的规则。

### 3. 错误码（新增，数字前缀式）

`lumen-order` 新建 `OrderErrorCode` 枚举，**实现 `com.lumen.common.error.ErrorCode` 接口**（照 `FinanceErrorCode` 的写法：数字前缀 + `_` + 三位序号），并新建 `OrderException extends BizException`：

| 码 | HTTP | 含义 |
| --- | --- | --- |
| `404_101` | 404 | 委托单不存在 |
| `404_102` | 404 | 客户不存在 |
| `409_101` | 409 | 状态不允许该转换 |
| `409_102` | 409 | 当前状态不可编辑（仅 `DRAFT` / `PENDING_CONFIRM` 可编辑） |
| `400_101` | 400 | 货物明细为空 |
| `400_102` | 400 | 服务项为空 |
| `400_103` | 400 | 原因不能为空（取消/作废/退回） |
| `400_104` | 400 | 金额非法（确认时服务项金额合计 ≤ 0） |

编号段选 `4xx_1xx` 是为了避开既有的 `404_001`/`400_001`/`409_003`（finance / portal 段）。

**字段级校验不进 order 码段**：`@NotNull` / `@NotBlank` / `@Positive` / `@Size` 这类**单字段**约束由 jakarta bean validation 兜住 → `GlobalExceptionHandler.handleValidation` → HTTP 400 + `CommonErrorCode.PARAM_INVALID`（**code 4001**）。order 码段只留给**跨字段 / 集合级 / 状态级**的规则（明细为空、服务项为空、原因必填、金额合计、状态转换、不可编辑、实体不存在）。**同一个失败不要同时有两条码**——实现时不要既写 `@NotEmpty` 又在 service 里查空。

#### 3.1 异常落点：**不新建 `@RestControllerAdvice`**

`com.lumen.common.error.GlobalExceptionHandler` 是**全局无 scope** 的 `@RestControllerAdvice`，其中 `handleBiz(BizException)` 已经做了：

```java
ErrorCode ec = ex.getErrorCode();
return ResponseEntity.status(ec.getHttpStatus()).body(R.fail(ec.getCode(), ex.getMessage()));
```

也就是说**只要 `OrderException extends BizException` 且 `OrderErrorCode` 声明了正确的 `getHttpStatus()`，管理端与门户端都自动拿到正确的 HTTP 状态 + body 错误码**，本轮**不需要任何新的 exception advice**，也**不改 `GlobalExceptionHandler`**（切片 B 未获批准，全局语义不动）。

门户端路径同样成立：`CustomerExceptionHandler` 虽然是 `@Order(HIGHEST_PRECEDENCE)`，但它只声明了 `CustomerException` / `FinanceException` / 参数解析类三个 handler，**没有 BizException 分支** → `OrderException` 会落到 `GlobalExceptionHandler.handleBiz`。门户拿到的 `body.code` 是 order 段的码（如 `404101`）+ 对应 HTTP 状态。

> **为什么不像 4.5C-2 那样建「order→portal 码翻译表」**：4.5C-2 建 `FINANCE_TO_PORTAL` 是因为门户前端按 `404_00x` 族做统一空态渲染、finance 的 `404_006`/`404_007` 门户根本不认识。本轮的门户货运委托单页面是**新建**的，直接认 order 段码即可；再翻译一层等于凭空多出一张要维护的映射表。

#### 3.2 **`StateMachineException` 必须被转换（漏了必 400 而不是 409）**

`StateMachineEngine.assertTransition` 抛的是 `com.lumen.extension.state.StateMachineException`，它**也是 `BizException`**，但码是 `14001`、HTTP 是 **400**：

```java
public class StateMachineException extends BizException {
    public StateMachineException(String message) {
        super(new ErrorCode() { ... getCode() → 14001; getHttpStatus() → 400; });
    }
}
```

若 `OrderService` 直接让它冒出去，客户端拿到的是 **HTTP 400 / code 14001**，而不是约定的 **409 / 409_101**。因此 service 层必须做转换（二选一，实现时择一）：

- **方案 A（推荐）**：先用 `StateMachineEngine.allowedNext(code, from)` 判定，`toState` 不在结果里 → 直接抛 `OrderException(OrderErrorCode.STATE_TRANSITION_INVALID)`（409_101），根本不让 `assertTransition` 抛。
- **方案 B**：调 `assertTransition` 并 `catch (StateMachineException e)` → 转抛 `OrderException(STATE_TRANSITION_INVALID, e.getMessage())`。

两种方案都**必须**在 `OrderServiceImpl` 的状态转换入口统一收口，**不能**让 `StateMachineException` 逃到 controller。

| --- | --- | --- |

**状态机与守卫仍在 `lumen-order` 里**（门户端不重复实现一套），门户控制器只做「取 `CustomerContext.requireCustomerId()` → 调上面的方法 → 装 `R` 信封」。

## 七、领域事件与计费衔接

### 1. 事件

新建 `OrderStateChangedEvent extends DomainEvent`（照 `DeliveryOrderStateChangedEvent` 的形状）：

| 字段 | 说明 |
| --- | --- |
| `orderId` / `orderNo` | 委托单标识 |
| `fromState` / `toState` / `action` | 状态机三元组 |
| `customerId` | 用于计费的对手方 |
| `totalWeightKg` / `totalVolumeCbm` / `totalQty` | 货量快照（计费 env） |
| `estimatedAmount` | 服务项金额合计（计费 env 的 `amount`）。**`t_order` 上没有这一列** —— 转换瞬间由 `t_order_service_item.amount` 求和算出来放进事件 |
| `currencyCode` | 结算币种（`t_order.settlement_currency`） |
| `actor` | 当前操作人 |

`eventType()` 固定 `"order.state.changed"`；`aggregateType()` = `"ORDER"`；`aggregateId()` = orderId。

**每条状态转换都发布一条**（含 `order.submitted` / `order.confirmed` / `order.cancelled` / `order.voided` / `order.settled` / `order.closed` / `order.returned` / `ops.started` / `order.delivered` 这 9 个语义动作）。用 `action` 字段区分具体动作，`eventType` 保持单一（便于 `t_event_outbox` 按类型聚合）。

> 设计文档（`05v4:129-134`）用的是 `order.submitted` / `order.confirmed` 等**多个 eventType**。本轮裁决：**单一 eventType + action 字段**，理由是 `t_event_outbox` 与 `DomainEvent` 的 `eventType()` 是单值契约，做多个子类会显著放大代码面。`action` 字段保留全部语义。

### 2. 计费衔接

**事件驱动，finance 不依赖 order**（沿用 `BusinessEventListener` 既有的反射解耦模式）。

在 `lumen-finance` 的 `BusinessEventListener.mapToBillingEvent` 加一个 case：

```java
case "OrderStateChangedEvent" -> mapOrderEvent(event);
```

`mapOrderEvent` 规则：
- 仅当 `toState == "DELIVERED"` 时触发计提（与 `LAST_MILE` 的 `SIGNED` 触发点同构：货已交付 → 费用成立）。
- `businessType = FinanceConstants.BIZ_ORDER`（新增常量 `"ORDER"`）。
- `businessId = orderId`；`direction = RECEIVABLE`；`counterpartyType = CUSTOMER`；`counterpartyId = customerId`。
- env：`weight` ← `getTotalWeightKg()`；`volume` ← `getTotalVolumeCbm()`；`quantity` ← `getTotalQty()`；`amount` ← `getEstimatedAmount()`。

`lumen-finance` 里**新增常量** `BIZ_ORDER = "ORDER"` 和 `FIN_TRIGGER_STATE_ORDER = "DELIVERED"`（与 `FIN_TRIGGER_STATE_LAST_MILE` 同款——独立存放，不依赖 order 模块）。

`lumen-order` **不依赖 `lumen-finance`**：不直接调 `BillingEngineService`，全靠 outbox 事件。

> **为什么不在 `lumen-order` 里直接调 finance？** 两种做法都可行。选事件驱动的理由：(1) `lumen-finance` 已有 `BusinessEventListener` 这个现成的扩展点，加一个 case 即可，零新机制；(2) 避免 `lumen-order` → `lumen-finance` 的编译期依赖，委托单模块保持轻；(3) 与既有 `LAST_MILE` 链路的做法一致，下一个切片加订舱模块时可以直接复用同一套路。

**生产环境不 seed `t_billing_rule`**：运价是业务配置。IT 里现建（`BillingRuleService.create` + `activate`，照 `BillingEventListenerIT`）。若运营环境没有 `ORDER` 的 ACTIVE 规则，计提会记 `NO_RULE` 事件日志并静默跳过 —— 这是计费引擎的既有行为，不改。

### 3. 其它订阅方

本轮**只有 finance 一个订阅方**。通知（`order.submitted` → 给客户发确认提醒）留到下一切片——`notification` 模块已有 `notification_template` + `send_log`，接入成本低，但本轮不加，避免范围膨胀。

## 九、测试策略

### 1. 单元测试（`lumen-order/src/test/`，Mockito 5.7.0 + AssertJ）

**必须是纯 Mockito 单元测试，不带 `@SpringBootTest`** —— 与 `lumen-dispatch`（11 个测试文件全部无 `@SpringBootTest`）、`lumen-customer`（15 个测试文件全部无 `@SpringBootTest`）一致。`lumen-order` 因此**不需要** `src/test/resources/application-test.yml`，也**不需要**自建 test 迁移。

- `OrderServiceImplTest`：创建草稿（编号生成 / 明细聚合 / 汇总回写）、9 个状态转换的守卫分支、非法转换抛 `OrderException`（**断言 code=409101 / HTTP 409，不是 `StateMachineException` 的 14001/400**，见 §六·3.2）、不可编辑状态拒绝编辑。
- `OrderConstantsTest`：9 个状态常量 + 15 条 from→to 常量表存在且不重复（纯内存断言）。

## 2. 范围边界与不变量

以下**不变量**在本切片全程成立, 任何实现不得违反:

- **[I1]** 商家门户**不得**看到别的商家的数据。`dispute_reason` 是商家的原话, 只流向
  admin 侧, 不回流到商家门户的任何响应。
- **[I2]** `t_billing_adjustment` 的**表结构不变**。商家异议快照是**瞬态字段**
  (`@TableField(exist = false)`), 不落 `t_billing_adjustment` 任何一列 —— 迁移文件
  V1..V40 已应用, 本切片**不新增任何迁移**。
- **[I3]** 商家异议的**唯一权威来源**仍是 `t_reconciliation` 的 `dispute_*` 三列。
  admin 侧看到的是**只读快照**, 不是副本; 商家改不了, admin 也改不了。
- **[I4]** 分页上限由后端 clamp 决定 (size ≤ 200), 前端页大小选择器的最大值不得
  超过后端上限 —— 否则前端选 500 条, 后端静默截到 200, 商家以为看全了。
- **[I5]** 已应用的迁移文件 (V1..V40) 一个字节都不改。

## 3. 缺口 #8 — `PaymentRecordServiceImpl` 租户谓词与错误码

### 3.1 事实更正（重要）

4.5C-2 那一轮把 #8 描述成"**真实的跨租户读**"。这个说法**是错的**, 本切片更正:

`com.lumen.common.entity.MybatisPlusConfig` 注册了 `TenantLineInnerInterceptor`,
`t_payment_record` **不在**豁免名单里 (`t_event_outbox` / `t_approval_record` /
`t_billing_rule_item` / `t_exchange_rate` / `t_tax_rate` 才是)。所以运行期
`mapper.selectById(id)` 生成的 SQL 会被自动改写成
`... WHERE id = ? AND tenant_id = <TenantContext>` —— **运行时已经按租户隔离**。

`README.dev.md` 缺口 #2 对同类问题的措辞 ("属财务内部读, 暂不构成越权面") 是准确的。

### 3.2 剩下的真实缺陷

1. **代码里没有显式谓词**。隔离完全依赖拦截器 + `TenantContext` 的隐式行为。
   一旦这张表将来被加进豁免名单, 或者该 service 在无租户上下文 (定时任务 / MQ 消费)
   的场景下被复用, 就会真的越权。显式谓词是**纵深防御**, 不是补丁。
2. **错误码与 javadoc 不符**。`BillingPaymentRecordController.get` 的 javadoc 明写
   「缺失 / 跨租户 → `PAYMENT_RECORD_NOT_FOUND`」, 实现却抛 `NOT_FOUND (404_005)`。
   `FinanceErrorCode` 的注释里也承认了这一点 (L61), 且 `PAYMENT_RECORD_NOT_FOUND (404_007)`
   **全仓没有任何地方抛它** —— 一个从未被使用的预留码。

### 3.3 规范条款

- **[N8-1]** `PaymentRecordServiceImpl.get(tenantId, id)` 必须按 `id` **和** `tenantId`
  过滤, 并且只返回 `deleted = 0` 的行。
- **[N8-2]** `PaymentRecordServiceImpl.get` 在取不到时抛
  `FinanceErrorCode.PAYMENT_RECORD_NOT_FOUND` (404_007), 不得抛通用 `NOT_FOUND` (404_005)。
- **[N8-3]** `PaymentRecordServiceImpl.list` 的查询条件必须包含 `tenantId` 与
  `deleted = 0`。
- **[N8-4]** `PaymentRecordServiceImpl.get` / `list` 不得改变既有排序
  (`orderByDesc(id)`) 与分页语义。

> `BillingPaymentRecord` 实体**没有** `deleted` 字段 (DDL 有, 实体无 —— 见 README 缺口 #1),
> 所以软删过滤必须手写 `.apply("deleted = 0")`, 不能指望 `@TableLogic`。
> 这与商家窄接口 `MerchantBillingViewServiceImpl.paymentScope` 的写法一致。

## 4. 缺口 #9 — 商家门户列表分页

### 4.1 现状

| 端点 | 现状 | service 层 |
|---|---|---|
| `GET /api/customer/recon` | `page=1, size=20` **字面量** | `listReconciliations(..., page, size)` 已支持 |
| `GET /api/customer/invoice` | `page=1, size=20` **字面量** | `listInvoices(..., page, size)` 已支持 |
| `GET /api/customer/payment` | `page=1, size=20` **字面量** | `listPayments(..., page, size)` 已支持 |
| `GET /api/customer/adjustment` | **已接** `page` / `size` | `listMyAdjustments(..., page, size)` 已支持 |

finance 侧的 service **早就**按 `Page.of(clampPage(page), clamp(size))` 查了, 并且
`MerchantPage` 带 `total` —— 前端拿得到总数, 只是没人用。

`clamp`: `size <= 0 → 20`, `size > 200 → 200`; `clampPage`: `page < 1 → 1`,
`page > 1_000_000 → 1_000_000`。

### 4.2 规范条款

- **[N9-1]** `PortalReconController.list` / `PortalInvoiceController.list` /
  `PortalPaymentController.list` 必须接受 `page` (默认 1) 与 `size` (默认 20) 两个
  `@RequestParam`, 并原样传给 finance 侧 service; **不得**再写死字面量。
- **[N9-2]** `PortalAdjustmentController.list` 的现有 `page`/`size` 参数保持不变
  (已满足本条)。
- **[N9-3]** 商家门户的 4 个列表页必须渲染**服务端分页器**: `current` / `pageSize`
  取自组件状态, `total` 取自响应的 `total`, 翻页时按新的 `page`/`size` 重新请求。
- **[N9-4]** 4 个列表页**不得**再显示"截断提示" (「只显示前 N 条, 请导出 / 联系客服」)。
  有分页器之后该提示是错的 —— 剩下的记录不是"看不到", 是"翻页就能看到"。
- **[N9-5]** 前端页大小选择器的可选项为 `10 / 20 / 50 / 100`, 最大值不得超过后端
  clamp 上限 200 (见 [I4])。
- **[N9-6]** 翻页 / 改页大小时, 期间 / 状态等过滤条件必须**保持不变**。
- **[N9-7]** 请求失败时, 页面必须显示错误提示且**不**显示旧数据 (沿用既有
  `error` state 语义)。

### 4.3 antd 服务端分页的正确性依据

antd v5 的 `Table` 会在 `dataSource.length < pagination.total` 时**尝试本地切片**
(`node_modules/antd/es/table/InternalTable.js:228-246`):

```js
if (mergedData.length < total) {
  if (mergedData.length > pageSize) {
    warning(false, 'usage', '`dataSource` length is less than `pagination.total` but large than `pagination.pageSize` ...');
    return mergedData.slice((current - 1) * pageSize, current * pageSize);
  }
  return mergedData;      // ← 服务端分页走这一支: 不切片
}
return mergedData.slice((current - 1) * pageSize, current * pageSize);
```

即: **`dataSource.length <= pageSize` 时 antd 不切片**, 当前页数据原样渲染。
服务端分页因此是安全的 —— **前提是 `dataSource.length` 永远不超过 `pageSize`**,
这由后端 clamp (size ≤ 200) 与前端只请求当前页保证。

### 4.4 前端改动面

- `portalBillingService`: `listRecons` / `listInvoices` / `listPayments` /
  `listAdjustments` 增加可选 `page` / `size` 参数 (默认 1 / 20)。
- 4 个列表页: 新增 `page` / `size` state, `useEffect` 依赖 `[page, size]`,
  `Table` 的 `pagination` 传对象, 删除截断 `Alert`。
- `zh-CN.ts`: `truncatedWithExport` / `truncatedContactSupport` 两个键随最后一个
  引用点消失而删除。

## 5. 缺口 #13 — admin 侧看到商家异议

### 5.1 现状

商家提异议后, `t_reconciliation` 写下 `dispute_amount` / `dispute_reason` /
`dispute_at` 三列, 并把那张已存在的 DRAFT 调账单推进到 `PENDING_L1`。

admin 侧的调账单审批界面 (`lumen-admin-web/src/components/finance/FinanceAdjustmentList.tsx`)
展示的是 `current.reason` —— 那是 `runReconciliation` **自动生成**的
「对账差异自动生成: 期间 … 差异 -10.00 CNY」。**商家那句原话一个财务角色都看不到**。

### 5.2 传输方式的选择

**采用: 调账单实体上的瞬态字段 + service 批量回填。**

备选方案与取舍:

| 方案 | 取舍 |
|---|---|
| **A. 瞬态字段 (采用)** | `BillingAdjustment` 加 3 个 `@TableField(exist = false)` 字段, `AdjustmentServiceImpl.list` / `get` 用**一次**批量查询回填。admin-web 只加列 + 抽屉项, 后端 API 形状不变 (`R<List<BillingAdjustment>>`)。代价: 实体多 3 个非持久化字段。 |
| B. 独立端点 + DTO | 契约干净, 但 admin 列表要用 N+1 或额外一轮请求才能填列 —— 列表页每行一次请求, 不可接受。 |
| C. admin-web 直接查 recon | admin-web 没有 finance 内部只读 API 的接入, 要新开一套权限, 且跨模块耦合。 |

**A 的两个约束**:
1. 瞬态字段**只在 `list` / `get` 填**。`submit` / `l1Approve` 等写操作的返回值不填 ——
   admin 前端在写操作后是 `actionRef.current?.reload()` 重新拉列表, 走 `list` 即可。
2. **实体不被商家侧看到**。`BillingAdjustment` 只出现在 admin 的
   `BillingAdjustmentController` (9 个端点) 与内部 service; 商家门户的
   `PortalAdjustmentController` 返回的是 `AdjustmentView` record, 不含该实体。
   → [I1] 成立。

### 5.3 规范条款

- **[N13-1]** `BillingAdjustment` 增加 3 个瞬态字段 `disputeReason` / `disputeAmount` /
  `disputeAt`, 全部标注 `@TableField(exist = false)`, **不落库** ([I2])。
- **[N13-2]** `AdjustmentServiceImpl.list` / `get` 必须按 `adjustment_id` 反查
  `t_reconciliation` 回填这 3 个字段, 且查询必须限定 `tenant_id` 与 `deleted = 0`。
- **[N13-3]** 同一 `adjustment_id` 被多条 recon 认领 (脏数据) 时, 取 **`dispute_at` 最新**
  的那一条。排序 `dispute_at DESC` 后取第一条即可, 不做"稳定挑一个"的兜底。
- **[N13-4]** 没有异议的调账单, 3 个字段保持 `null` (不是空串 / 0)。
- **[N13-5]** `AdjustmentService.list` 增加 `Boolean disputed` 过滤参数:
  - `null` → 不过滤;
  - `TRUE` → 只返回**有**商家异议的调账单;
  - `FALSE` → 只返回**无**商家异议的调账单。
  过滤用 **Java 侧 id 集 + `in` / `notIn`** 实现 (与
  `MerchantBillingViewServiceImpl.ownedAdjustmentIds` 的既有写法一致), **不用 SQL 子查询** ——
  `TenantLineInnerInterceptor` 对相关子查询的处理是未验证风险, 而 id 集这条路已被
  4.5C-2 在生产验证过。
- **[N13-6]** `disputed` 集合为空时: `TRUE` → 返回空页; `FALSE` → **不加任何过滤条件**
  (全部调账单都无异议)。禁止生成 `id IN ()` 这种非法 SQL。
- **[N13-7]** `BillingAdjustmentController.list` 接受 `?disputed=true|false` 参数并透传。
- **[N13-8]** admin-web 的调账单列表必须有一列展示**是否**有商家异议, 并在详情抽屉里
  展示**异议理由原文 / 主张金额 / 异议时间**三项。
- **[N13-9]** admin-web 必须支持按「有异议 / 无异议」筛选。

### 5.4 admin-web 呈现

- 列表新增列「商家异议」: 有异议 → 橙色 Tag「有异议」+ 主张金额; 无 → 灰色 Tag「无」。
- 抽屉新增 3 个 `Descriptions.Item`: 「商家异议理由」(原文, 无则 `—`) /
  「主张金额」/「异议时间」。
- ProTable 搜索区新增 `disputed` 下拉 (有异议 / 无异议), 透传为 `?disputed=true|false`。

## 6. 数据流与时序

### 6.1 #13 读路径

```
admin-web ProTable
  → GET /api/v1/finance/adjustments?status=&disputed=&page=&size=
  → BillingAdjustmentController.list
  → AdjustmentServiceImpl.list(tenantId, status, disputed, page, size)
      1. wrapper = tenant_id + [status] + [disputed 的 in / notIn]
      2. selectPage → 本页 adjustment
      3. attachDisputes(tenantId, 本页 ids)
           → SELECT ... FROM t_reconciliation
             WHERE tenant_id = ? AND adjustment_id IN (本页 ids)
               AND dispute_at IS NOT NULL AND deleted = 0
             ORDER BY dispute_at DESC
           → 逐个 setDisputeReason / setDisputeAmount / setDisputeAt
  → R<List<BillingAdjustment>> (含瞬态字段)
```

### 6.2 #13 写路径 (不变)

商家提异议 → `MerchantBillingViewServiceImpl.raiseDispute` → 先 submit 调账单
(成功) → 再用 CAS 条件更新写 recon 三列。**本切片不改任何写路径**。

## 7. 明确不做的事

### 7.1 不新增迁移

3 个瞬态字段 + 3 个过滤参数都不需要 DDL 变更。**不写 V41**。

### 7.2 不改商家侧任何契约

`PortalReconController` / `PortalInvoiceController` / `PortalPaymentController` 只**增加**
可选参数, 既有调用方 (不传参数) 的行为不变 (默认 1 / 20)。

### 7.3 finance admin 列表的 `total` 缺失 (另开切片)

`BillingAdjustmentController.list` 返回 `R<List<BillingAdjustment>>` —— **没有 `total`**。
admin 前端 `financeAdjustmentService.listAdjustments` 用
`total: data.length` 硬凑, 于是 ProTable 的分页器**只能看到一页**。

这是 finance admin 侧**全部**列表端点的**系统性**问题
(`BillingInvoiceController` / `BillingAccrualController` / `BillingClosingController` /
`BillingEventLogController` / `BillingPaymentRecordController` / `BillingRuleController` /
`BillingAdjustmentController` 全部同构)。改一处会让 admin-web 的分页语义与其他模块不一致,
改全部则是另一个切片。

**本切片的处置**: 不改。写进 README 新缺口 (#14), 并在本 spec 里说明它对 #13 的影响 ——
财务只能在这一页里看到有异议的调账单; 若异议对应的调账单不在当前页, 财务需要用
「有异议」筛选把它筛出来 (筛选本身也会被 total 缺失限制在第一页)。

**这对 #13 的影响有限**: 财务用「有异议」筛选时, 后端返回的**第一页**就是有异议的
调账单 —— 筛选场景是完好的 (有异议的调账单通常远少于一页)。真正受影响的是
"翻页找第 21 条以后的调账单"这个场景, 那与异议无关。所以本切片的 #13 交付
**不被** #14 阻塞。

### 7.4 不动 `t_reconciliation` 的写路径

商家的异议数据仍由 4.5C-2 的 CAS 条件更新写入, 本切片只读。

## 10. 规范条款索引 (便于逐条对表)

| 编号 | 一句话 |

# Iteration 4.4 — 财务月结 + 对账 + 报表 设计

> **For agentic workers:** 继承 4.3.1/4.3.2 (V26/V27/V28/V29/V30, 14 entities, 14 services, 92 单元 + 22 IT + 146 Vitest, 34 endpoints). 4.4 在此基座上加: 月结 + 对账 + 报表.

**Goal:** lumen-finance 增加会计期间锁账(月结)+ 对账差异自动调账 + 3 种 Excel 报表导出 + Web 报表页, 给财务期末结账/对账一个最小可用闭环.

**Architecture:** 3 新表 (t_payment_record / t_monthly_closing / t_reconciliation) + 1 V31 migration + 3 状态机 (monthly_closing OPEN→IN_PROGRESS→CLOSED, 含 reopen) + 3 新 service + 1 报表 service (Apache POI 即时生成) + 1 异步 listener (CLOSED 后调账过账 → 增量重算快照) + 4 权限 + 1 角色扩展 (finance_manager). 复用 4.3.2 调账单流 (CREDIT/DEBIT + L1/L2 审批). 报表 Excel 走 GET 接口直接返回二进制.

**Tech Stack:** Spring Boot 3.2.5 + MyBatis-Plus 3.5.7 + Flyway 9.x + Apache POI 5.2 (报表) + Lombok + JUnit 5 + Testcontainers. Vite 5 + React 18 + TS 5 + Antd 5 + ProComponents 2.7 + Vitest 1 + RTL + MSW 2.

## 1. 背景与目标

### 1.1 现状 (4.3.2 末态)

- 计费引擎 (BillingEngineService) + 5 个状态机 (billing_rule / billing_invoice / billing_accrual / billing_adjustment) + 汇率 + 税率
- 14 entities + 14 services + 14 controllers
- L2 两级审批 (L1→PENDING_L2→L2_APPROVED) + 调账单 CREDIT/DEBIT 走 L1→L2→POSTED

### 1.2 缺口 (驱动 4.4)

1. **没有"会计期间"概念** — 任意时间可改任意单据, 没有"7 月已结账, 不能改 7 月单据"的边界 (虽然选了"快照+允许调账"模式, 仍有期间标记)
2. **没有对账** — 客户/承运商实际回款/付款 vs 财务应收/应付, 差异人工核对
3. **没有报表** — 财务想知道"本期开了多少发票 / 多少调账 / 汇率影响", 全靠 SELECT

### 1.3 目标 (4.4)

| 目标 | 验收 | 优先级 |
|------|------|--------|
| 月结周期 | t_monthly_closing 表 + 状态机 (OPEN→IN_PROGRESS→CLOSED) + start/close/reopen API | P0 |
| 月结快照 | 快照: total_invoice + total_accrual + total_adjustment + currency. CLOSED 后调账过账自动重计 | P0 |
| 实收/实付 | t_payment_record 表 + CRUD + CSV 批量导入 | P0 |
| 对账差异 | ReconciliationService: variance != 0 自动生成调账单 (CREDIT/DEBIT 走 4.3.2 审批流) | P0 |
| 报表导出 | 3 种: summary / detail / variance, Apache POI 即时生成, GET 接口返回 xlsx 二进制 | P0 |
| 报表 UI | /finance/closing + /finance/payments + /finance/reports (3 子页) | P0 |
| 增量重计 | CLOSED 后调账过账 (POSTED) → ClosingAffectedEvent → 异步重计快照 | P0 |
| 文档 | README §15.12 增量总结 | P0 |

### 1.4 非目标 (YAGNI 4.4 排除)

- ❌ 月结 lock 阻止新增单据 (用户已选"快照+允许调账", 不需硬锁)
- ❌ 异步报表任务 (POI 即时生成, < 2k 行内存 OK)
- ❌ 银行/ERP API 集成 (source_ref 字段预留即可)
- ❌ PDF 导出 (4.4 暂只 Excel)
- ❌ 月结自动开启 cron (运营手动 start)
- ❌ 月结跨年特殊处理 (一期跳过, 按 CHAR(7) 'YYYY-MM' 简单切)

### 4.2 MonthlyClosingService

**职责**: 月结周期 + 快照管理.

```java
public interface MonthlyClosingService {
    MonthlyClosing get(Long tenantId, String period);
    MonthlyClosing getOrCreate(Long tenantId, String period);  // 默认 OPEN 状态
    MonthlyClosing start(Long tenantId, String period);        // OPEN → IN_PROGRESS + 初版快照
    MonthlyClosing close(Long tenantId, String period);        // IN_PROGRESS → CLOSED
    MonthlyClosing reopen(Long tenantId, String period, String reason);  // CLOSED → IN_PROGRESS
    MonthlyClosing recalculateSnapshot(Long tenantId, String period);   // 增量重算 (Listener 调)
    List<MonthlyClosing> list(Long tenantId, int page, int size);
}
```

**关键规则**:
- `start`: 校验 state machine `monthly_closing OPEN→IN_PROGRESS`, 计算初版快照 = 该 period 全部 L2_APPROVED invoice + total accrual + total adjustment, 全部换算到 CNY 基准 (用各单据 `fx_rate_at_creation` 倒推)
- `close`: 校验 `IN_PROGRESS→CLOSED`, 写入 closed_by / closed_at / snapshot_recalculated_at = now
- `reopen`: 校验 `CLOSED→IN_PROGRESS`, 必须有 reopen_reason (>= 10 chars), 重算快照
- `recalculateSnapshot`: 不动 status, 只重算 3 个 snapshot_* 字段 + snapshot_recalculated_at; 由 ClosingAffectedEvent 触发

**快照计算公式**:
```
snapshot_total_invoice = SUM(
  L2_APPROVED invoice WHERE DATE_FORMAT(l2_approved_at, '%Y-%m') = period
  AND currency = 'CNY' → net_amount
  AND currency = 'USD' → net_amount * fx_rate_at_creation
)
snapshot_total_accrual = SUM(CONVERTED accrual 同期间)
snapshot_total_adjustment = SUM(L2_APPROVED 调账单同期间)  -- CREDIT 为正, DEBIT 为负
```

### 4.3 ReconciliationService

**职责**: 对账差异检测 + 自动调账.

```java
public interface ReconciliationService {
    ReconciliationResult runReconciliation(Long tenantId, String period);
    Reconciliation get(Long tenantId, Long id);
    List<Reconciliation> list(Long tenantId, String period, int page, int size);
    Reconciliation waive(Long tenantId, Long id, String reason);  // 手动标记差异接受 (不调账)
}

public record ReconciliationResult(
    String period,
    int totalChecked,
    int varianceCount,
    List<Reconciliation> variances,
    List<String> autoAdjustmentIds   // 自动创建的调账单 ID 列表
) {}
```

**关键规则**:
- `runReconciliation(period)`:
  1. 按 (tenant, period, direction, counterparty_id, currency) 分组
  2. `expected_amount` = SUM(invoice.net_amount WHERE status=L2_APPROVED AND period)
  3. `actual_amount` = SUM(payment_record.amount WHERE period)
  4. `variance_amount` = expected - actual
  5. 若 variance != 0:
     - RECEIVABLE variance > 0 (应收 > 实收) → 生成 DEBIT 调账单 (补收)
     - RECEIVABLE variance < 0 (应收 < 实收) → 生成 CREDIT 调账单 (退款)
     - PAYABLE variance > 0 (应付 > 实付) → 生成 CREDIT 调账单 (少付)
     - PAYABLE variance < 0 (应付 < 实付) → 生成 DEBIT 调账单 (补付)
  6. 调用 BillingAdjustmentService.create() 走 4.3.2 调账流, status=PENDING_L1
  7. 写入 t_reconciliation, 关联 adjustment_id
- 幂等: 同一 (tenant, period, direction, counterparty_id, currency) 已存在 reconciliation 且 status=ADJUSTMENT_CREATED → 跳过

### 4.4 ReportService (Apache POI 即时生成)

**职责**: 3 种报表 Excel 导出.

```java
public interface ReportService {
    byte[] exportSummary(Long tenantId, String period, String currency);   // 汇总表
    byte[] exportDetail(Long tenantId, String period, String currency);     // 明细 invoice+调账
    byte[] exportVariance(Long tenantId, String period, String currency);   // 对账差异
}
```

**关键规则**:
- `exportSummary`: 1 sheet, 3 行 (invoice/accrual/adjustment), 6 列 (币种 / 本期数 / 累计数 / 占比 / 同比上月 / 备注)
- `exportDetail`: 1 sheet, 每行 = 1 个 invoice, 关联 adjustment 放最后两列 (信用/借方调账金额). 排序: invoice_no ASC
- `exportVariance`: 1 sheet, 来自 t_reconciliation, 列: 期间 / 方向 / 客户/承运商 / 币种 / 应收/付 / 实收/付 / 差异 / 状态 / 调账单 ID
- POI 用 SXSSFWorkbook (流式), 数据量 < 2k 行, 内存 OK
- 空数据: 返回空 xlsx (1 sheet "No Data", 单行提示), 不抛 REPORT_EMPTY
- currency 参数: 默认 CNY; 若传 USD, 在金额列加 suffix " (USD)"

### 4.5 ClosingEventListener

**职责**: 调账过账 → 异步重算月结快照.

```java
@Component
@RequiredArgsConstructor
public class ClosingEventListener {
    private final MonthlyClosingService monthlyClosingService;

    @Async
    @EventListener
    public void onClosingAffected(ClosingAffectedEvent event) {
        String period = event.getPeriod();
        Long tenantId = event.getTenantId();
        try {
            monthlyClosingService.recalculateSnapshot(tenantId, period);
            log.info("Recalculated snapshot for tenant={} period={}", tenantId, period);
        } catch (Exception e) {
            log.error("Failed to recalculate snapshot for tenant={} period={}", tenantId, period, e);
        }
    }
}
```

**事件触发位置**: `BillingAdjustmentServiceImpl.markPosted` 在更新 status=L2_APPROVED→POSTED 后, 发 `ClosingAffectedEvent(tenantId, period)`. period 从 `markPosted` 时的 current date 取 `YYYY-MM`.

## 5. 关键流程

### 5.1 月结 start/close/reopen 时序

```
财务经理 → POST /finance/closing/start { period: "2026-10" }
  → MonthlyClosingService.start(tenantId, "2026-10")
    → getOrCreate("2026-10")  -- 第一次则创建 status=OPEN
    → StateMachineEngine.assertTransition(monthly_closing, OPEN, IN_PROGRESS)
    → recalculateSnapshot  -- 初版快照
    → UPDATE status=IN_PROGRESS

财务经理 → POST /finance/closing/close { period: "2026-10" }
  → StateMachineEngine.assertTransition(IN_PROGRESS, CLOSED)
  → recalculateSnapshot
  → UPDATE status=CLOSED, closed_by, closed_at

财务经理 → POST /finance/closing/reopen { period: "2026-10", reason: "发现未过账调账" }
  → StateMachineEngine.assertTransition(CLOSED, IN_PROGRESS)
  → UPDATE status=IN_PROGRESS, reopen_reason
  → recalculateSnapshot

调账过账 (BillingAdjustmentService.markPosted)
  → UPDATE adjustment.status=POSTED
  → publishEvent(ClosingAffectedEvent(tenantId, "2026-10"))
  → @Async ClosingEventListener.onClosingAffected
    → recalculateSnapshot(tenantId, "2026-10")
```

### 5.2 对账 runReconciliation 时序

```
财务经理 → POST /finance/reconciliation/run { period: "2026-10" }
  → ReconciliationService.runReconciliation(tenantId, "2026-10")
    1. SELECT invoice WHERE status=L2_APPROVED AND period, GROUP BY (direction, counterparty_id, currency)
       → expected_map
    2. SELECT payment_record WHERE period, GROUP BY (direction, counterparty_id, currency)
       → actual_map
    3. 全集 (expected_map.keySet() ∪ actual_map.keySet()) 遍历
       → variance = expected - actual
       → 若 variance != 0:
         - BillingAdjustmentService.create({
             adjustmentType: (variance > 0 && direction=RECEIVABLE) ? DEBIT : CREDIT,
             amount: |variance|,
             currency, sourceInvoiceId: <top 1 invoice in this group>,
             reason: "对账差异自动生成: 期次 2026-10, 差异 {variance}"
           })
         - adjustmentService.submit(adjustmentId)  -- 推 PENDING_L1
         - 写 t_reconciliation, status=ADJUSTMENT_CREATED, adjustment_id=<新>
    4. 幂等: 同一 key 已存在 reconciliation → 跳过 + 累计 totalChecked
  → return ReconciliationResult(totalChecked, varianceCount, variances, autoAdjustmentIds)
```

### 5.3 报表 export 时序

```
  → @PreAuthorize("hasAuthority('finance:report:export')")

    Content-Disposition: attachment; filename="summary-2026-10-CNY.xlsx"
```

## 10. 风险与回退

| 风险 | 缓解 |
|------|------|
| POI 内存峰值 (2k 行 Excel 估算 < 50MB) | 4.4 数据量小, 暂不监控; 5.x 数据量 > 10k 行再换异步任务 |
| ClosingEventListener 异步失败 | 失败只 log error, 不影响调账过账主流程; 提供 ManualReconcile API 兜底 |
| 调账重复过账导致 snapshot 多次重算 | recalculateSnapshot 幂等 (按 period 全量重算, 不增量) |
| 对账生成调账在跑批期间冲突 | runReconciliation 不加锁, 但 ReconciliationService 加幂等检查; 业务上层 (定时任务) 串行调用 |
| POI 版本冲突 | lumen-parent 已有 POI 5.2 依赖 (来自 lumen-bootstrap 报表, 4.2 用过) |

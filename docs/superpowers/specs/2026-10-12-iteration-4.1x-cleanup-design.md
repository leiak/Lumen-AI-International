## 3. PR1 — V23 + resolveException

### 3.1 V23 migration (`V23__dispatch_exception_resolve.sql`)

往 `t_state_transition` 灌 2 行：

```sql
INSERT INTO t_state_transition (state_machine, from_state, to_state, action, guard_expression, ...)
VALUES
('DISPATCH_ORDER', 'EXCEPTION', 'DISPATCHED', 'reDispatch', 'role:dispatch_admin OR role:dispatcher', ...),
('DISPATCH_ORDER', 'EXCEPTION', 'CANCELLED', 'exceptionCancel', 'role:dispatch_admin OR role:dispatcher', ...);
```

（具体字段对齐 V20 已有的 INSERT 模式；`tenant_id=0` 全局行；与 MybatisPlusConfig 的 `t_state_transition` ignore 一致。）

### 3.2 Service 契约

```java
public interface DeliveryOrderService {
    // ... 12 个原有方法 ...
    WmsDeliveryOrder resolveException(Long id, ResolveExceptionRequest req);
}
```

`ResolveExceptionRequest`：
- `strategy` enum: `RE_DISPATCH` | `CANCEL`
- `vehicleId` (RE_DISPATCH 必填)
- `driverId` (RE_DISPATCH 必填)
- `reason` (CANCEL 必填)

实现：
- `RE_DISPATCH`：校验车辆可用 + LoadingValidator → `assertTransition(SM, EXCEPTION, DISPATCHED)` (action=reDispatch) → `update` vehicle status IDLE → DISPATCHED（同 PR4 assign 路径）+ order status
- `CANCEL`：`assertTransition(SM, EXCEPTION, CANCELLED)` (action=exceptionCancel) → 写 remark

### 3.3 Controller 端点

`POST /api/v1/dispatch/orders/{id}/resolve-exception`
- `@PreAuthorize("hasAuthority('dispatch:order:assign')")` — RE_DISPATCH 路径
- `@PreAuthorize("hasAuthority('dispatch:order:cancel')")` — CANCEL 路径
- 在 controller 层根据 strategy 分支
- `@Audit(action="dispatch:order:resolveException", resource="dispatch-order")`

### 3.4 测试

- `DeliveryOrderServiceTest` +4 cases：
  - `resolveException_RE_DISPATCH_assignsNewVehicle` 
  - `resolveException_RE_DISPATCH_invalidVehicle_throwsInsufficientVehicle`
  - `resolveException_CANCEL_fromException_succeeds`
  - `resolveException_invalidStrategy_throws`
- `ResolveExceptionIT` (lumen-bootstrap)：3 cases
  - `resolveException_reDispatch_restoresDispatched`
  - `resolveException_cancel_endsAsCancelled`
  - `resolveException_fromNonException_throws`

## 4. PR2 — Outbox 事件发布

### 4.1 已具备的 outbox 基础设施

- `t_event_outbox`（V7）：`event_type, aggregate_type, aggregate_id, tenant_id, payload (JSON), status, retry_count, max_retries, next_retry_at` —— **schema 已够用，无需 V24 迁移**
- `lumen-extension/outbox/EventBus`（接口）+ `DefaultEventBus`（publish 写 outbox 行 + 触发 `@EventListener`）
- `DomainEvent`（接口）
- `OutboxDispatcher`（定时拉取 PENDING 行分发）

### 4.2 新事件

```java
public class DeliveryOrderStateChangedEvent implements DomainEvent {
    private String eventId;          // UUID, dedup
    private String eventType;        // "delivery_order.state_changed"
    private String aggregateType;    // "WmsDeliveryOrder"
    private String aggregateId;      // String.valueOf(orderId)
    private Long tenantId;
    private Instant occurredAt;
    private Map<String, Object> payload;  // orderId, fromState, toState, action, no, vehicleId, driverId, ...
}

public class DeliveryExceptionStateChangedEvent implements DomainEvent {
    // 5 个异常工单转换
}
```

### 4.3 钩入点

**选项 A（推荐）**：在每个 service 的状态机迁移后，调 `eventBus.publish(event)`。

```java
// DeliveryOrderServiceImpl.assign(...) 末尾
orderMapper.updateById(order);
eventBus.publish(DeliveryOrderStateChangedEvent.of(...));   // ← 新增
log.info(...);
```

优点：精准控制事件 payload（每种转换携带不同字段）；易测试。
缺点：13 个 service 方法都要加一行（机械）。

**选项 B（不推荐）**：扩展 `StateMachineEngine.assertTransition` 让它接受 `DomainEvent` 并自动 publish —— 跨所有 SM 实例。
优点：一次改动覆盖全局（WMS 也受益）。
缺点：跨模块改动风险高；payload 难通用化；不容易精确控制 `vehicleId` 等字段。

→ **选项 A**。

### 4.4 事务边界

`eventBus.publish()` 内部是对 `t_event_outbox` 的 INSERT，与外层 `@Transactional` 共事务 —— 业务表回滚则 outbox 行也回滚（**正好**。事件不会"发了但状态没改"）。

### 4.5 测试

- Unit（DeliveryOrderServiceTest 加 Mockito.verify(eventBus).publish(any()) 在每个 transition case）：
  - `assign_publishesEvent` 等等
- IT（`OutboxDeliveryEventIT`，lumen-bootstrap）：
  - `fullFlow_sign_creates8OutboxRows` — create → assign → load → depart → arrive → sign 应产生 6 个 `delivery_order.state_changed` + 0 个 exception
  - `raiseException_createsExceptionEvents` — raise → 1 个 `delivery_order.state_changed`(EXCEPTION) + 1 个 `delivery_exception.state_changed`(OPEN)

### 4.6 监听器（可选）

加一个 `DeliveryOrderStateChangedLogger` listener 只打日志（占位用，未来真实订阅方接入）。或者不写，让 `OutboxDispatcher` 把事件抛到 Spring 事件总线，由未来的 `DeliveryOrderStateChangedFinanceListener`（V5/4.3）订阅。

→ **不写**（最小化 PR2 范围）。

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 13 处 service 方法机械重复 publish 调用易漏 | 每个 service method 都有 unit test 断言 `verify(eventBus).publish(any())` —— 漏一个就红灯 |
| outbox 行重（PR2 publish 调用本身就重复） | `event_id` UUID 去重，PK `uk_event_id` 保证幂等 |
| StateMachineEngine 已经够复杂，再加 publish 会成"上帝对象" | publish 放在 service 层而非 engine 层（选项 A 的核心理由） |
| PR2 改动会触发 OutboxRetryIT 等已有 outbox 测试的并发问题 | publish 是 INSERT 不阻塞；listener 不在本切片写 —— 已有 IT 不应受影响 |

# 4.5C-1 门户取消订单的计费冲销 Design

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this spec task-by-task via a plan doc. Steps use checkbox (`- [ ]`) syntax in the plan, not this spec.

**Goal:** 客户在门户取消 `PENDING_DISPATCH` 订单时，把 4.5B 下单时写下的计费应计 (accrual) 从 `OPEN` 释放为 `RELEASED`，消除「订单已取消但账上仍有应计收入」的账实不符。

**Architecture:** 复用 4.3.1 已有的 `AccrualService.release()`（OPEN → RELEASED，语义即「本期不计入收入」），新增一条 `billing_accrual` 状态机迁移 `OPEN_FAILED → RELEASED` 让计费失败的应计也能被冲销。在 `BillingEngineService` 加 `reversalForSourceEventId(tenantId, sourceEventId, reason)` 按 accrual 状态分派，`DeliveryOrderServiceImpl.cancelForCustomer` 同步调用它。冲销**非阻塞**（失败只记 ERROR 日志），但 409 预检**在写 DO 状态之前**完成，保证被拒绝的取消不会留下已改状态的半成品单。

**Tech Stack:** Spring Boot 3.2.5 / MyBatis-Plus 3.5.7 / Flyway / JUnit 5 / Mockito / AssertJ / Testcontainers.

## 1. Goals & Non-Goals

### 1.1 要解决的问题

4.5B 的 `DeliveryOrderServiceImpl.createForCustomer` 在建单成功后同步调 `BillingEngineService.estimateAndAccrue`，写一行 `t_billing_accrual`，`status = OPEN`，其中：

- `source_event_id` = `String.valueOf(doId)`（注释里写明这是幂等键）
- `business_type` = `'LAST_MILE'`
- 唯一键 `uk_accrual (tenant_id, source_event_id, business_type, deleted)`

`cancelForCustomer` (4.5B.2 T2.4) 只改 DO 状态和 remark、发事件，**完全不碰 accrual**。结果：客户取消的单，对应的 accrual 永远停在 `OPEN`。

`OPEN` 的 accrual 会不会被别的机制自动清理？核过 4.3/4.4 三个模块：

| 模块 | 读 accrual 吗 | 会自动 finalize 吗 |
|---|---|---|
| `BillingReconciliationService` | 否 —— 读的是 `BillingInvoice` + `PaymentRecord` | 否 |
| `ReportService`（含 `REPORT_GENERATION_FAILED`） | 否 —— 报表基于 invoice | 否 |
| `BillingMonthlyClosingService` | 否 —— 基于 invoice + adjustment | 否 |

全仓只有 **3 个 `@Scheduled` 方法**（`SlaEscalationScheduler` / `OutboxDispatcher` 轮询 / `RateSyncService` 汇率同步），**没有任何定时任务把 accrual 的 `OPEN` 或 `OPEN_FAILED` 转成别的状态**。

outbox 轮询会不会兜住失败的 accrue？也不会 —— `BusinessEventListener.onEvent` 只把 `toState = SIGNED` 的 `DeliveryOrderStateChangedEvent` 映射成计费事件，其余全部返回 null 静默跳过。而 `PENDING_DISPATCH → CANCELLED` 的订单永远不会经过 `SIGNED`。所以「等后台重试」这条路对被取消的单是不存在的。

`OPEN_FAILED` 同样没有重试 job —— 4.5B 的注释和 README §15.14 里写的「由后台 job 重试」是不成立的描述。全仓共 **6 处**注释这么写（`DeliveryOrderService.java:146`、`DeliveryOrderServiceImpl.java:91`、`DeliveryOrderServiceCreateForCustomerTest.java:193`、`BillingEngineService.java:39` 与 `:60`、`BillingEngineServiceImpl.java:283`），需要更正，但那是独立小改，本 spec 只记为已知偏差。

所以准确的说法是：**这是一颗埋着的雷，不是已经爆掉的雷。** 月底有人手工 finalize 那批 accrual 时，这笔根本不存在的收入就会被开成 invoice，一路带到对账和报表。

### 1.2 目标

1. 门户取消 → accrual 从 `OPEN` 变 `RELEASED`（主路径）
2. `OPEN_FAILED` 的 accrual 也走释放（用户在设计阶段明确要求，避免取消后仍留一个失败的取证行）
3. 已开票（`CONVERTED`）或开票中（`LOCKED`）的 accrual **拒绝取消并返回 409**，且 DO 状态一个字节都不改
4. 冲销幂等：重复触发不产生副作用
5. 冲销失败**不阻塞**取消（用户已定），但必须有带 `doId` 的 ERROR 日志可定位

### 1.3 非目标 (YAGNI)

- ❌ 走红字 adjustment (`t_billing_adjustment`) —— 该表 `source_invoice_id` 是 NOT NULL，而被取消订单的 accrual 还没有 invoice，红字无处挂
- ❌ 新增 `BillingAccrual` 反向计费原语 —— `AccrualService.release()` 语义完全够用
- ❌ 改 `canCancel` 的计算逻辑 —— 它现在只看 DO 状态。若改成也查 accrual，订单列表页每行都要打一次财务库；罕见竞态（`PENDING_DISPATCH` 但已开票）用点击后 409 + 文案表达即可
- ❌ FE 改动 —— 沿用既有的 `409_001`，后端文案原样透传到 `message.error`，见 §7.3
- ❌ 动 `cancelForCustomer` 的 `@Transactional` —— 它已是承重项（`EventBus.publish` 是 `MANDATORY`），见 §6.2
- ❌ 把 `AccrualService.release` 放宽到接受任意状态 —— 幂等分支属于新方法，见 §6.4
- ❌ 在 `BillingEngineServiceImpl` 里重写一遍释放逻辑 —— 委托给已有的 `AccrualService.release`
- ❌ 修正 4.5B 那 6 处「后台 job 重试」的不实注释 —— 独立小改，不混进本 PR

- 4.5B spec: `docs/superpowers/specs/2026-10-19-iteration-4.5B-customer-order-pickup-design.md`（§5.3 定义了 `cancelForCustomer`）

## 2. 方案选型

三个候选，结论是复用 `release()`。

| 方案 | 做法 | 否决理由 |
|---|---|---|
| **A. `release()` 改状态** ✅ | 把 accrual 从 OPEN/OPEN_FAILED 推到 RELEASED | 采纳。语义准确（`AccrualService` javadoc 原话：「释放: OPEN → RELEASED，用于本期不计入收入的场景」），不新增计费原语，不需要 invoice |
| B. 红字 adjustment | 建一条 `t_billing_adjustment` 冲减 | `source_invoice_id` NOT NULL，被取消单的 accrual 没有 invoice，挂不上 |
| C. accrual 反向计费 | 新增负金额 accrual | 同一 `uk_accrual` 键上必然撞唯一键；且「一笔应计被释放」和「新增一笔负应计」在期末结转语义上不等价 |

**选 A 的关键前提**：`AccrualServiceImpl.release()` 目前只接受 `OPEN`，要让它接受 `OPEN_FAILED` 就必须先补状态机迁移（V26 只种了 4 条边，`OPEN_FAILED` 是终点，没有出边）。这是 §4 存在的唯一理由。

## 3. 状态分派表

`reversalForSourceEventId` 读到 accrual 后的动作：

| accrual 状态 | 动作 | 理由 |
|---|---|---|
| **查不到** | 无需冲销，成功返回 | `createForCustomer` 的 `estimateAndAccrue` 有三种「不写 accrual」的路径：无规则命中（`SOURCE_NONE`）、表达式求值前就返回 null、唯一键冲突静默 return null（见 `BillingEngineServiceTest` 的 4 个 `returnsNull` 用例）。这些情况本就没有应计 |
| `OPEN` | → `RELEASED` | 主路径，V26 已有种好的 `release` 边 |
| `OPEN_FAILED` | → `RELEASED` | 设计阶段决策。需 V38 新增迁移 |
| `RELEASED` | 幂等跳过，成功返回 | 重试安全 |
| `CONVERTED` | 抛 `ACCRUAL_ALREADY_CONVERTED` → 门户 409 | 已开出 invoice，不可回退 |
| `LOCKED` | 同 `CONVERTED` → 抛同一异常 | **防御性分支**。`AccrualServiceImpl.finalize` 全程 `@Transactional`，LOCKED 理论上不可见（要么提交成 CONVERTED，要么回滚成 OPEN）。归入 409 是为了万一有残留行时不误动它 |

## 4. Schema Changes (V38)

### 4.1 `t_state_transition` 加 1 行

V26 (第 212–220 行) 给 `billing_accrual` 种了 4 条边：

```sql
('billing_accrual', 'OPEN',   'LOCKED',     'finalize', 'role:system', '锁定待生成单据',   10, ...)
('billing_accrual', 'OPEN',   'OPEN_FAILED','fail',     'role:system', '计费失败回滚',     11, ...)
('billing_accrual', 'OPEN',   'RELEASED',   'release',  'role:system', '释放到下一周期',   12, ...)
('billing_accrual', 'LOCKED', 'CONVERTED',  'convert',  'role:system', '锁定后转为单据',   20, ...)
```

`OPEN_FAILED` 是**终点，没有出边**。V38 补第 5 条：

```sql
('billing_accrual', 'OPEN_FAILED', 'RELEASED', 'releaseFailed', 'role:system', '计费失败后释放', 13, 0, NOW(), NOW(), 0, 1)
```

`sort_order = 13` 接在 OPEN 的三条（10/11/12）之后，与 20 组的 LOCKED 边隔开。

### 4.2 `V38__accrual_open_failed_to_released.sql` 全文

```sql
-- =============================================================
-- V38: billing_accrual 状态机补 OPEN_FAILED → RELEASED 边
--
-- 背景 (4.5C-1 设计阶段发现):
--   V26 给 billing_accrual 种了 4 条边, 其中 OPEN_FAILED 是终点 ——
--   计费失败的应计一旦落进 OPEN_FAILED 就再也无法离开, 没有任何路径
--   能把它清掉。
--
--   4.5C-1 要做的是: 客户在门户取消了订单, 如果这单的 accrual 当初
--   因表达式求值失败而落在 OPEN_FAILED, 取消之后这行仍然是"取证实",
--   账单侧永远动不了它。
--
-- 处理:
--   补一条 OPEN_FAILED → RELEASED 边 (transition_name=releaseFailed),
--   让 AccrualServiceImpl.release() 的状态机校验 (assertSmTransition)
--   在 OPEN_FAILED 状态下也能通过。
--
--   不动 V26 本身 —— Flyway 已记录其 checksum, 改动会导致校验失败。
-- =============================================================

INSERT INTO t_state_transition
    (state_machine_code, from_state, to_state, transition_name, guard_expression, description, sort_order, tenant_id, created_at, updated_at, deleted, version)
VALUES
('billing_accrual', 'OPEN_FAILED', 'RELEASED', 'releaseFailed', 'role:system', '计费失败后释放', 13, 0, NOW(), NOW(), 0, 1)
ON DUPLICATE KEY UPDATE description = VALUES(description), sort_order = VALUES(sort_order);
```

`ON DUPLICATE KEY UPDATE` 沿用仓库既有惯例（V25 / V26 / V27 / V30 都是这个写法），命中 `uk_machine_from_to_tenant (state_machine_code, from_state, to_state, tenant_id)` 时幂等。

### 4.3 `guard_expression` 不会被求值

`StateMachineEngine.assertTransition` **只校验边是否存在，从不读 `guard_expression`**（已核实实现）。所以这条边的 `'role:system'` 纯粹是文档性的，与 V26 那 4 条同款，不会因为门户是 `aud=portal` 的 JWT 而被拦下。

### 4.4 `FinanceErrorCode` 加 1 个码

`409_001`–`409_003` 已被 `DUPLICATE_RULE` / `INVOICE_NO_CONFLICT` / `INVALID_STATE_TRANSITION` 占满，新增：

```java
ACCRUAL_ALREADY_CONVERTED         (409_004, "Accrual 已转为单据，不可冲销",       409),
```

同时把类注释里的区间 `409_001..409_003` 改成 `409_001..409_004`。枚举最后一项 `REPORT_GENERATION_FAILED (400_023)` 带分号，新码插在它前面。

## 5. Service Shape

### 5.1 `AccrualServiceImpl.release()` 放宽状态 guard

现状（L172）：`FinanceConstants.ACCRUAL_STATUS_OPEN.equals(accrual.getStatus())` 否则抛 `INVALID_STATE_TRANSITION`。改为：

```java
if (!FinanceConstants.ACCRUAL_STATUS_OPEN.equals(accrual.getStatus())
        && !FinanceConstants.ACCRUAL_STATUS_OPEN_FAILED.equals(accrual.getStatus())) {
    throw new FinanceException(FinanceErrorCode.INVALID_STATE_TRANSITION,
            "只有 OPEN / OPEN_FAILED 的应计可释放, 当前状态: " + accrual.getStatus());
}
```

`ACCRUAL_STATUS_OPEN_FAILED` 常量已存在于 `FinanceConstants:45`，不需要新建。

**这一处是必需的** —— 不放宽，`release` 内部的 `assertSmTransition(SM_BILLING_ACCRUAL, OPEN, RELEASED)` 会因为 `from_state` 是 OPEN_FAILED 而抛异常。

副作用（有意为之）：staff 现在也能通过 controller 手工释放 `OPEN_FAILED` 的行。两个入口语义保持一致，比「门户能释放但后台不能」要好解释。

### 5.2 `BillingEngineService` 加 2 个方法 + impl 注入 `AccrualService`

```java
/**
 * 4.5C-1 — 纯读预检: 该 sourceEventId 的应计当前是否可冲销.
 *
 * <p>不修改任何数据。供 cancelForCustomer 在改 DO 状态<b>之前</b>调用,
 * 让被拒绝的取消不会留下已改状态的半成品单 (见 spec §6.1 第 3 步)。
 *
 * <p>已 CONVERTED / LOCKED 抛 {@link FinanceErrorCode#ACCRUAL_ALREADY_CONVERTED} (409_004)。
 */
void assertReversible(Long tenantId, String sourceEventId);

/**
 * 4.5C-1 — 按 sourceEventId 冲销一笔应计 (门户取消订单时调用).
 *
 * <p>幂等: 查不到 / 已 RELEASED 都视为成功。已 CONVERTED / LOCKED 抛
 * {@link FinanceErrorCode#ACCRUAL_ALREADY_CONVERTED} (409_004)。
 *
 * <p>真正的释放在 REQUIRES_NEW 独立事务里跑, 失败不会污染调用方事务 ——
 * 原因见 spec §6.2。
 *
 * <p>businessType 固定 LAST_MILE —— 4.5B createForCustomer 写死这个值。
 */
BillingReversalResult reversalForSourceEventId(Long tenantId, String sourceEventId, String reason);

record BillingReversalResult(String outcome, Long accrualId) {}
```

`BillingEngineServiceImpl` 需要**新增注入 `AccrualService`**（构造函数第 9 个参数）。冲销的写操作委托给 `AccrualService.release`，不在 impl 里重写一遍状态机校验 —— DRY。

无循环依赖：`AccrualServiceImpl` 只依赖 4 个 mapper + `StateMachineEngine`，不依赖 `BillingEngineService`。

两个方法各自独立查一次 `t_billing_accrual`（`tenant_id` + `source_event_id` + `business_type = FinanceConstants.BIZ_LAST_MILE`，命中 `uk_accrual`）。`BillingAccrual.deleted` 带 `@TableLogic`，MyBatis-Plus 自动追加 `deleted = 0`，查询条件里**不要**手写。

为什么是两个方法而不是一个（详见 §6.3）：预检必须发生在写 DO 状态之前，冲销必须发生在写状态之后。

`BillingReversalResult` 作为嵌套 record 放在接口里。该接口目前没有嵌套类型，这是第一个；`outcome` 取值 `RELEASED` / `ALREADY_RELEASED` / `NOT_FOUND`，用于测试断言分派分支和将来 staff 侧 UI 显示。

### 5.3 `DeliveryOrderServiceImpl.cancelForCustomer()` 插入两段

在既有 uniform-404 校验和 `PENDING_DISPATCH` guard **之后**、改 DO 状态**之前**插入预检；在 `updateById` 之后、发事件之前插入冲销。方法的 `@Transactional` **保持不动**（原因见 §6.2）。

## 6. 数据流与事务边界

### 6.1 完整流程

```
1. uniform 404 校验                                    (不变)
2. status == PENDING_DISPATCH 否则 409_001              (不变)
3. billingEngineService.assertReversible(tenantId, sourceEventId)   ← 新增, 纯读
       查不到 / OPEN / OPEN_FAILED / RELEASED  → 放行
       CONVERTED / LOCKED → 抛 ACCRUAL_ALREADY_CONVERTED → 409
       ★ 此刻 DO 一个字节都没改
4. order.setStatus(CANCELLED) + remark 追加 → updateById  (不变)
5. billingEngineService.reversalForSourceEventId(...)                ← 新增, 写
       失败 → log.error, 不 rethrow (不阻塞)
6. eventBus.publish(DeliveryOrderStateChangedEvent)     (不变)
```

### 6.2 事务边界：外层不能动，冲销必须隔离出去

`cancelForCustomer`（`DeliveryOrderServiceImpl.java:775`）**已经有 `@Transactional`**，且它是承重的 —— 因为 `DefaultEventBus.publish` 标注的是 `@Transactional(propagation = Propagation.MANDATORY)`（`DefaultEventBus.java:17`），没有外层事务它直接抛 `IllegalTransactionStateException`。所以「去掉 `@Transactional` 让 `updateById` 走 auto-commit」这条路是**堵死的**，那会拆掉 DO 状态与 outbox 行之间的事务原子性（事务性 outbox 的全部意义）。

那「外层事务 + 里面 catch 掉冲销异常」行不行？不行：

1. `AccrualServiceImpl.release` 是 `@Transactional`（默认 `REQUIRED`），会加入 `cancelForCustomer` 的外层事务
2. release 抛异常（如 `OptimisticLockingFailureException`，发生在写 accrual **之后**）→ Spring 的 `globalRollbackOnParticipationFailure` 把外层事务标记为 **rollback-only**
3. dispatch 侧 catch 掉、log、继续 publish 事件
4. 方法返回时 commit → 抛 `UnexpectedRollbackException` → **整个取消 500 回滚**

结果是「不阻塞」反而变成「整单取消失败」，与设计决策正好相反。

**解法**：把释放动作放进一个 REQUIRES_NEW 独立事务，让它与外层事务完全隔离。仓库里已经有现成设施 —— `BillingEngineServiceImpl` 构造时就建了一个 `requiresNewTx`（`BillingEngineServiceImpl.java:69` / `:88-89`），`accrue` 的失败取证正是用它，这样外层 `throw FinanceException(EXPRESSION_INVALID)` 触发回滚时失败标记已经落库。冲销复用同一个模板：

```java
String outcome = requiresNewTx.execute(tx -> {
    accrualService.release(tenantId, accrual.getId(), reason, null);
    return "RELEASED";
});
```

`accrualService.release` 是另一个 bean，它的 `@Transactional(REQUIRED)` 会加入这个 REQUIRES_NEW 事务；release 抛异常 → 内层事务回滚 → 异常向上抛给 dispatch → dispatch catch 并 log → **外层事务从未被标记 rollback-only，照常提交**。

用 `TransactionTemplate` 而不是 `@Transactional(REQUIRES_NEW)` 注解，是因为 `reversalForSourceEventId` 与 `requiresNewTx` 在同一个 bean 里，自调用会绕过代理。这与 `accrue` 的既有写法一致。

代价：REQUIRES_NEW 会从连接池再取一条连接并挂起外层连接。门户取消是低频客户操作，池压力可忽略。

### 6.3 为什么预检和冲销要查两次

合并成一次（把冲销放最前）的话，「冲销成功但 status 写入失败」会留下一张 **DO 仍 PENDING_DISPATCH、accrual 已 RELEASED** 的单 —— 这单之后还能正常派送，但永远不会计费，属于永久漏计费。虽然重试 cancel 能自愈（冲销幂等），但用户不重试就收不回。

分成两次，两次都是唯一索引点查，开销可忽略，换来「先判定、再落状态、最后做财务后果」的清晰语义。

（有了 §6.2 的 REQUIRES_NEW 隔离之后，这个失败方向的风险进一步降低：冲销失败时内层事务已回滚，accrual 保持原状，与「DO 没被改」是一致的，不会出现单边状态。）

### 6.4 幂等归属

`release` 对非 OPEN/OPEN_FAILED 状态**仍然抛 `INVALID_STATE_TRANSITION`，保持严格**。`RELEASED` 的幂等跳过写在 `reversalForSourceEventId` 内部 —— 它本来就要读一次状态来分派，零额外成本。

这样 staff 手工调 `release` 时「已经释放过」依然报错，不会静默成功；既有单测 `AccrualServiceTest.release_nonOpenStatus_throwsInvalidStateTransition`（用 CONVERTED）**一行不用改**，正好守住这条边界。

真实重试路径上幂等由 `cancelForCustomer` 的 status guard 兜住：第二次取消时 DO 已是 CANCELLED ≠ PENDING_DISPATCH，第 2 步就 409 了，根本走不到冲销。

## 7. 错误处理

### 7.1 异常翻译链（逐环核实）

```
FinanceException(ACCRUAL_ALREADY_CONVERTED)      FinanceException extends BizException,
                                                 @Getter ErrorCode errorCode → 可 == 比对枚举
  ↓ BillingEngineServiceImpl.assertReversible 抛 (预检阶段, DO 未被修改)
catch (FinanceException ex)                       lumen-dispatch 捕获并改写文案
  ↓
PortalBadRequestException(409_001, "订单已完成计费，无法取消")
  ↓ PortalOrderController.mapPortalBadRequest case 409_001   ← 该分支已存在, 不改
CustomerException(PortalErrorCode.ORDER_NOT_CANCELLABLE)
  ↓ CustomerExceptionHandler
HTTP 409 + body.message
  ↓ http.ts 响应拦截器只对 401 做特殊处理, 409 走普通 reject   ← 已读, 不拦截
OrderDetail.onCancel catch → message.error(e.response.data.message)  ← 原样透传后端文案
```

### 7.2 沿用 409_001 而不新开 portal code

代价：客户端分不清「状态不对」和「已开票」两种 409。但两者对客户都是同一句话「这单你取消不了」，真正区分靠后端文案。新开一个 portal code 只会让 `PortalErrorCode` 和 FE 多一个分支，却不改变用户看到的东西。

### 7.3 FE 零改动是核实过的

第 4、5 两环都已在代码里跑通：`http.ts:35` 的拦截器条件是 `err.response?.status !== 401`，409 原样 reject；`OrderDetail.tsx:93` 是 `message.error(e?.response?.data?.message || ...)`，原样显示后端文案。所以 FE 不用动。

### 7.4 非阻塞 catch 的日志规范

```java
log.error("cancelForCustomer: 计费冲销失败, 订单已取消但 accrual 未释放 "
        + "tenantId={} doId={} sourceEventId={} businessType={} 原因={}",
        tenantId, order.getId(), sourceEventId, "LAST_MILE", ex.toString(), ex);
```

必须带 tenantId + doId + sourceEventId，且传 `ex` 保留堆栈 —— 否则事后日志里一堆「冲销失败」根本定位不到是哪张单。

### 7.5 `business_type` 不匹配的防御

查询固定用 `LAST_MILE`。若同一 `source_event_id` 存在不同 `business_type` 的行（理论上不会，`createForCustomer` 写死 `LAST_MILE`），匹配不上，按「查不到」处理、不动它。

## 8. 测试策略

共 **15 个新用例**，四层。

### 8.1 dispatch 编排（扩展 `DeliveryOrderServiceCancelForCustomerTest`，3 例）

| case | 关键断言 |
|---|---|
| 冲销成功 | `updateById` × 1、status=CANCELLED、事件照发 |
| `assertReversible` 抛 `ACCRUAL_ALREADY_CONVERTED` | `PortalBadRequestException(409_001)` + **`verify(orderMapper, never()).updateById(any())`** + **`verify(billingEngineService, never()).reversalForSourceEventId(any(), any(), any())`** + 事件不发 |
| `reversalForSourceEventId` 抛其它异常 | cancel **仍然成功**、DO=CANCELLED、不 rethrow |

第 2 条的两个 `never()` 是整个设计的核心时序断言 —— 只有它们能证明「409 时 DO 没被改」且「预检失败就没往下走」。

### 8.2 finance 分派（扩展 `BillingEngineServiceTest`，9 例）

现有 `setUp()` 已经 stub 了一个 `txManager`（`BillingEngineServiceTest.java:89`，注释写明是给 REQUIRES_NEW 分支用的），所以 `requiresNewTx` 在单测里能跑。只需补一个 `@Mock AccrualService` 进构造参数（`accrualMapper` 已经是 mock，`assertReversible` 够用）。

`assertReversible` 3 例：查不到 → 放行 / OPEN → 放行 / CONVERTED → 抛 `ACCRUAL_ALREADY_CONVERTED`。

`reversalForSourceEventId` 6 例：查不到 / OPEN / OPEN_FAILED / RELEASED（`verify(accrualService, never()).release(...)`）/ CONVERTED / LOCKED。其中 OPEN / OPEN_FAILED 两例还要断言 `accrualService.release(tenantId, accrualId, reason, null)` 的**四个参数**——第四个 `operatorId` 传 null 表示系统操作。

### 8.3 release 放宽（扩展 `AccrualServiceTest`，1 例）

新增 `release_openFailedAccrual_succeeds`。既有 `release_nonOpenStatus_throwsInvalidStateTransition` 不动。

### 8.4 IT（新建 `PortalCancelAccrualReversalIT extends PortalOrderFixtureBase`，2 例）

用 `JdbcTemplate` seed accrual 行（`source_event_id` = doId、`business_type` = `LAST_MILE`），调真实的 `POST /api/customer/order/{doId}/cancel`。

为此给 `PortalOrderFixtureBase` 加一个 `seedAccrual(long doId, String status)` helper（比照既有 `seedRateOverride` / `seedActiveLastMileRule` 的写法，用 `nextId()` 取主键并登记到集合），并在既有 `cleanPortalFixture` 的 `@AfterEach` 里清理 —— 容器复用模式下不清会逐次累积。

- `cancel_releasesOpenAccrual` → 断言 DO=CANCELLED **且** `t_billing_accrual.status = RELEASED`
- `cancel_releasesFailedAccrual` → 同上，seed 的是 OPEN_FAILED

**第二条是 V38 唯一的回归防线。** `release` 内部会调 `assertSmTransition(OPEN_FAILED → RELEASED)`，V38 漏写或写错边必红；而 §8.2 的单测 mock 掉了 `StateMachineEngine`，挡不住。

### 8.5 既有 IT 与 FE 零改动（不是遗漏）

`PortalOrderFixtureBase.seedDeliveryOrder` 直接用 `JdbcTemplate` 插 DO，**不走** `createForCustomer`，所以现有 7 个 `extends PortalOrderFixtureBase` 的 IT（`PortalOrderCancelPendingIT` / `PortalOrderCancelDispatchedForbiddenIT` / `PortalOrderCreateIT` / `PortalOrderCrossCustomer404IT` / `PortalOrderPickupWindowValidationIT` / `PortalOrderPreviewIT` / `PortalOrderReadWindowIT`）里根本不存在 accrual，新逻辑全部走「查不到」分支空转。

不依赖这一点来「让测试通过」 —— 新路径由 §8.4 正面覆盖；这里只是说明为什么既有 IT 不受影响。

FE 无改动 → 不加 Vitest。

### 8.6 回归范围

受影响模块：`lumen-finance` / `lumen-dispatch` / `lumen-customer` / `lumen-bootstrap`（IT）。**不跑全量回归**（用户明确约束）。

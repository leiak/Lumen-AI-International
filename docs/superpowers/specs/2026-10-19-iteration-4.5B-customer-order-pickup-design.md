# 4.5B Customer Portal — Order & Pickup Booking Design

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this spec task-by-task via a plan doc. Steps use checkbox (`- [ ]`) syntax in the plan, not this spec.

**Goal:** 让商家在 `lumen-customer-web` 自助下单 (含取件时间窗选择 + 实时价格预估) + 取消, 替代 30% 走 CS 坐席的下单类工单.

**Architecture:** 复用 4.5A 的 `lumen-customer` 模块 + 4.5A 加的 `wms_delivery_order.customer_id` 字段, 扩 `DeliveryOrderService` 加 `createForCustomer` / `cancelForCustomer` 重载, 同步调 `BillingEngineService.estimate` (不写库, 只跑 Aviator) + 在 `lumen-finance` 加 `t_customer_rate_override` 表做合同价简化版. 前端在 `lumen-customer-web` 加 3 页面 (CreateOrder / OrderList / OrderDetail) + 8 Vitest.

**Tech Stack:** Spring Boot 3.2.5 / MyBatis-Plus 3.5.7 / Flyway / JJWT 0.12.6 / Vite 5 / React 18 / TS 5 / Antd 5 / zustand 4 / Vitest 1.

## 1. Goals & Non-Goals

### 1.1 业务目标 (P0)
- 商家能创建配送单 (含起止地址/重量体积/取件时间窗), 实时看到价格预估
- 商家能取消自己创建的 `PENDING_DISPATCH` 单子
- 商家能查看自己所有的 DO 列表 + 详情 (复用 4.5A Track)
- 跨租户/跨客户的 ownership 校验与 4.5A 一致 (404 兜底)

### 1.2 技术目标
- 同步价格预估: < 200ms (单条 rule 命中 + Aviator 求值, 命中 override 直接返 base_amount)
- 复用 4.5A 既有的 `CustomerContext` (ThreadLocal) + `CustomerException` + `JwtAuthenticationFilter` (aud=portal) + V33 7 个 perms
- 保持 `lumen-customer` 模块零循环依赖: 服务层返 `Map<String,Object>`, controller 转 DTO

### 1.3 非目标 (YAGNI 4.5B 排除)
- ❌ 合同价谈判 / 自动议价 — 4.5B 走 override 表简化版, 不做 bidding
- ❌ 在线支付 — 4.5C 财务对账范畴
- ❌ 修改已下单字段 (改地址/时间) — 下单后只能取消重下 (CS 走 staff 路径)
- ❌ 跨仓调度 / 多段路由 — 商家选 warehouseId, 调度员/系统后续处理
- ❌ 商家上传图片 / 备注附件 — 4.5D 评价/工单再做
- ❌ e2e Playwright — 跟 4.5A 一致, 不做
- ❌ refresh_token HttpOnly cookie / 登录失败锁 — 4.5B.2 polish 阶段独立子 spec
- ❌ 改密 / AuditLog.customer_id 字段 — 4.5B.2 独立子 spec

## 2. User Stories

### US-1: 商家下单
> 商家登录后, 进 `/orders/new` → 选仓库 / 填起止地址 / 填重量体积件数 / 选取件时间窗 → 实时看到价格预估 → 点提交 → 跳详情页看到新建单 PENDING_DISPATCH

### US-2: 商家看自己的单子
> 商家进 `/orders` → 看到自己的 DO 列表 (按创建时间倒序) → 点单子进详情 → 看 status 时间线 + POD (若 SIGNED)

### US-3: 商家取消自己的 PENDING 单
> 商家进 `/orders/{id}` → 看到 PENDING_DISPATCH 状态有 "取消" 按钮 → 点 → 弹原因输入 → 确认 → status 变 CANCELLED, 列表里灰色显示

### US-4: 商家不能取消 DISPATCHED/ENROUTE/ARRIVED 单
> 商家进 `/orders/{id}` 看到 DISPATCHED, 提示 "请联系客服" + 客服电话 (不显示取消按钮)

### US-5: 实时估价
> 商家在 CreateOrder 页填完所有字段, 触发 preview 接口, 看到 "预估 ¥123.45 (按 1-3 个 30kg 内, 5km 内)" 类 breakdown, 数字随输入变

## 4. Backend API Surface

### 4.1 路由前缀
所有 portal 端点继续在 `lumen-customer/controller/PortalOrderController.java`, 前缀 `/api/customer/orders`, 由 `JwtAuthenticationFilter` 强制 `aud=portal`.

### 4.2 5 个端点

#### POST `/api/customer/orders/preview` — 实时估价 (不写库)
- 权限: `customer:order:create`
- 入参: 同 CreateOrder 但所有字段必填
- 返参:
```json
{
  "code": 0,
  "data": {
    "estimatedAmount": 123.45,
    "currency": "CNY",
    "source": "RULE_AUDIT",   // 或 "RATE_OVERRIDE"
    "ruleId": 17,             // override 时为 override.id
    "breakdown": "基础 1-3 件 30kg ¥100.00 + 距离 5km ¥23.45"
  }
}
```
- 行为: 调 `BillingEngineService.estimate(tenantId, customerId, "LAST_MILE", env)`, 不写 `t_billing_event_log` / `t_billing_accrual`. FE 用作下单页实时展示.

#### POST `/api/customer/orders` — 真下单
- 权限: `customer:order:create`
- 入参: `PortalCreateOrderRequest` (见 §4.3)
- 返参: `R<WmsDeliveryOrder>` (整张 DO, 含 `no` / `id` / `status` / `planned_pickup_window_*`)
- 行为:
  1. 强制 `customerId = CustomerContext.requireCustomerId()` (忽略请求里可能传的值)
  2. 校验 pickup window (见 §7)
  3. 调 `DeliveryOrderService.createForCustomer(tenantId, customerId, req)`
     - impl 内做 tenantId/customerId 强制, 写 DO (PENDING_DISPATCH)
     - **同步**调 `BillingEngineService.estimateAndAccrue(...)` 写 accrual (跟 4.5A Track 的 preview 不同: 这里真写一条 OPEN accrual, 业务侧后续可走 invoice 流程; 失败不回滚 DO, 记 `OPEN_FAILED` 由后台 job 重试)
     - 发 `DeliveryOrderStateChangedEvent(order, null, PENDING_DISPATCH, "create")` 走 outbox

#### GET `/api/customer/orders` — 列表
- 权限: `customer:order:view`
- 入参: `q` (status / dateFrom / dateTo / q keyword) 同 4.5A Track
- 返参: `R<IPage<Map<String,Object>>>` 同 4.5A Track
- 行为: 复用 `DeliveryOrderService.pageForCustomer(tenantId, customerId, q)`, 但额外返 `planned_pickup_window_start` / `planned_pickup_window_end` 字段 (4.5A TrackQuery 没返, 这里加)

#### GET `/api/customer/orders/{doId}` — 详情
- 权限: `customer:order:view`
- 返参: `R<Map<String,Object>>` 同 4.5A TrackDetail, 加 `planned_pickup_window_start` / `planned_pickup_window_end` / `canCancel` (布尔, 仅 PENDING_DISPATCH 时 true)
- 行为: 复用 `DeliveryOrderService.getDetailForCustomer(tenantId, customerId, doId)`

#### POST `/api/customer/orders/{doId}/cancel` — 客户取消
- 权限: `customer:order:cancel`
- 入参: `PortalCancelOrderRequest { reason: String @NotBlank @Size(max=200) }`
- 返参: `R<WmsDeliveryOrder>`
- 行为:
  - 调 `DeliveryOrderService.cancelForCustomer(tenantId, customerId, doId, reason)`
  - impl 校验 ownership (404), 校验状态 (仅 PENDING_DISPATCH→CANCELLED; 其他状态返 409, code 409_001 ORDER_NOT_CANCELLABLE)
  - 写 cancel 时间戳 + reason 进 `remark` 后缀
  - 发 `DeliveryOrderStateChangedEvent(order, PENDING_DISPATCH, CANCELLED, "cancel")` 走 outbox
  - 同时发 portal audit log (`@Audit(action="cancel", resource="dispatch_order")`)
  - **不发** Billing 任何 event (不冲销 accrual, 由 staff 走 EXCEPTION/CANCELLED 路径时财务侧处理)

### 5.2 `DeliveryOrderServiceImpl.createForCustomer` 关键步骤
```java
@Transactional
public WmsDeliveryOrder createForCustomer(Long tenantId, Long customerId, PortalCreateOrderRequest req) {
    // 1. ownership 不需要校验 (新订单, 不存在跨客户问题)
    // 2. 构造 WmsDeliveryOrder:
    //    - tenantId (强制), customerId (强制)
    //    - no = "PO-" + UUID8 (PO = Portal Order, 区别于 staff "DO-")
    //    - sourceType = "PORTAL" (新枚举值, V36 seed sys_dict OR 走 comment)
    //    - status = PENDING_DISPATCH
    //    - signRequired = 1
    //    - plannedPickupWindowStart / End (从 req)
    //    - 其余字段从 req 直接 copy
    // 3. wmsDeliveryOrderMapper.insert(order)
    // 4. 同步 estimateAndAccrue (finance):
    //    - try { billingEngineService.estimateAndAccrue(order); }
    //      catch (FinanceException e) { log.warn(...); }  // 失败不阻塞 DO 创建
    // 5. 发 DeliveryOrderStateChangedEvent(order, null, PENDING_DISPATCH, "create") via eventBus
    // 6. 返 order
}
```

### 5.3 `DeliveryOrderServiceImpl.cancelForCustomer` 关键步骤
```java
@Transactional
public WmsDeliveryOrder cancelForCustomer(Long tenantId, Long customerId, Long doId, String reason) {
    WmsDeliveryOrder order = wmsDeliveryOrderMapper.selectById(doId);
    // ownership: 跨租户 OR 跨客户 → 404 (与 4.5A getDetailForCustomer 一致)
    if (order == null
        || !Objects.equals(order.getTenantId(), tenantId)
        || !Objects.equals(order.getCustomerId(), customerId)) {
        throw new DeliveryOrderNotFoundException(doId);  // 现有 4.5A 异常
    }
    // 状态 guard: 仅 PENDING_DISPATCH 可取消
    if (!"PENDING_DISPATCH".equals(order.getStatus())) {
        throw new CustomerException(PortalErrorCode.ORDER_NOT_CANCELLABLE);
    }
    // SM 复用 (走现有 WmsDeliveryOrderStateMachine 还是新增一行? 决定 §6.4)
    stateMachine.transition(order, "CANCELLED", "cancel", Map.of("reason", reason));
    // 写 remark 后缀
    order.setRemark(appendCancelReason(order.getRemark(), reason, SecurityContextHolder.user()));
    wmsDeliveryOrderMapper.updateById(order);
    // 发事件
    eventBus.publish(DeliveryOrderStateChangedEvent.of(order, "PENDING_DISPATCH", "CANCELLED", "cancel"));
    return order;
}
```

### 5.4 状态机: PENDING_DISPATCH→CANCELLED by "customer" 角色
现有 SM 在 V20 + V23 migration 中以 `sys_state_transition` 表 seed (V20 12 行 + V23 2 行 = 14 个 DISPATCH_ORDER transition). 4.5B 在 V36 migration 加 1 行, 沿用同一张表的同一种格式:
```sql
-- V36__state_transition_customer_cancel.sql
INSERT INTO sys_state_transition (sm_key, from_state, to_state, action, allowed_role, sort_order)
  VALUES ('DISPATCH_ORDER', 'PENDING_DISPATCH', 'CANCELLED', 'cancel', 'customer', 35);
```
- `sm_key='DISPATCH_ORDER'` 与 V20/V23 一致
- `action='cancel'` 与 staff cancel 共用 action 字符串
- `allowed_role='customer'` 是新角色 (V33 引入, 见 4.5A)
- `sort_order=35` 接在 V20 已有的 30 (staff cancel) 之后, 保留 staff cancel 的 priority

## 6. Price Estimate Algorithm

### 6.1 输入
```java
env = {
    "weight": order.totalWeightKg,         // BigDecimal
    "distance": order.distanceKm,           // BigDecimal, 0 if unknown (4.5B 暂不接地图 API, 默认 0)
    "quantity": order.stopCount,            // Integer
    "stopCount": order.stopCount,
    "totalWeightKg": order.totalWeightKg,
}
```

### 6.2 优先级
```
1. CustomerRateOverride (命中 → 返 base_amount, source=RATE_OVERRIDE, ruleId=override.id)
2. BillingRule.match(tenantId, businessType=LAST_MILE, direction=RECEIVABLE, counterpartyType=CUSTOMER, asOf=now)
   → 命中 → 跑 Aviator expressions 逐条求值求和 → 返 amount, source=RULE_AUDIT, ruleId=rule.id
3. miss → 返 amount=0, source=NONE, breakdown="无匹配计费规则, 后续人工报价"
```

### 6.3 输出
```java
public record EstimateResult(
    BigDecimal estimatedAmount,
    String currency,             // 来自 override.currency OR tenant.defaultCurrency OR rule.currency
    String source,               // RATE_OVERRIDE | RULE_AUDIT | NONE
    Long ruleId,                 // override.id OR rule.id, NONE 时 null
    String breakdown             // 中文一行解释, e.g. "基础 ¥100 + 距离 5km ¥23.45 = ¥123.45"
) {}
```

### 6.4 breakdown 文案生成
- override: "合同价 ¥123.45 (override #17)"
- rule: `BillingRuleItem` 逐条求值时, 收集 `(item.expression → amount)` 拼字符串: "基础 ¥100.00 + 距离 5km ¥23.45 = ¥123.45"

### 6.5 性能预算
- 同步 estimate < 200ms (单条 rule 命中, override 是单 SELECT, Aviator 6 条求值 < 50ms)

## 7. Pickup Window Validation

### 7.1 规则
| 字段 | 规则 | 错误码 |
|---|---|---|
| `planned_pickup_window_start` | 必填 | ORDER_PICKUP_WINDOW_INVALID |
| `planned_pickup_window_start` | `>= now + 2h` (给调度留 2h 响应) | ORDER_PICKUP_WINDOW_TOO_SHORT |
| `planned_pickup_window_start` | `<= now + 30d` | ORDER_PICKUP_WINDOW_INVALID |
| `planned_pickup_window_end` | 可空; 空 = `start + 4h` | (无, 隐式设置) |
| `planned_pickup_window_end` | `> start` | ORDER_PICKUP_WINDOW_INVALID |
| `planned_pickup_window_end` | `<= start + 8h` (最长 8h 窗) | ORDER_PICKUP_WINDOW_INVALID |
| `planned_pickup_window_end` | 同日 (`end.toLocalDate() == start.toLocalDate()`) | ORDER_PICKUP_WINDOW_INVALID |

### 7.2 实现位置
- Controller `@Valid` 注解 + service impl 内手工校验 (兜底)
- 提示: time-of-day 范围 `08:00-20:00` 由 FE 限制 (FE picker), service 校验同日已足够; 跨凌晨就拒绝 (符合"上门取件"现实)

## 10. Listener Fix (WmsOutboundShippedListener 补洞)

### 10.1 现状
`lumen-dispatch/src/main/java/com/lumen/dispatch/listener/WmsOutboundShippedListener.java:46-58` 调 `deliveryOrderService.create(req)`, 但 `OutboundShippedEvent` 已有 `customerId` 字段, listener 丢弃了. 后果: 从 outbound (仓库) 自动创建的 DO `customer_id` 永远为 null, 4.5A 商家看不到这些单子.

### 10.2 修复 (V36 同 PR 改, ~5 行)
走 **方案 A (重载分支)**, 保留 listener 调用点清晰:
```java
// 现有: deliveryOrderService.create(req) 在 WmsOutboundShippedListener.onOutboundShipped
// 改为: 查 req 是否有 customerId, 有则走 createForCustomer 路径, 自动复用 billing estimate
if (req.getCustomerId() != null) {
    PortalCreateOrderRequest portalReq = PortalCreateOrderRequest.fromOutbound(req);
    deliveryOrderService.createForCustomer(req.getTenantId(), req.getCustomerId(), portalReq);
} else {
    deliveryOrderService.create(req);  // 现有 staff 路径, 不变
}
```
DTO `CreateDeliveryOrderRequest` 同步加 `customerId` 字段 (nullable, V36 后允许 staff 创建时也带 customer, 为 staff "代客下单" 留口).

### 10.3 影响
- 现有 IT `OutboundShipEventIT` (lumen-bootstrap) 需加 assertion: outbound 走的 DO 也有 `customer_id`
- 4.5A `PortalTrackIT` 已有"客户能看到自己 DO"用例, 但当时是手工 insert, 不依赖 listener; 4.5B 加一个新 IT 验证 listener 路径

# 迭代 4.5C-2: 商家门户对账 / 发票 / 付款 + 对账异议 — 设计

> **For agentic workers:** 本文档是设计 (design)。实施计划由 `superpowers:writing-plans` 基于本文档产出。

**Goal:** 商家 (B2B 客户) 在独立 SPA `lumen-customer-web` 上自助查看自己的月结对账单、发票与付款记录，并对不认可的差异提出异议; 异议直接落到已有的调账单审批流, 不需要联系 CS 或财务线下沟通。

**Architecture:** 在 `lumen-finance` 新增**商家视角窄接口** `MerchantBillingViewService` —— 所有 `counterparty_id` 过滤、状态判定、字段裁剪都在 finance 侧完成。`lumen-customer` 新增 4 个 portal controller, 只负责取当前登录商家、编解码与错误翻译。异议写入 `t_reconciliation` 新增的三列, 并推进关联的自动调账单进审批。

**Tech Stack:** Spring Boot 3.2.5 / MyBatis-Plus 3.5.7 / Flyway / Apache POI (xlsx) / React + TypeScript + Vite; JDK 17

**父切片:** 4.5C (对账)。4.5C-1 (门户取消的计费冲销) 已完成, 见
`docs/superpowers/specs/2026-10-21-iteration-4.5C-1-portal-cancel-billing-reversal-design.md`。

---

## 1. 背景

4.5A 建了门户起点, 4.5B 让商家能自助下单与选取件窗口, 4.5C-1 让取消订单能冲销应计。剩下的「商家看账单、对差异有话说」一直没有自助通道:

- 财务导出 PDF/Excel 发邮件给商家
- 商家核对后, 有差异就发邮件反馈
- 差异再由财务手工建调账单

本切片把这条链路搬到门户上。

## 2. 范围

### 做

- 商家查看自己的**对账单** (按期次), 含差异标记
- 商家查看自己的**发票** (list / detail)
- 商家查看自己的**付款记录**
- 对已 CLOSED 期次且已自动建调账单的差异**提出异议**
- 商家**跟踪**自己提的异议所关联调账单的审批状态
- 上述三类数据的 **xlsx 导出**

### 不做

- **商家支付 / 退款**。付款仍走银行流水由财务在 admin 侧录入 (`t_payment_record` 只读)
- **PDF 下载**。仓库无任何 PDF 依赖或实现, 中文 PDF 需处理 CJK 字体嵌入; 本轮用 Excel (finance 已有 `poi-ooxml` 依赖与现成 `ResponseEntity<byte[]>` 写法)
- **在线付款/退款审批**
- **商家自助报表** (`PortalReportController`) —— 属 4.5D
- **商家提 CS 工单** —— 见 §3.2 的语义修正
- **应付侧 (PAYABLE)** 数据的商家可见性 —— 见 §4

## 3. 设计前置: 三个被证伪的假设

设计过程中有三个初始假设经查证不成立, 记在这里避免后人重蹈。

### 3.1 现有 finance service 全部没有商家过滤

| Service | 现有 list 签名 | 有 `counterpartyId` 吗 |
|---|---|---|
| `InvoiceService.list` | `(tenantId, status, page, size)` | **无** |
| `ReconciliationService.list` | `(tenantId, period, page, size)` | **无** |
| `PaymentRecordService.list` | `(tenantId, period, direction, page, size)` | **无** |

portal 若直接调这些接口会看到**该租户下所有商家**的数据。所以 §5 的窄接口不是「更干净的选择」, 而是**唯一安全的选择**。

### 3.2 差异已经自动建过调账单, 商家不应再「建调账单」

`ReconciliationServiceImpl.runReconciliation` 对**每一笔非零差异**已经:

```
variance > 0 (应收 > 实收) → ADJ_TYPE_DEBIT  (补收)
variance < 0 (应收 < 实收) → ADJ_TYPE_CREDIT (退款)
→ billingAdjustmentService.create(...)        // 仅 create, 停在 DRAFT
→ recon.adjustment_id = 该单 id
→ recon.reconciliation_status = ADJUSTMENT_CREATED
```

所以商家看到差异时**调账单已经存在**。商家再"建一张"就是针对同一笔差异的双重调账。

商家真正要表达的是「**我不认可这个差额**」, 因此原 spec 的"提工单"更贴近真实语义。最终采用**异议声明**: 商家在该期 recon 行上留下主张与理由, 并把已存在的 DRAFT 调账单推进进审批 (§7)。

### 3.3 `t_billing_adjustment` 没有 `counterparty_id`

`V29__billing_exchange_tax_adjustment.sql` 的列是
`tenant_id / adjustment_no / source_invoice_id / adjustment_type / amount / currency / fx_rate_at_creation / tax_rate / gross_amount / tax_amount / net_amount / reason / status / l1_* / l2_* / error_msg`。

没有 `counterparty_id`、`business_id`、`period`。且 `runReconciliation` 创建时 `sourceInvoiceId` 留空交由 `BillingAdjustmentServiceImpl` 自动 resolve 锚定单, 所以靠 `source_invoice_id` 反查商家也不可靠。

因此**不修改 `t_billing_adjustment`** (它正被 staff 审批流大量使用, 改表风险高于收益), 改为把商家异议与归属都放在 `t_reconciliation` 上 —— 那里本来就有 `counterparty_id` 和指向 adjustment 的 `adjustment_id` (见 §7)。

## 4. 数据可见性契约

商家能看到的行必须同时满足:

```
counterparty_id = 当前登录商家        -- CustomerContext.requireCustomerId()
AND direction    = 'RECEIVABLE'
AND period (CHAR(7), 'YYYY-MM') ∈ 请求范围
```

**为什么额外卡 `direction`, 而不只按 `counterparty_id`:**

- `counterparty_type` 列存在于三张表, 但代码里**没有对应枚举常量** (值来自 `rule.getCounterpartyType()`, 数据驱动), 且**没有 `t_counterparty` 主数据表** —— `counterparty_id` 是裸 BIGINT
- 只按 id 过滤存在理论上的撞车面 (某承运商应付方 id 恰好等于某客户 id)
- `direction='RECEIVABLE'` 语义上就是「商家欠我们的钱」, 天然排除应付侧
- 三张表都有能覆盖该复合过滤的索引 (各自不同, 别照抄成同一个名字):
  | 表 | 索引 | 覆盖情况 |
  |---|---|---|
  | `t_reconciliation` | `uk_recon_tenant_period_cpty (tenant_id, period, direction, counterparty_id, currency, deleted)` | 前 4 列全等值, 最优 |
  | `t_payment_record` | `uk_payment_tenant_period_cpty (tenant_id, period, direction, counterparty_id, payment_date, deleted)` | 前 4 列全等值 |
  | `t_billing_invoice` | `idx_counterparty (tenant_id, counterparty_id, direction, status)` | 该表无 period 列, 走这条 |

`FinanceConstants.DIR_RECEIVABLE / DIR_PAYABLE` **已存在** (L22-24), 直接引用, 本轮不加常量。

**软删除过滤必须显式写**。`BillingReconciliation` 与 `BillingPaymentRecord` 两个实体的字段表里**没有 `deleted`** (而 DDL 有 `deleted TINYINT NOT NULL DEFAULT 0`), 且全仓**没有配 MyBatis-Plus 全局逻辑删除** —— 于是 MP 不会自动补 `deleted = 0`, 查询会把已删行一起捞出来。商家视图必须显式 `.apply("deleted = 0")`。(`BillingInvoice` 有 `@TableLogic`, 走自动过滤; **`BillingAdjustment` 没有** —— V29 的 schema 压根没有 `deleted` 列, 实体里刻意不加 `@TableLogic` / `@Version`, 见 `BillingAdjustment` 的类注释。所以调账单侧**不能**写 `.apply("deleted = 0")`, 那样会生成 `Unknown column 'deleted'`, 让商家调账单页直接 500。)

**「进行中」标识**: 按 `period` 关联 `t_monthly_closing` (`OPEN / IN_PROGRESS / CLOSED`)。非 `CLOSED` 的期次在列表与详情都带「数据可能变动」标识, 且**该期次禁止提异议**。

**字段裁剪**: 只暴露业务语义字段。`rule_id`、`l1_approver_id`、`l2_approver_id`、`payload_json`、`event_log` 关联一律不出 finance 层。

`error_msg` 也一并裁掉 —— 该列被 `AdjustmentService` 复用着存 submit 时间戳 (4.3.2 schema 无独立 `submitted_at` 列), 且同时承载汇率/税额计算错误的诊断文本。商家看到「submitted at 2026-10-21 15:04:05」只会困惑, 属于内部留痕不该外泄。

## 5. 组件与端点

### 5.1 Finance 侧新增窄接口

`com.lumen.finance.service.MerchantBillingViewService` (impl `MerchantBillingViewServiceImpl`)。

所有方法**显式收 `tenantId` + `counterpartyId`, 不读 `TenantContext`** —— 沿用 `AdjustmentService` 既有的「所有方法都接受 `tenantId` 显式参数」惯例。

```
// 查询 (period 一律 'YYYY-MM'; list 类返回 MerchantPage<T>, 带 total)
MerchantPage<InvoiceView>    listInvoices(tenantId, counterpartyId, period, status, page, size)
InvoiceView                  getInvoice(tenantId, counterpartyId, id)
byte[]                       exportInvoices(tenantId, counterpartyId, period, status)

MerchantPage<ReconView>      listReconciliations(tenantId, counterpartyId, period, page, size)
ReconView                    getReconciliation(tenantId, counterpartyId, id)
byte[]                       exportReconciliations(tenantId, counterpartyId, period)

MerchantPage<PaymentView>    listPayments(tenantId, counterpartyId, period, page, size)

// 异议
DisputeResult                raiseDispute(tenantId, counterpartyId, userId, reconId, claimedAmount, reason)
MerchantPage<AdjustmentView> listMyAdjustments(tenantId, counterpartyId, page, size)
AdjustmentView               getMyAdjustment(tenantId, counterpartyId, adjustmentId)
```

返回 DTO 为 record, 放 `com.lumen.finance.dto.portal` (`InvoiceView` / `ReconView` / `PaymentView` / `AdjustmentView` / `DisputeResult`), 字段按 §4 裁剪。

**两个与 finance 现状不一致、必须显式处理的点:**

1. **发票没有 `period CHAR(7)` 列**。`t_billing_invoice` 用的是 `period_year INT` + `period_month INT` 两列 (V26), 而 `t_reconciliation` / `t_payment_record` 才是 `period CHAR(7)`。对外契约三处统一收 `'YYYY-MM'` 字符串, `listInvoices` / `exportInvoices` 内部拆成 `(Integer year, Integer month)` 再进查询 —— 前端不感知这个差异。
2. **分页要返回总数**。finance 现有的 `InvoiceServiceImpl.list` / `ReconciliationServiceImpl.list` 都是 `Page.of(...)` 查完 **`return result.getRecords()` 直接把 total 丢掉**。门户列表前端要用 (ProTable 要 `total` 才能翻页), 所以本接口返回 `MerchantPage<T>` record (`records` / `total` / `page` / `size`), 与 `PortalOrderController.list` 的 `records`/`total`/`page`/`size` 信封对齐。**不复用 `PageResult`** —— 它的字段叫 `pageNum`/`pageSize`, 与门户侧契约差一个名字, 混用会破坏前端。

**过滤一律 `LambdaQueryWrapper`。** finance 模块**零 XML mapper** (`src/main/` 下连 `resources` 目录都没有), 唯一自定义 SQL 是 `CustomerRateOverrideMapper.findActive` 的 `@Select` 文本块。不要开 XML。分页沿用既有 clamp 写法: `page < 1 ? 1 : page` / `size < 1 ? 20 : Math.min(size, 200)`。

**隔离靠查询谓词, 不靠调用方自觉。** 每个 `get` 的 WHERE 恒为:

```sql
WHERE id = :id AND tenant_id = :tenantId AND counterparty_id = :counterpartyId
  AND direction = 'RECEIVABLE'
```

`getMyAdjustment` 的归属校验走 recon 链 (§7.3), 因为 adjustment 自身没有 `counterparty_id`。

路由前缀沿用既有惯例 **`/api/customer/*`** (4.5A/4.5B 已是 `/api/customer/order`、`/api/customer/track`; auth 另有 `/api/auth/portal`)。

| Controller | 路径 | 端点 | 权限码 | 返回 |
|---|---|---|---|---|
| `PortalReconController` | `/api/customer/recon` | `GET /` | `customer:recon:view` | `R<MerchantPage<ReconView>>` |
| | | `GET /{id}` | `customer:recon:view` | `R<ReconView>` |
| | | `GET /export` | `customer:recon:view` | `ResponseEntity<byte[]>` |
| | | `POST /dispute` | `customer:adjustment:create` | `R<DisputeResult>` |
| `PortalInvoiceController` | `/api/customer/invoice` | `GET /` | `customer:invoice:view` | `R<MerchantPage<InvoiceView>>` |
| | | `GET /{id}` | `customer:invoice:view` | `R<InvoiceView>` |
| | | `GET /export` | `customer:invoice:view` | `ResponseEntity<byte[]>` |
| `PortalPaymentController` | `/api/customer/payment` | `GET /` | `customer:payment:view` | `R<MerchantPage<PaymentView>>` |
| `PortalAdjustmentController` | `/api/customer/adjustment` | `GET /` | `customer:adjustment:view` | `R<MerchantPage<AdjustmentView>>` |

权限用 Spring Security 原生 `hasAuthority('...')` 字符串 (全仓既有写法, 无 SpEL bean), 逐端点声明。`POST /dispute` 用 `customer:adjustment:create` 而不是 `recon:view` —— 提异议是写操作, 不能只靠一个只读权限码放行。

共 **10** 个端点 (对账 4 + 发票 3 + 付款 1 + 调账单 2), 与 §5.1 的 10 个 service 方法一一对应。

所有 handler 用 `CustomerContext.requireCustomerId()` 取商家; `raiseDispute` 另需 `userId` 作 `AdjustmentService.submit` 的 `operatorId`。

### 5.3 `CustomerContext` 需补 `requireUserId()`

现有只有 `getUserId()` (nullable) 与 `requireCustomerId()`。`raiseDispute` 需要一个必然非空的 `operatorId`, 按 `requireCustomerId()` 同款写法补 `requireUserId()`, 缺失时抛 `401_003` (`PORTAL_AUTH_INVALID`)。

### 5.4 权限

4.5A 的 V33 已经种过 7 个码 (`customer:invoice:view` = 162、`customer:recon:view` = 163 都在其中), 4.5B.2 的 V36 又补了 `customer:order:cancel` = 168。本轮**只需新增 3 个**并绑到 `customer` 角色 (id 14):

```
customer:payment:view       (id 169)
customer:adjustment:view    (id 170)
customer:adjustment:create  (id 171)
```

**不要重种 `customer:invoice:view` / `customer:recon:view`**。`sys_permission` 上有 `UNIQUE KEY uk_perm_tenant_code (tenant_id, code)`, 而 V33 的 INSERT 写的是 `ON DUPLICATE KEY UPDATE` —— 用新 id 重插已存在的 code, 撞的是这个唯一键而不是主键, MySQL 会**就地更新已存在的那一行**, 新 id 永远不会被创建。V37 正是为此擦屁股 (V36 用 166/167 重插 160/161 的 code, 生成两条悬空 `sys_role_permission`)。`sys_permission` 末态最大 id = 168, `sys_role_permission` 最大 id = 330 (328/329 已被 V37 删) → 本轮 id 从 **169** 起、绑定行从 **331** 起。

**只种 `sys_permission` 不够, 还必须改 `PortalAuthService.CUSTOMER_PERMS`。** 该常量是**硬编码的 8 个码**, 在 `issueToken` 里原样塞进 JWT 的 perms claim —— **它不查 `sys_role_permission`**。漏改的后果是: 登录拿到的 token 里没有新权限码, 4 个新 controller 的每个端点都 403, 而且日志里看不出是权限 seed 还是鉴权的问题。

## 6. 错误处理

`CustomerExceptionHandler` 目前**只处理 `CustomerException`**。`FinanceException extends BizException`, 且 `GlobalExceptionHandler` **已有** `@ExceptionHandler(BizException.class)` 分支, 会用 `ec.getHttpStatus()` 返回 —— 所以它**现在就已经不是 500 了**。问题不在状态码, 在**码值语义**:

`ADJUSTMENT_NOT_FOUND` 在 finance 侧编码成 `400_015` / HTTP **400**。商家调「我的调账单」拿别人的 id 时, 走通用分支会得到 **HTTP 400 + code 400015** —— 既违反下面的 uniform 404 约定, 也把「这张单存在但不是你的」这件事泄漏了。所以本轮补 `@ExceptionHandler(FinanceException.class)`, 唯一职责就是**把白名单内的 finance 码翻译成 `PortalErrorCode`**, 白名单外维持现状 (按 `ec.getHttpStatus()` 返回并记 ERROR)。注意 `FinanceException` 没有 `getCode()` int, 只有父类的 `getErrorCode()` 返回 `ErrorCode` 接口对象, 需要强转。

新增 `PortalErrorCode`:

| 码 | 枚举名 | 触发条件 |
|---|---|---|
| `404_002` | `RECON_NOT_FOUND` | 对账行不存在**或不属于当前商家** |
| `404_003` | `INVOICE_NOT_FOUND` | 发票不存在或不属于当前商家 |
| `404_004` | `PAYMENT_NOT_FOUND` | 付款记录不存在或不属于当前商家 |
| `404_005` | `ADJUSTMENT_NOT_FOUND` | 调账单不存在或无关联异议 |
| `409_002` | `RECON_NOT_DISPUTABLE` | 月结未 CLOSED / 状态非 `ADJUSTMENT_CREATED` / 本期已提过异议 |
| `400_003` | `DISPUTE_REASON_REQUIRED` | 理由为空或短于 `ADJUSTMENT_REASON_MIN_LEN` |
| `400_004` | `DISPUTE_AMOUNT_INVALID` | 填了 `claimedAmount` 但为 **0** (负数是合法主张 —— 商家主张的是差额) |

白名单 (`FINANCE_TO_PORTAL`, **实现后共 8 个 finance 码**会被翻译成商家可理解的响应; 其余全部 500):

| `FinanceErrorCode` | 自身码值 / HTTP | → `PortalErrorCode` | 商家侧 HTTP |
|---|---|---|---|
| `ADJUSTMENT_NOT_FOUND` | `400_015` / **400** | `404_005 ADJUSTMENT_NOT_FOUND` | **404** |
| `RECON_NOT_DISPUTABLE` | `409_005` / 409 | `409_002 RECON_NOT_DISPUTABLE` | 409 |
| `ADJUSTMENT_REASON_REQUIRED` | `400_012` / 400 | `400_003 DISPUTE_REASON_REQUIRED` | 400 |
| `RECONCILIATION_NOT_FOUND` | `404_006` / 404 | `404_002 RECON_NOT_FOUND` | **404** |
| `INVOICE_NOT_FOUND` | `404_004` / 404 | `404_003 INVOICE_NOT_FOUND` | **404** |
| `PAYMENT_RECORD_NOT_FOUND` | `404_007` / 404 | `404_004 PAYMENT_NOT_FOUND` | **404** |
| `BAD_REQUEST` | `400_022` / 400 | `400_005 PORTAL_PARAM_INVALID` | 400 |
| `REPORT_GENERATION_FAILED` | `400_023` / 400 | `500_001 EXPORT_FAILED` | 500 |

**实现期订正 1**: `RECON_NOT_DISPUTABLE` (409_005) 是商家路径上真正会被抛出的那个码 ——
`INVALID_STATE_TRANSITION` (409_003) 在 `MerchantBillingViewServiceImpl` 内部就被收敛成
`RECON_NOT_DISPUTABLE` 了 (调账单状态不对 / adjustment_id 悬空), 它根本逃不出 finance 层,
所以**没有**进翻译表。

**实现期订正 2 —— `400_004 DISPUTE_AMOUNT_INVALID` 不走翻译表**: 商家主张金额为 0 是
**controller 层**的形状校验 (`PortalReconController#dispute` 直接抛
`CustomerException(PortalErrorCode.DISPUTE_AMOUNT_INVALID)` = 400_004), 它压根不是
`FinanceException`, 自然不经过 `FINANCE_TO_PORTAL`。finance 侧的兜底用
`FinanceErrorCode.BAD_REQUEST` → 翻成 `400_005 PORTAL_PARAM_INVALID` —— service 兜底只保证
"是 400 不是 500", 精确的 400_004 由 controller 给。同理
`ADJUSTMENT_AMOUNT_INVALID` (400_011) 也不在翻译表里 —— 商家路径从不抛它。

**为什么第一条必须翻译**: `ADJUSTMENT_NOT_FOUND` 在 finance 侧编码成 `400_015` (语义上是 404, 历史编码如此)。直接放行会把「不是你的单」报成 400, 既违反下面 uniform 404 的约定, 也泄漏了该 adjustment 存在这一事实。

约定:

- **跨商家访问一律 uniform 404** —— 不区分「不存在」与「不是你的」, 沿用 4.5A/B 做法
- **xlsx export** 返回 `ResponseEntity<byte[]>` + `Content-Disposition`, 与 `BillingReportController` 现有写法一致; 生成失败记 ERROR 后抛 500, **不返回半截文件**
- **finance 不可用时商家侧就是 500**。这与 4.5C-1 的取消冲销不同 —— 冲销在订单关键路径上故 fail-open; 商家看账单是只读场景, 失败如实报错, 不降级

## 7. 异议流程

### 7.1 数据落点

新增迁移 **V39**, 给 `t_reconciliation` 加三列:

```sql
ALTER TABLE t_reconciliation
  ADD COLUMN dispute_amount DECIMAL(18,4) NULL COMMENT '商家主张金额, NULL = 仅质疑不主张',
  ADD COLUMN dispute_reason VARCHAR(500)  NULL COMMENT '商家异议理由',
  ADD COLUMN dispute_at     DATETIME(3)   NULL COMMENT '异议时间, 非空即该期已被异议';
```

落在 recon 行而非 adjustment 行, 因为**异议的自然粒度就是 `(period, direction, counterparty)`** —— 正是 recon 的粒度 (`uk_recon_tenant_period_cpty`)。放 adjustment 上则需新建表。

### 7.2 提异议 (`POST /api/customer/recon/dispute`)

请求体 `{ reconId, claimedAmount?, reason }`。单个事务内:

1. 按 §4 谓词取 recon 行, 取不到 → `404_002`
2. 校验该期 `t_monthly_closing.status = CLOSED`, 否则 `409_002` —— **只有该期已 CLOSED 才可提异议** (进行中的数字会变, 异议无意义; 无月结记录 / `OPEN` / `IN_PROGRESS` 一律按"未闭期"处理)
3. 校验 `reconciliation_status = ADJUSTMENT_CREATED` 且 `adjustment_id` 非空, 否则 `409_002` (没跑过对账就没有异议对象)
4. 校验 `dispute_at IS NULL`, 否则 `409_002` —— **同一期只允许一次异议** (幂等: 重复提交不建单、不重复推进)
5. `reason` 非空且长度 ≥ `ADJUSTMENT_REASON_MIN_LEN`, 否则 `400_003`; `claimedAmount` 若填则**不得为 0**, 否则 `400_004` —— 负数是合法主张 (商家主张的是差额), 「只质疑不主张金额」的做法是留 `null` 而不是填 0
6. 写 `dispute_amount` / `dispute_reason` / `dispute_at` —— **必须是一条带 CAS 谓词的条件更新**: `WHERE id = ? AND tenant_id = ? AND counterparty_id = ? AND direction = 'RECEIVABLE' AND deleted = 0 AND dispute_at IS NULL`, 影响行数 ≠ 1 就按 `409_002` 处理。`t_reconciliation` 没有 `version` 列、`BillingAdjustment` 也没有 `@Version`, 所以乐观锁只能靠 `dispute_at IS NULL` 这个谓词自己实现; 先查后写会被并发请求穿透 (两笔异议都通过第 4 步检查, 后写的那笔会覆盖前一笔)
7. 取关联 adjustment: 若状态为 `DRAFT` 则调 `AdjustmentService.submit(tenantId, adjustmentId, userId)` 推进到 `PENDING_L1`; 若已是 `PENDING_*` 说明已推进过, **不重复调用 submit**, 但仍然写三列并返回当前状态; 其它状态 (`REJECTED` / `L2_APPROVED` / `POSTED` 等) 说明这笔差异已经被财务处理完, 再提异议 → `409_002`

**自动调账单的 `amount` 不被商家主张改写** —— 那是 finance 按差异算出来的账务金额; 商家的主张只作为异议记录存在, 由财务在 L1/L2 审批时权衡。

### 7.3 「我的调账单」的归属链

`t_billing_adjustment` 无 `counterparty_id` (§3.3), 所以:

- **列表**: 查 `t_reconciliation` 中 `dispute_at IS NOT NULL AND counterparty_id = :me` 的行, 带出 `adjustment_id` 与审批状态
- **详情**: 按 `recon.adjustment_id` 取 adjustment, 归属校验**始终回到 recon 那一侧**确认 `counterparty_id = :me`

不依赖 adjustment 自身的商家字段, 也不需要给它加列。

### 7.4 商家认可的情况

商家认可差异时不点任何东西 —— 那张自动调账单仍停在 `DRAFT`, 等 staff 在 admin 侧手工 `submit`。**这是既有行为, 本切片不改变**。把它自动化 (例如「商家确认」也推进审批) 留后续迭代, 因为商家不登录门户会卡住整个审批流。

### 9.1 Finance 单测

## 10. 风险与已知缺口

- **商家不登录门户则对账异议无人提出**, 自动调账单停在 DRAFT 等 staff 手工 submit (§7.4)。这是既有行为, 本切片不改变
- **既有 finance list 接口漏了 tenantId 过滤** —— `ReconciliationServiceImpl.list` 与 `PaymentRecordServiceImpl.list` 的 `LambdaQueryWrapper` 里**没有 `.eq(tenantId)`**, 收了参数不用。商家门户**不得复用这两个方法**, 必须走 §5.1 的窄接口。这属于既有缺陷, 本切片只绕开不修 (修了会改变 admin 侧 `BillingReconciliationController` 的返回, 超出本切片范围, 另开)。**新代码里任何漏掉 tenantId 的地方都是越权面**。
- **`direction='RECEIVABLE'` 硬过滤**: 将来若某商家同时是承运商 (有应付侧), 需要显式改造这条契约并重新评估越权面, 不能只去掉一个条件
- **`counterparty_type` 无枚举也无主数据表**: 本切片绕开它 (§4)。若将来要按类型区分, 需先补 `t_counterparty` 主数据
- **`t_payment_record` 无外键到 invoice**: 付款记录与发票的关联靠 `period + counterparty + direction`, 详情页只能按期次呈现, 无法逐笔勾稽
- **xlsx 在大期次下的内存占用**: 导出无分页流式写出, 期次极大时可能吃内存。本轮按现有 `ReportService.export` 写法实现, 与既有导出同风险等级

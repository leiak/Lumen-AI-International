## 1. 背景

4.5C-2.1 收尾时记录了「已知缺口 15:finance 端点的参数类型不匹配返回 500 而不是 400」,并把下一轮的方向定为「质量与正确性」。本切片从该方向的候选清单里取两项:

- **缺口 #1**:`FinanceTestApplication` 的组件扫描漏了 `com.lumen.extension.state` → finance 模块 30 个测试类里唯一那个 `@SpringBootTest`(`BillingRuleMapperTest`)常年红;其余 29 个全是 mock 单测 → **SQL 层与事务层的问题在本模块无处可测**

调查推翻了 #2 的原始表述,并在同一条链路上查出三个**用户可见**的缺陷。本文档记录调查结论与修法。

## 2. 调查结论

> **行号基准**:本节引用的行号与方法名基于**基线 `1d53582`**(4.5C-2.1 收尾,即 4.5D-1 修复
> **之前**的文件版本)。修复后 `BillingEngineServiceImpl` 的行号有位移(`accrue` 现于 `:111`,
> `estimateAndAccrue` 现于 `:339`),且 `writeFailureAudit` 已拆成 `writeOpenFailedAccrual`
> (accrue 路径)/ `writeEstimateAndAccrueFailureAudit`(estimateAndAccrue 路径)—— 查当前代码请按
> **方法名**定位,不要按本节的行号。

### 2.1 被推翻的假设:自调用没有造成写入不原子

`accrue`(`BillingEngineServiceImpl.java:101`)带 `@Transactional`(`:100`),但 `estimateAndAccrue`(`:292`)在 `:311` 直接调 `accrue(event)` —— 同 bean 自调用,不走代理,注解不生效。

**但今天没有丢原子性**,因为唯一生产调用方自带事务:

| 调用方 | 位置 | 外层事务 |
|---|---|---|
| `DeliveryOrderServiceImpl.createForCustomer` | `lumen-dispatch/.../DeliveryOrderServiceImpl.java:687` | **有** —— `@Transactional` 在同文件 `:630` |
| `BusinessEventListener` | `lumen-finance/.../BusinessEventListener.java:73` | 有 —— 跨 bean 接口调用 → 走代理 → `accrue` 自己的 `@Transactional` 生效 |

自调用唯一的后果是「`accrue` 失去了自己独立的事务边界」,而这个边界今天没有任何调用方依赖。**它是一条契约隐患,不是一个正在流血的 bug。**

### 2.2 真正的缺陷:失败取证链路整条报废

求值失败(表达式非法 / 变量超白名单)时的系统契约是三条:

1. 写 `t_billing_event_log.process_status = 'FAILED'`(失败留痕)
2. 写一行 `t_billing_accrual` status = `OPEN_FAILED`(金额 0,供后台 job 重试)
3. 抛 `FinanceException(EXPRESSION_INVALID)`,由 listener catch 后交 outbox 重试

今天这三条**全部落空**:

**缺陷 ① —— `rule_id` NOT NULL,OPEN_FAILED 取证行根本写不进去**

`writeEstimateAndAccrueFailure`(`:386-405`)设置了 12 个字段,**唯独没设 `ruleId`**。而:

- schema:`t_billing_accrual.rule_id BIGINT NOT NULL`,无 DEFAULT(`V26__billing_schema_and_rbac.sql:97`)
- MyBatis-Plus 3.5.7 默认 `insertStrategy = NOT_NULL` → `ruleId=null` 的列被从 INSERT 语句里**整个省略**
- MySQL 8 strict mode → `ERROR 1364 Field 'rule_id' doesn't have a default value`

→ `estimateAndAccrue` 的 `catch` 块(`:322-331`)里 `requiresNewTx.executeWithoutResult(...)` 抛出数据访问异常 → 传播出 `estimateAndAccrue` → 被 `DeliveryOrderServiceImpl.java:688` 的 `catch (Exception)` 吞掉 → **订单照常提交,账上零行痕迹**。

`README.dev.md:1194` 与 `BillingEngineService.java:61` 承诺的「写 OPEN_FAILED accrual,由后台 job 重试」**没有对象可重试**(仓库里也**没有**任何「扫 DO 缺 accrual 补」的后台 job)。

**缺陷 ② —— REQUIRES_NEW 行锁等待,失败取证整条路径挂死**

`accrue` 在**外层未提交事务**里 `eventLogMapper.insert(logRow)`(`:119`)→ 该行被外层事务持 **X 行锁**。求值失败时(`:173-175`):

```java
requiresNewTx.executeWithoutResult(status -> writeFailureAudit(logRow, event, rule.getId(), err));
```

`writeFailureAudit`(`:357`)→ `markFailed`(`:346`)→ `eventLogMapper.updateById(logRow)` → 要 UPDATE 那一行 → 内层新连接等外层 → `innodb_lock_wait_timeout`(默认 **50 秒**)→ 超时异常。

Spring 的 `PROPAGATION_REQUIRES_NEW` 只是**挂起**外层事务(不回滚、不提交),外层的行锁**依然持有**。

**仓库自带对照组反证**:`BillingRuleServiceImpl.commitInvalidAndAudit`(`:214-246`)用的是同一模式,但它安全 —— 差别在于外层 `activate` 只 `SELECT` 过 rule 行、**从未写过它**(无锁)。而 `BillingRuleActivationIT.activate_invalidExpression_throwsAndSetsInvalid` 实测通过 → 模式本身在真实 MySQL 上是通的,差别只在「外层有没有写过那一行」。

**路径可达性**:`DeliveryOrderServiceImpl.java:680-684` 的注释自己写着「key 超出白名单会抛 FinanceException_UnknownVar, 导致 accrue 永远失败」→ 这条路径是**可到达**的。

**路径 2(listener)同样中招**:那里 `accrue` 走代理 → 有自己的事务 → `event_log` 的 INSERT 在那个事务里**未提交** → 失败时的 REQUIRES_NEW UPDATE **一样要等锁**。回滚发生在异常抛出**之后**;而在异常抛出之前,那一行一直未提交、一直被外层持锁。→ **两条路径今天都挂 50 秒。**

**缺陷 ③ —— 对外异常类型失真**

`:173-178` 的顺序是「先 `requiresNewTx`、后 `throw FinanceException`」。① 或 ② 任一成立时,抛出去的是数据访问异常,**`FinanceException` 根本没机会抛出** → `BillingEngineService.java:39-40` 声明的「仅在求值失败时抛 `FinanceException`」与 `BusinessEventListener.java:74-77` 的「catch 后交 outbox 重试」契约全部失真。

### 2.3 净效果

> **客户下单成功,账上一行痕迹都没有,请求挂约 50 秒。**
>
> 两条调用路径(`createForCustomer` 与 `BusinessEventListener`)都挂 50 秒。

## 3. 目标

1. 失败取证链路在**任何**失败点都能完整落库(`event_log=FAILED` + `accrual=OPEN_FAILED`),且不产生长挂起
2. 对外抛出的异常类型回到契约:`FinanceException`
3. 「取证本身失败」不阻断下单主流程,但必须留日志 —— 不能静默
4. `estimateAndAccrue` 具备自足的事务边界(契约护栏)
5. finance 模块的测试入口与生产对齐,SQL 层 / 事务层的问题有地方可测

## 5. 设计

### A1 —— `rule_id` 改可空(新迁移 V41)

**改法**:`V41__billing_accrual_rule_id_nullable.sql`

```sql
ALTER TABLE t_billing_accrual MODIFY COLUMN rule_id BIGINT NULL;
```

**为什么不用「补 ruleId」**:

- `EstimateResult` 的 javadoc 明确「ruleId 仅 SOURCE_RULE 时非空」→ **override 命中时本就没有 rule 归属**
- estimate 阶段失败时,规则归属**本就未知** —— 硬填一个值反而是编造
- `t_billing_accrual` 只有 `uk_accrual` 与 `idx_status`,**无 FK on rule_id**(`V26:90-114`)→ 改列无牵连
- `accrue` 阶段的失败(`writeFailureAudit`,`:357-379`)**本来就带 ruleId** → 不受影响

**同步**:`estimateAndAccrue` 的 `catch` 里,若能拿到 ruleId 则补上。`EstimateResult result` 目前声明在 `try` 块内(`:299`)→ catch 看不到 → 需提到 `try` 外面。但这只能覆盖「estimate 成功、accrue 失败」的情形;「estimate 自身抛异常」时 ruleId 仍不可得 → **列必须可空**。

### A2 —— REQUIRES_NEW 锁等待:把 `markFailed` 移回 accrue 事务内

**改法**:把 `markFailed(logRow, err)`(event_log 的 UPDATE)从 `requiresNewTx` 回调里**移出**,改成在 `accrue` 方法体内、抛 `FinanceException` **之前**直接执行;`REQUIRES_NEW` 里只保留 `OPEN_FAILED` accrual 的 INSERT。

**为什么这样就没有锁冲突**:FAILED UPDATE 与 `event_log` 的 INSERT 落在**同一个事务**里 → 自己 UPDATE 自己未提交的行 → 无冲突。

**两条路径的行为**:

| 路径 | 外层事务 | `event_log` 结果 | `accrual` 结果 |
|---|---|---|---|
| 1 `createForCustomer` | catch 后**提交** | `=FAILED` 存活 ✓ | `OPEN_FAILED` 独立提交 ✓ |
| 2 `BusinessEventListener` | `accrue` 自己的事务**回滚** | 行不存在(整个事务回滚)—— **今天也是行不存在**(今天挂在锁等待上,内层回滚后同样什么都没留下)→ **无回退** | `OPEN_FAILED` 独立提交 ✓ |

**路径 2 是严格变好**:今天是「挂 50 秒 + 什么也没留下」,修完是「不挂 + 留下 OPEN_FAILED 取证行」。

**明确放弃的一点**:原设计的意图是「失败标记活过外层事务回滚」。A2 在路径 1 依然满足这一点(外层提交);在路径 2 上与今天一样不满足(行不存在)—— **没有比现状更差**。

**`markNoRule`(`:337`)不动**:它本来就在 accrue 的事务内(不在 `REQUIRES_NEW` 里)→ 路径 1 中自己 UPDATE 自己未提交的行 → 无冲突。

### A3 —— 异常契约:取证失败不得顶掉 `FinanceException`

**改法**:失败取证的写库调用用 try/catch 兜住并 `log.error`,**然后照旧抛 `FinanceException`**。

- 对外异常类型回到契约 ✓
- 「取证本身失败」不阻断下单(主流程关键路径)✓
- 但取证失败必须留日志 —— 不能像今天这样被 `DeliveryOrderServiceImpl:688` 的 `catch (Exception)` 静默吞成一行 warn ✓

**边界**:若连 `FinanceException` 的构造都失败(不可能),才允许原始异常上抛。

### A4 —— `FinanceTestApplication` 与生产对齐

**改法**:

```java
@ComponentScan(basePackages = {"com.lumen.finance", "com.lumen.common", "com.lumen.extension.state"})
@MapperScan(basePackages = {"com.lumen.finance.mapper", "com.lumen.common.audit", "com.lumen.extension.state"})
```

**为什么两处都要加**:

- `StateMachineProperties` **不是 `@Component`**,靠同包的 `StateMachineAutoConfiguration` 的 `@EnableConfigurationProperties` 注册 → 必须扫到 `com.lumen.extension.state` 才带上
- `StateTransitionMapper` 是 `@Mapper` 接口,但 `FinanceTestApplication` 显式声明了 `@MapperScan` → MyBatis-Plus 的 `AutoConfiguredMapperScannerRegistrar`(`@ConditionalOnMissingBean(MapperFactoryBean.class, MapperScannerConfigurer.class)`)**退避** → 显式 `@MapperScan` 不含该包时,mapper bean 注册不上

**为什么不扫整个 `com.lumen.extension`**:该包下还有 `approval` 与 `outbox`,依赖 `t_approval_record` / `t_event_outbox` 两张表,finance 测试迁移里没有 → 爆炸半径大得多。只扫 `.state` 正好够。

**为什么不用补 `t_state_transition` 表**:`StateMachineRegistry.init()`(`@PostConstruct`)只建 Caffeine 缓存,**不查库**;`warmup()` 只 `cache.invalidateAll()` → 上下文能起。`BillingRuleMapperTest` 不触达状态机 → **不需要这张表**。YAGNI:真有用例要跑状态机时再补 finance 测试迁移的 V2。

### A5 —— `estimateAndAccrue` 加 `@Transactional`(契约护栏)

**改法**:`estimateAndAccrue`(`:292`)加 `@Transactional`(默认 `REQUIRED`)。

**为什么注解会生效**:它是被**跨 bean** 调用的(`DeliveryOrderServiceImpl` 注入 `BillingEngineService` 接口)→ 走代理 → 注解生效。

**行为**:

- 路径 1:`REQUIRED` 加入 `createForCustomer` 的外层事务 → **行为不变**
- 将来若有人从非事务上下文调它:立刻获得事务边界(这正是护栏的目的)

**注意**:`estimateAndAccrue` 吞掉所有异常(`:316` 与 `:325` 两个 catch 都不抛)→ 事务**正常提交**而非回滚。这正是想要的:失败取证已在独立事务里落库,主事务该提交就提交。

**关于「今天 0 行为变化」的诚实说明**:

- Spring 的事务是**线程绑定**的 —— 即使没有 `@Transactional`,只要调用方线程上已有事务,MyBatis-Plus 的写操作照样加入那个事务(DataSourceUtils 复用同一连接)。所以 A5 **不改变**「有没有外层事务」这件事下的任何行为。
- A5 唯一能改变的场景是:**线程上没有任何事务 + 写入中途失败** → 无 A5 时前面已写的语句已自动提交,A5 时整体回滚。
- 而 `estimateAndAccrue` 吞掉所有异常 → 它的事务**永远不会因异常回滚** → 上述场景在本切片不构造 IT 覆盖。
- 因此 A5 的守卫只有一条:**反射断言该方法带 `@Transactional`**(照 `CustomerExceptionHandlerParamTest` 的仓库先例 —— 因为去掉注解不会让任何行为型用例变红)。
- **A5 是护栏,不是修 bug。** 如果将来有人从非事务上下文调 `estimateAndAccrue`,它挡住的正是「写到一半」的窗口。

## 6. 测试策略

**全部落 `lumen-bootstrap`**,用 `IntegrationBase`(`@SpringBootTest(webEnvironment = RANDOM_PORT)` + Testcontainers MySQL 8.0 + 全量 Flyway schema + 真实 `DataSourceTransactionManager`)。理由:schema 完整、事务基建现成、`OutboxAsyncIT` 提供了可直接抄的形状。

**方法论**:先写 IT 让它**红**,再修。修不出来的就不修 —— 不预先认定缺陷 ② 的锁语义推断成立。

| IT | 断言 | 今天的状态 |
|---|---|---|
| IT-1 失败取证完整性 | 求值失败 → `event_log` 有 `FAILED` 行 **且** `accrual` 有 `OPEN_FAILED` 行(金额 0、`error_msg` 非空) | **红**(1364) |
| IT-2 无长挂起 | 同 IT-1,加 `@Timeout(30, SECONDS)` —— 锁等待会挂 50s | **红**(超时) |
| IT-3 成功路径不回退 | 正常规则 → `event_log=SUCCESS` + `accrual=OPEN` 且金额正确 | 绿(防回归) |
| IT-4 原子性 | `TransactionTemplate` + `setRollbackOnly()` → `event_log` / `accrual` 都无行(**事务内先证明「确实写过」, 回滚后才断言「查不到」**) | 绿(防回归) |
| IT-5 订单端到端 | `createForCustomer` 遇失败规则 → DO 提交成功 + 账上有 `OPEN_FAILED` 痕迹 + 不超时 | **红**(用户可见症状) |
| IT-6 A5 护栏 | 反射断言 `estimateAndAccrue` 带 `@Transactional` | 绿(结构断言) |

**IT-4 守的是什么**:「写入加入**调用方**事务」这一性质。**它不是 A5 的守卫** —— 因为 Spring 事务是线程绑定的,即使没有 `@Transactional`,写操作也会加入调用方已有的事务。IT-4 守的是「别把写操作误改成 `REQUIRES_NEW`」这类回归。

**IT-6 为什么是反射断言**:去掉 `@Transactional` 不会让任何行为型用例变红(见 §5 A5 的说明)。仓库已有同样的先例 —— `CustomerExceptionHandlerParamTest` 用反射断言 `@ExceptionHandler` 存在,理由一模一样。

**原子性用例的形状**(**实际落地版**, 见 `lumen-parent/lumen-bootstrap/src/test/java/com/lumen/integration/BillingFailureAuditIT.java`
的 `rolledBackOuterTransaction_leavesNoEventLogAndNoAccrual`):

```java
TransactionTemplate tx = new TransactionTemplate(txManager);
// 最外层 status.setRollbackOnly() 在 commit 时是**静默回滚、零异常** —— 不需要 try/catch。
tx.executeWithoutResult(status -> {
    billingEngineService.estimateAndAccrue(event);

    // 事务内先证明「确实写进去了」(未提交, 但对本事务自己的连接可见)
    assertThat(jdbc.queryForList(
            "SELECT id FROM t_billing_event_log WHERE source_event_id = ? AND deleted = 0",
            String.valueOf(doId)))
        .as("事务内: event_log 已经写入 (未提交) —— 证明下面断言的「回滚后为空」是真回滚")
        .hasSize(1);
    assertThat(jdbc.queryForList(
            "SELECT id FROM t_billing_accrual WHERE business_id = ? AND deleted = 0", doId))
        .as("事务内: accrual 已经写入 (未提交) —— 证明下面断言的「回滚后为空」是真回滚")
        .hasSize(1);

    status.setRollbackOnly();
});

// 回滚**之后**才断言查不到行
assertThat(jdbc.queryForList(
        "SELECT id FROM t_billing_event_log WHERE source_event_id = ? AND deleted = 0",
        String.valueOf(doId)))
    .as("外层事务回滚后 event_log 不该有行")
    .isEmpty();
assertThat(jdbc.queryForList(
        "SELECT id FROM t_billing_accrual WHERE business_id = ? AND deleted = 0", doId))
    .as("外层事务回滚后 accrual 不该有行")
    .isEmpty();
```

**为什么不需要 try/catch**:最外层事务的 `status.setRollbackOnly()` 在 commit 时是**静默回滚、零异常**
—— Spring 6.1.6 `AbstractPlatformTransactionManager.commit()` 里 `defStatus.isLocalRollbackOnly()`
分支直接 `processRollback(status, false)` 然后 `return`,**不经过 `processCommit()`**,**不抛任何异常**。
(`javap -p -c` 复核: `commit()` 的字节码在 26 处调 `isLocalRollbackOnly()`,54 处调
`processRollback(status, false)`,57 处 `return`; 而 `processCommit()` 里**没有**任何
`isLocalRollbackOnly()` 引用 —— 只有三处 `isGlobalRollbackOnly()`。)
`UnexpectedRollbackException` **只在全局 rollback-only 时才抛**(`commit()` 的
`isGlobalRollbackOnly()` 分支 → `processRollback(status, true)`; `processCommit()` 自己的
`isGlobalRollbackOnly()` 分支也会抛)—— 典型场景是**内层参与型事务**
(`PROPAGATION_REQUIRED` 加入外层)失败并被标 rollback-only。仓库里 4.5C-1 的冲销链路
(`BillingEngineServiceImpl.reversalForSourceEventId` 的 javadoc)记的就是那一种,本节不是。

**为什么事务内那一步不能省**:少了它,「回滚后查不到行」这条断言就可能是因为「压根没写进去」
而**空洞地通过** —— 那样它守不住「写了一半」。事务内那两条 `hasSize(1)` 先把「确实写过」钉死,
回滚后的两条 `isEmpty()` 才是「真回滚」的证据。

> ⚠️ **本节早期草稿里的 `catch (RuntimeException commitEx)` 是错的**(4.5D-1 收尾时订正):
> 那段 catch ①**永不命中**(最外层 `setRollbackOnly()` 不抛异常), ②又宽到能吞掉
> `estimateAndAccrue` 内部的**真实失败** —— 于是「压根没写进去」也能让后面两条 `isEmpty()`
> 空洞地绿。同一处错误假定在 plan 与 `OutboxAsyncIT` 里也有,已在 4.5D-1 收尾时一并订正。

**IT-4 的边界说明**:它用的是 `TransactionTemplate` 显式开事务 —— 调用方线程上**本来就有事务**,所以写操作无论有没有 `@Transactional` 都会加入它 → IT-4 今天就是**绿的**。它守的是「写操作没有被人为改成独立事务」,不是 A5 本身。

**IT-5 的构造**:种一条表达式引用白名单外变量的 ACTIVE 规则(例如 `unknown_var * 2`),再调 `deliveryOrderService.createForCustomer`。

## 8. 已知遗留(本切片不修,记录在案)

1. **`estimate` 与 `accrue` 的规则口径不一致** —— `estimate` 走 override 优先(合同价),`accrue` 完全不查 override,只按 rule 求值。`PortalOrderCreateIT` 的 fixture 同时 seed 了 override `88.0000` 与 rule `"weight * 2"`(weight=10 → 20),实际入账写的是 **20 而不是 88**,而该 IT 只断言 `status=='OPEN'`、**不断言金额** → 差异不可见
2. **规则匹配不看 `counterparty_type`** —— `BillingRule.counterpartyType` 是规则 UNIQUE 键的一部分,但 `accrue` 与 `estimate` 的规则查询都没有该过滤 → 一条 `CARRIER` 规则可能被 CUSTOMER 订单命中
3. **`estimate` 的结果被丢弃** —— `EstimateResult.amount` 算出来后从未被使用;javadoc 承诺的「供调用方记录 sourceAmount」没有实现(全仓无 `source_amount` 列、无写入代码)
4. **`uk_accrual` 不含 `status` → 同键的 accrual 行只能有一条, `OPEN` 与 `OPEN_FAILED` 互斥** —— `uk_accrual (tenant_id, source_event_id, business_type, deleted)`(`V26__billing_schema_and_rbac.sql:112`;finance 测试夹具 `V1__billing_schema.sql:88` 同形)与 `status` 无关。两个方向都要知道:
   - **既有 `OPEN_FAILED` 行会挡住重试**:后台 job 必须 **UPDATE** 那行而非 INSERT。这是既有设计,本切片不动,但重试方必须知道。
   - **既有任意 accrual 行会挡住失败取证**(4.5D-1 收尾时核实):`BillingEngineServiceImpl.writeOpenFailedAccrual` 的 INSERT 撞 `uk_accrual` → `catch (DuplicateKeyException)` 把它吞成一行 `log.info("failed-accrual UNIQUE hit, skip")` → **这次失败在账上留不下取证行**(只留一行日志)。触发前提是「同一键上已有**已提交**的 accrual 行,而 `uk_event` 那条 event_log 行不挡着本次运行」。
   - **另一条曾被提出的形状经核实不可达**:「外层事务已插入未提交的 `OPEN` 行、内层 `REQUIRES_NEW` 再插 `OPEN_FAILED` → InnoDB 死锁 → 取证行丢失」。`accrue` 的步骤顺序决定它不成立 —— `OPEN_FAILED` 只在**第 4 步**(逐条求值失败)写,而 `OPEN` 行第 5 步才插;第 4 步抛 `FinanceException` → 第 5 步根本不执行 → 两者互斥 → 那个形状**当前不可达**(不是死锁,而是压根不会同时存在)。
5. **没有「扫 DO 缺 accrual 补」的后台 job** —— `README.dev.md:1194` / `BillingEngineService.java:61` 提到它,仓库里**找不到实现**
6. **`t_billing_accrual.rule_id` 可空后的报表口径** —— 将来若有 accrual 行 `rule_id IS NULL`,报表需明确如何归因
7. **A5 的行为效果无 IT 覆盖** —— 「线程上无事务 + 写入中途失败 → 整体回滚」这一场景本切片不构造(见 §5 A5)。守卫只有 IT-6 的反射断言。若将来 `estimateAndAccrue` 改成会抛异常,应补一条真实的行为型 IT
